# 第8章 托管工具家族

上一章的工具全部跑在你自己的 Python 进程里。但有些能力你根本没法在本地实现——联网搜索、在 OpenAI 的沙箱里跑代码、生成图片、驱动一台虚拟机点鼠标。这些活由 OpenAI 服务端执行，SDK 只负责把"工具声明"翻译成 Responses API 的 payload。

这一章把 0.25 的十个工具一次讲清：谁在执行、参数长什么样、结果怎么回来、什么时候不该用。

## 学习目标

- 能区分 OpenAI 服务端执行、本地执行、以及"服务端决策 + 本地执行"三种工具形态。
- 能说出 `WebSearchTool`、`FileSearchTool`、`CodeInterpreterTool`、`ImageGenerationTool` 的关键参数与结果落点。
- 能判断 `ComputerTool`、`ShellTool`、`ApplyPatchTool` 该由谁提供实现，以及各自的审批语义。
- 能用一张表向同事解释 hosted tool 与 function tool 的差别。
- 能写出"web search + code interpreter"的研究助手，并知道去哪里看它的原始结果。

## 一、先分清三件事

判断一个工具怎么用，先问三个问题：**谁执行、谁付钱、结果落在哪**。

| 类别 | 代表 | 执行位置 | 你的代码能看到什么 |
| --- | --- | --- | --- |
| 托管工具（hosted tool） | WebSearch、FileSearch、CodeInterpreter、ImageGeneration、HostedMCP、ToolSearch | OpenAI 服务端 | 只有 `RunItem` 里的原始条目（`web_search_call`、`code_interpreter_call` 等），**没有回调** |
| 本地运行时工具 | ComputerTool、ShellTool（local）、ApplyPatchTool、LocalShellTool | 你的进程/你的机器 | 你实现 executor/editor，参数与结果都过你的手 |
| 混合型 | ShellTool（container_auto） | OpenAI 托管容器 | 只看到 `shell_call` 条目，命令在你的机器之外跑 |

这个划分决定了两件事：**能不能在工具里做鉴权**（托管工具不行，你拿不到调用时刻），以及**出错时你能不能介入**（托管工具的错误在服务端，SDK 只能转发）。

## 二、OpenAI 服务端执行的六个工具

### WebSearchTool

联网搜索，只在 `OpenAIResponsesModel` 下可用。参数：

| 参数 | 说明 |
| --- | --- |
| `search_context_size` | `"low"`/`"medium"`/`"high"`，控制带回多少上下文，直接影响 token 成本 |
| `user_location` | 近似位置，例如 `{"type": "approximate", "city": "New York"}` |
| `filters` | 域名等过滤条件 |
| `external_web_access` | 是否允许抓取实时网页；`False` 表示只用缓存/索引 |
| `search_content_types` | `["text"]` 或 `["text", "image"]` |
| `image_settings` | `{"max_results": 3, "caption": True}`，仅在包含 `"image"` 时有意义 |

结果不在返回值里，而在 run items：`ToolCallItem` 的 `raw_item` 是一个 `web_search_call`，含 `queries` 与 `results`。请求图片时，SDK 会自动带上 `web_search_call.results`，原始条目里可能有 `image_url`、`thumbnail_url`、`source_website_url`、`caption`，这些内容保存在 `RunResult.raw_responses` 中，与助手消息分开存放。

### FileSearchTool

检索你事先建好的 OpenAI 向量库（Vector Store）。参数：`vector_store_ids`（必填）、`max_num_results`（1–50，`None` 或 0 用服务端默认）、`include_search_results`、`ranking_options`、`filters`。

向量库不是 SDK 建的，要用 OpenAI SDK 或控制台提前建好并索引文件——`repo/examples/tools/file_search.py` 演示了完整流程：上传文件 → 建 store → `create_and_poll` 索引 → 传 `FileSearchTool(vector_store_ids=[...])`。结果同样是 `file_search_call` 原始条目。

### CodeInterpreterTool

在 OpenAI 的沙箱里执行 Python。构造参数只有一个 `tool_config`：

```python
from agents import CodeInterpreterTool

CodeInterpreterTool(tool_config={"type": "code_interpreter", "container": {"type": "auto"}})
```

模型写代码、跑代码、读输出，全程在服务端。你在 `ToolCallItem.raw_item` 里能拿到 `code_interpreter_call` 的 `code` 字段（仓库示例就是靠它把代码打印出来的）。限制：需要支持该工具的模型；仓库示例特别注明，配合 gpt-5 类模型时不要用 minimal reasoning effort，流式使用有时还需要组织级验证。

### ImageGenerationTool

生成或编辑图片。`tool_config` 是 Responses API 原样透传的字典，常用键：`type="image_generation"`、`action`（`generate`/`edit`/`auto`）、`model`、`size`、`quality`、`background`、`output_format`、`input_fidelity`、`moderation`。结果是 `image_generation_call` 条目，`result` 字段是 base64 字符串，示例里解码后写进临时文件。

### HostedMCPTool

把远端 MCP 服务器整体交给 Responses API：你只给 `server_label` 和 `server_url`（或用 `connector_id` + `authorization` 走连接器），模型自己去列工具、调工具，全程不回到你的进程。`tool_config` 里可以写 `require_approval`（`"always"`/`"never"`）、`allowed_tools`、`defer_loading`。

需要审批时，配 `on_approval_request` 回调，它收到 `MCPToolApprovalRequest`，返回 `{"approve": True}` 或 `{"approve": False, "reason": "..."}`。不配的话，待审批项会进 `result.interruptions`，由 `RunState.approve/reject` 处理。

> 注意：`HostedMCPTool` 不要加进 `Agent.mcp_servers`，它是 `tools` 列表里的一项。两者的区别是《第9章 MCP 协议集成》的重点。

### ToolSearchTool

0.25 的"工具搜索"：让模型在运行时按需加载被延迟的工具。相关组件有三个——`@tool(defer_loading=True)` 的延迟函数工具、`tool_namespace(name=..., description=..., tools=[...])` 打的命名空间、以及 `HostedMCPTool(tool_config={..., "defer_loading": True})`。三者任选其一或组合，并**恰好加一个** `ToolSearchTool()`。

约束要记住几条：只有 Responses 模型支持；`ToolSearchTool(execution="client")` 是给手写 Responses 编排用的，标准 `Runner` 不会替你执行客户端搜索，遇到会直接抛错；命名 `tool_choice` 不能指向裸命名空间或纯延迟工具。

顺带一提，同族的 `ProgrammaticToolCallingTool()` 让模型生成一段 JavaScript 来编排多个工具调用（`allowed_callers=["programmatic"]`），适合"循环 + 分支 + 并行"的短流程，细节见 `repo/docs/tools.md` 对应小节。

## 三、本地执行、服务端"出主意"的四个工具

### ComputerTool

每次 `computer_call` 都要你真正操作一台机器。你要实现 `Computer` 或 `AsyncComputer` 接口：`screenshot / click / double_click / scroll / type / wait / move / keypress / drag`，再加上 `environment` 与 `dimensions` 两个属性。

```python
from agents import AsyncComputer, ComputerTool


class BrowserHarness(AsyncComputer):
    environment = "browser"
    dimensions = (1280, 800)

    async def screenshot(self) -> str:
        return "<base64 png>"

    async def click(self, x: int, y: int, button: str) -> None: ...
    async def double_click(self, x: int, y: int) -> None: ...
    async def scroll(self, x: int, y: int, scroll_x: int, scroll_y: int) -> None: ...
    async def type(self, text: str) -> None: ...
    async def wait(self) -> None: ...
    async def move(self, x: int, y: int) -> None: ...
    async def keypress(self, keys: list[str]) -> None: ...
    async def drag(self, path: list[tuple[int, int]]) -> None: ...


computer_tool = ComputerTool(computer=BrowserHarness())
```

它是"本地执行 + 服务端 schema"的典型：工具的 wire 形态是 Responses 的 computer 工具，实际动作全在你这边。两个细节值得记住：模型的 GA 路径（如 `gpt-5.6`）发 `{"type": "computer"}`，旧的 `computer-use-preview` 发 `computer_use_preview` 并需要尺寸；`ComputerTool.name` 为了兼容仍返回 `"computer_use_preview"`，追踪面板显示的是 `"computer"`。另外还有 `on_safety_check` 回调——服务端报 `pending_safety_checks` 时逐个问你，返回 `False` 会在执行动作前抛 `UserError`。

### LocalShellTool 与 ShellTool

`LocalShellTool` 是旧接口：一个 `executor(request: LocalShellCommandRequest) -> str`，`request` 里有 `ctx_wrapper` 和 `data`（`LocalShellCall`）。官方已把它标记为将被 `ShellTool` 取代。

`ShellTool` 是 0.25 的主推形态，同时支持本地与托管容器：

```python
from agents import ShellCommandRequest, ShellResult, ShellTool


async def run_shell(request: ShellCommandRequest) -> str | ShellResult:
    commands = request.data.action.commands
    return ShellResult(output=[])  # 或直接返回一段文本


local_shell = ShellTool(executor=run_shell, needs_approval=True)

hosted_shell = ShellTool(
    environment={
        "type": "container_auto",
        "network_policy": {"type": "disabled"},
    }
)
```

规则很硬：`environment` 省略即本地模式，本地模式**必须**给 `executor`；托管模式**不允许**给 `executor`、`needs_approval`、`on_approval`，给了会 `UserError`。托管模式用 `container_auto`（每次开新容器，可带 `file_ids`、`memory_limit`）或 `container_reference`（复用已有 `container_id`）。本地模式的审批默认关闭，一旦开启，行为与其他工具一样走中断/恢复。

### ApplyPatchTool

让模型用统一 diff 改文件。你实现 `ApplyPatchEditor`：

```python
from agents import ApplyPatchTool
from agents.editor import ApplyPatchEditor, ApplyPatchOperation, ApplyPatchResult


class WorkspaceEditor(ApplyPatchEditor):
    async def create_file(self, op: ApplyPatchOperation) -> ApplyPatchResult:
        return ApplyPatchResult(status="completed")

    async def update_file(self, op: ApplyPatchOperation) -> ApplyPatchResult:
        return ApplyPatchResult(status="completed")

    async def delete_file(self, op: ApplyPatchOperation) -> ApplyPatchResult:
        return ApplyPatchResult(status="completed")


patch_tool = ApplyPatchTool(editor=WorkspaceEditor(), needs_approval=True)
```

同样支持 `needs_approval` 与 `on_approval`。`on_approval` 只在该调用需要审批且尚无既有决策时被调用——"设了回调"不等于"打开了审批"。

## 四、十个工具的参数速查

| 工具 | 执行方 | 关键构造参数 | 结果落点 |
| --- | --- | --- | --- |
| `WebSearchTool` | OpenAI | `search_context_size`、`user_location`、`filters`、`search_content_types`、`image_settings` | `web_search_call` |
| `FileSearchTool` | OpenAI | `vector_store_ids`、`max_num_results`、`include_search_results`、`ranking_options`、`filters` | `file_search_call` |
| `CodeInterpreterTool` | OpenAI | `tool_config={"type": "code_interpreter", "container": {...}}` | `code_interpreter_call` |
| `ImageGenerationTool` | OpenAI | `tool_config={"type": "image_generation", ...}` | `image_generation_call`（base64） |
| `HostedMCPTool` | OpenAI | `tool_config={"type": "mcp", ...}`、`on_approval_request` | `mcp_call` / `mcp_list_tools` |
| `ToolSearchTool` | OpenAI | `description`、`execution` | `tool_search_call` |
| `ComputerTool` | 本地 harness | `computer`、`on_safety_check` | `computer_call` |
| `LocalShellTool` | 本地 | `executor` | `local_shell_call` |
| `ShellTool` | 本地或托管容器 | `executor`、`environment`、`needs_approval`、`on_approval` | `shell_call` |
| `ApplyPatchTool` | 本地 | `editor`、`needs_approval`、`on_approval` | `apply_patch_call` |

## 五、hosted tool 与 function tool 的区别

| 维度 | function tool | hosted tool |
| --- | --- | --- |
| 谁执行 | 你的进程 | OpenAI（或你提供的 harness） |
| 参数可见性 | 全部经过你的代码，可校验、可审计 | 托管工具你拿不到调用参数，只有结果条目 |
| schema 来源 | 函数签名自动生成，可改 | 由服务端工具定义，SDK 只透传配置 |
| 错误处理 | `failure_error_function` 可定制 | 服务端返回错误，SDK 只能转发 |
| 审批 | `needs_approval`（可拿到参数） | `require_approval` 策略或 `on_approval_request` |
| 返回值 | 任意 Python 值，转成文本/图片/文件 | 固定条目类型，不能自定义 |
| 计费 | 你自己的服务成本 | 计入 OpenAI 账号的平台费用 |
| 适合 | 内部 API、数据库、业务规则 | 联网、检索、沙箱计算、多模态生成 |

一句话决策：**能在你的信任边界内做完、且需要审计/鉴权的，用 function tool；需要 OpenAI 侧资源或你没有的基础设施，用 hosted tool。**

落笔前问自己三个问题，基本不会选错：

1. 这个动作会不会接触我的生产数据或内部权限？会 → function tool（或本地 MCP），因为 hosted tool 你拿不到调用参数。
2. 这个动作需要 OpenAI 侧的算力/联网/沙箱吗？需要 → hosted tool，不要在本地硬造一个劣化版。
3. 失败时我需要"按参数做补救"吗？需要 → function tool，因为 hosted tool 的错误只能整体转发给模型。

## 六、完整例子：研究助手（web search + code interpreter）

这个例子的目标很具体：先搜事实，再用代码算数，最后给出一段带来源的结论。它演示了"两个 hosted tool 在同一次 run 里协作"。

```python
import asyncio

from agents import Agent, CodeInterpreterTool, Runner, WebSearchTool, trace


def build_research_agent() -> Agent:
    return Agent(
        name="Research analyst",
        model="gpt-5.6-sol",
        instructions=(
            "You research a question in two steps. "
            "1) Use web_search to collect recent facts and note the source domains. "
            "2) Use code_interpreter to compute or verify every number, and show the code you ran."
        ),
        tools=[
            WebSearchTool(search_context_size="medium"),
            CodeInterpreterTool(
                tool_config={"type": "code_interpreter", "container": {"type": "auto"}}
            ),
        ],
    )


async def main() -> None:
    agent = build_research_agent()
    with trace("Research assistant"):
        result = await Runner.run(
            agent,
            "Find the GDP of the three largest economies, then compute each one's share of the total.",
        )

    print(result.final_output)
    for item in result.new_items:
        print(item.type, type(getattr(item, "raw_item", None)).__name__)

    # 预期输出（示意）：
    # 助手给出三国 GDP、各自占比，以及一段可复核的 Python 代码
    # tool_call_item ResponseFunctionWebSearch
    # tool_call_item ResponseCodeInterpreterToolCall
    # message_output_item None


if __name__ == "__main__":
    asyncio.run(main())
```

四个关键点：

- **两个工具的顺序由模型决定**，你在 `instructions` 里写"先搜再算"，但不要指望 100% 遵守；需要确定性就拆成两次 `Runner.run`（第 11 章的 routing 模式）。
- **代码是可审计的**：`code_interpreter_call` 条目里有 `code` 字段，把它打进 trace 或日志，比"相信模型算对了"可靠得多。
- **不要在 hosted tool 里做鉴权**：搜索与计算都不该接触你的私有数据；私有数据要么走 FileSearch 的向量库，要么走 function tool。
- **成本随 `search_context_size` 与容器使用时长变化**，生产环境建议先用 `"low"` 跑通，再按需要升高。

## 七、看原始结果：new_items 与 raw_responses

托管工具的"输出"分两层，排查问题时别找错地方：

- `RunResult.new_items`：面向教学与展示的事件流，每项是 `ToolCallItem`（模型发起了调用）、`ToolCallOutputItem`、`MessageOutputItem` 之一。
- `RunResult.raw_responses`：模型返回的原始响应对象列表，托管工具的真正细节在这里，例如 `web_search_call` 的 `results`（含图片 URL 与 caption）。

```python
from agents import Agent, Runner, WebSearchTool


async def main() -> None:
    agent = Agent(
        name="Search auditor",
        instructions="Search the web and answer in one sentence.",
        tools=[WebSearchTool(search_context_size="low")],
    )
    result = await Runner.run(agent, "What changed in Python 3.14?")

    for response in result.raw_responses:
        for output in response.output:
            if getattr(output, "type", None) == "web_search_call":
                print("queries:", getattr(output, "queries", None))
                print("results:", getattr(output, "results", None))
```

判断标准很简单：**要给用户看的，从 `new_items` 取；要审计或调试的，从 `raw_responses` 取。** 这条经验对后面第 22 章的追踪与第 24 章的调试同样适用。

## 八、计费与限制（必须知道的边界）

- 托管工具执行在 OpenAI 侧，费用计入你的 OpenAI 账号；`RunContextWrapper.usage` 只累计**模型 token**，不含托管工具本身的平台费用，对账请看平台用量页。
- `FileSearchTool.max_num_results` 只接受 1–50；`None` 或 0 表示用服务端默认。
- `CodeInterpreterTool` 与 `ComputerTool` 对模型有要求：换模型前先确认它支持对应工具；`ComputerTool` 在模型未指定时会走 SDK 默认模型（当前 `gpt-5.6-luna`），若用 `RunConfig.model` 改写请选支持 computer use 的模型。
- 托管 `ShellTool` 的容器是"每次请求的生命周期"，不要指望跨 run 保留状态，除非用 `container_reference` 显式复用。
- 所有 hosted tool 都只对 `OpenAIResponsesModel` 生效；换成 Chat Completions 或第三方 provider 时，这些工具会被拒绝或忽略。

## 常见坑与排查

1. **`FileSearchTool` 一直搜不到内容**：向量库还是 `in_progress` 就开始跑了。**修法**：建库后用 `create_and_poll` 等索引完成，再发起 run。
2. **`CodeInterpreterTool` 报模型不支持**：模型选错（例如用了只支持文本的型号），或 gpt-5 类模型配了 minimal reasoning。**修法**：按示例改用受支持模型与默认 reasoning effort。
3. **`ComputerTool` 报缺少尺寸/环境**：走的是 `computer-use-preview` 路径，序列化前需要已解析的 `Computer` 实例。**修法**：显式指定支持 GA computer 工具的模型，或确保 harness 提供 `environment` 与 `dimensions`。
4. **托管 `ShellTool` 构造时报 `UserError`**：同时给了 `environment={"type": "container_auto"}` 和 `executor`/`needs_approval`。**修法**：托管模式只留 `environment`。
5. **以为 hosted tool 的结果能拿到参数做审计**：托管工具在你进程外执行，你只能看到结果条目。**修法**：需要审计的动作改用 function tool 或 MCP 本地服务器。
6. **`ToolSearchTool` 加了但延迟工具仍不可见**：命名 `tool_choice` 指向了裸命名空间或延迟工具，或加了多个 `ToolSearchTool`。**修法**：保持恰好一个，`tool_choice` 用 `auto`/`required`。

## 动手练习

1. 用 `WebSearchTool` 写一个"行业新闻摘要"Agent，把 `search_context_size` 分别设成 `low` 和 `high`，对比 `result.new_items` 里 `web_search_call` 的差异。
2. 给研究助手加一个 `FileSearchTool`，把内部文档放进向量库，并在 `instructions` 里规定"外部事实用 web search、内部事实用 file search"，观察模型是否遵守。
3. 打开 `repo/examples/tools/code_interpreter.py`，在它的流式循环里额外统计 `code_interpreter_call` 出现的次数，并打印每次的 `code`，验证"模型确实用代码算而不是口算"。

## 本章小结

- 三类工具：托管（服务端执行）、本地运行时（你执行）、混合（Server 决策 + 容器执行）。
- `WebSearchTool`/`FileSearchTool`/`CodeInterpreterTool`/`ImageGenerationTool`/`HostedMCPTool`/`ToolSearchTool` 的结果都在 run item 的原始条目里，没有回调。
- `ComputerTool`、`ApplyPatchTool` 必须由你实现 harness/editor；`ShellTool` 本地要 executor、托管不能给 executor。
- hosted tool 与 function tool 的核心差别是执行位置与可审计性，不是"高级/低级"。
- 托管工具只支持 Responses 模型，费用在 OpenAI 侧结算，`Usage` 不体现。
- 研究助手的正确姿势：搜索取事实、代码验数字、结论标来源。
- 展示看 `new_items`，审计看 `raw_responses`，两者别混用。
