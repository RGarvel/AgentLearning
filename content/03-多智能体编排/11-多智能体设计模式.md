# 第11章 多智能体设计模式

第 10 章我们把 Agent 变成了工具，也学会了强制模型调用某个工具。零件已经齐了，剩下的问题是**怎么组织**：三个专家、一个管理者，还是一串流水线。

选错的代价很实在：你会得到一套又贵又慢、还查不出问题的系统。

这一章只给一条默认主线：先回答"谁拥有最终答案"，默认走交接这条路；再沿 routing → parallel → evaluator-optimizer → orchestrator-workers 逐级升级，把四个脚本跑通。manager 与其他写法降级为可选微调，放在主线之后。

按这章走完，你会得到五个能整段运行的脚本、一张四维对比表，以及一条能复用的拆分判断轴。

---

## 学习目标

- 能用"谁拥有最终答案"这条轴区分 manager 与交接（handoff），并说出各自的代价。
- 能跑通 routing、parallel、evaluator-optimizer、orchestrator-workers 四种模式的简化脚本，并解释各自的硬上限。
- 能从状态、成本、延迟、失败传播四个维度比较模式，而不是只凭感觉选。
- 能判断什么情况下"单 Agent + 更多工具"才是正解。
- 能对 `repo/examples/agent_patterns/` 里每个文件说出它演示的模式。

## 一、先回答一个问题：谁拥有最终答案

选架构只需要先回答一句话：**最后那句回复，是哪个 Agent 说的？**

所有多智能体架构的分歧，最后都收敛到这一个问题上。

- 如果答案是"一个中心 Agent 汇总所有人的结论，再统一回复"，这是 **manager（agents as tools）**。
- 如果答案是"用户最后直接对话的那个专家"，这是**交接（handoff，去中心化）**。

这个答案会连带决定四件事：上下文怎么流动、成本怎么叠加、失败怎么传播、排障从哪里看起。它比"哪个架构更先进"重要得多。

| 判断轴 | manager | 交接 |
| --- | --- | --- |
| 最终答案归属 | 中心 Agent | 接手专家 |
| 上下文流动 | 由中心 Agent 生成片段给专家 | 整段历史随交接转移 |
| 用户感知 | 始终同一个"人"在说话 | 会切换人格与话术 |
| 并行能力 | 天然支持 | 不支持 |
| 排障入口 | 中心 Agent 的 trace 里能看到每次调用 | 沿 `last_agent` 链回溯 |

> 提示：一条实用经验。专家需要"直接服务用户"时用交接，只需要"提供一段结论"时用 as_tool。前者是人际交接，后者是内部咨询。

本章默认走交接，第 12 章把这条路走到底。manager 只作为第二节末尾的可选微调出现，不是主线。

## 二、manager 与 handoff 的最小实现

默认主线是交接骨架：分诊 Agent 把用户交给专家，专家直接说话，分诊自己退出对话。

### 路径与配置一次对齐

本章所有脚本都放在本机 SDK 根目录 `openai-agents-python/`。正文里的 `repo/xxx` 是课程的逻辑前缀，点击跳 GitHub，不是让你真建一个 `repo` 目录。

| 课程里写的（可点击） | 你本机打开的文件 |
| --- | --- |
| `repo/examples/agent_patterns/routing.py` | `openai-agents-python/examples/agent_patterns/routing.py` |

跑通本章脚本需要下面这些配置。每一项漏了都有明确症状，先配齐再往下走。

| 配置项 | 在哪设 | 漏了会报什么错 |
| --- | --- | --- |
| API Key | `OPENAI_API_KEY` 或 `AsyncOpenAI(api_key=...)` | 鉴权失败；追踪提示 `OPENAI_API_KEY is not set, skipping trace export` |
| base URL | `OPENAI_BASE_URL` 或 `AsyncOpenAI(base_url=...)` | 请求发往 `api.openai.com`，网关场景连接失败或 401 |
| 模型名 | `Agent(model=...)` 或 `OPENAI_DEFAULT_MODEL` | 网关报 `model not found`（沿用了默认 `gpt-5.6-luna`） |
| API 形态 | `set_default_openai_api("chat_completions")` | 网关报 404 或"接口不支持"（默认走 Responses API） |
| `output_type` | `Agent(output_type=...)` | `final_output` 退化成 `str`，读 `.route`/`.score`/`.subtasks` 报 `AttributeError` |
| `handoffs` / `tools` | `Agent(handoffs=...)` / `Agent(tools=[...])` | 交接或工具调用不发生，Agent 直接自己回复 |
| `trace()` | `with trace("...")` | 不报错，但一次工作流散成多条 trace，排障困难 |
| `return_exceptions=True` | `asyncio.gather(..., return_exceptions=True)` | 一个 worker 失败就让整批结果一起丢失 |
| `failure_error_function` | `as_tool(..., failure_error_function=None)` | 失败被吞成脱敏文案，中心 Agent 通常会编一个答案 |

这段验证"默认交接、可选 manager"两种所有权：脚本能整段运行，`main()` 里默认只跑 `triage`。

```python
import asyncio

from agents import Agent, Runner

billing = Agent(name="Billing", instructions="Handle invoices and refunds.")
shipping = Agent(name="Shipping", instructions="Handle tracking and delays.")

# manager：中心 Agent 拥有最终答案
manager = Agent(
    name="Support manager",
    instructions="Call the expert tools you need, then answer the user yourself.",
    tools=[
        billing.as_tool(tool_name="ask_billing", tool_description="Billing questions."),
        shipping.as_tool(tool_name="ask_shipping", tool_description="Shipping questions."),
    ],
)

# handoff：专家接手后直接对用户说话
triage = Agent(
    name="Triage",
    instructions="Route the user to the right specialist, then stop talking.",
    handoffs=[billing, shipping],
)


async def main() -> None:
    # 默认主线：跑交接
    result = await Runner.run(triage, "My invoice has a duplicate charge.")
    print("final agent:", result.last_agent.name)
    print(result.final_output)
    # 可选微调：取消下面两行注释，对比 manager 的行为
    # result = await Runner.run(manager, "My invoice has a duplicate charge.")
    # print("manager:", result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

预期输出先是一行 `final agent: Billing`（或 Shipping），再是接手专家的答复。取消注释后，同一句话由中心 Agent 汇总后自己回答。

把它存成 `manager_and_handoff.py`，放在 SDK 根目录 `openai-agents-python/` 下。运行命令：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python manager_and_handoff.py
```

预期输出：`final agent: <接手的专家名>` 加一段答复文本。这一步证实环境能创建 Agent 并完成一次交接。

两个骨架长度差不多，行为完全不同。`manager` 每次都会"回来汇报"，`triage` 交接后自己退出对话。第 12 章会把交接的参数讲透，这里先记住骨架。

## 三、四种常见模式的简化实现

四种模式是同一组骨架的升级路：从最确定的 routing 起步，遇到新信号再往上加 parallel、evaluator-optimizer、orchestrator-workers，不要一上来全用。

每节先给结论，再给最小实现。默认先跑 routing，其余三段按需升级。

### routing：先分类，再派活

routing 最确定、也最便宜。它用一次结构化输出（structured output）的分类调用，替代"让模型自己决定交接"，这样路由结果可测试、可断言。

这段验证"分类与执行分离"：分类器只输出 `Intent`，派活由代码里的 `ROUTES` 表完成。

```python
import asyncio
from typing import Literal

from pydantic import BaseModel

from agents import Agent, Runner


class Intent(BaseModel):
    route: Literal["billing", "shipping", "account"]
    reason: str


classifier = Agent(
    name="Intent classifier",
    instructions="Classify the customer message into exactly one route.",
    output_type=Intent,
)

billing = Agent(name="Billing", instructions="Resolve billing issues.")
shipping = Agent(name="Shipping", instructions="Resolve shipping issues.")
account = Agent(name="Account", instructions="Resolve account issues.")

ROUTES = {"billing": billing, "shipping": shipping, "account": account}


async def main() -> None:
    message = "My invoice has a duplicate charge."
    intent = (await Runner.run(classifier, message)).final_output
    result = await Runner.run(ROUTES[intent.route], message)
    print(intent.route, result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

预期输出形如 `billing <一段答复文本>`，第一项是路由名。要点有三个：

| 要点 | 说明 |
| --- | --- |
| 路由表是代码而不是 prompt | 改路由只改 `ROUTES`，不用动模型指令 |
| `intent.reason` | 天然是一份审计记录 |
| 分类失败兜底 | 默认进人工队列即可 |

把它存成 `pattern_routing.py`，放在 SDK 根目录 `openai-agents-python/` 下。运行命令：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python pattern_routing.py
```

预期输出：一行 `<route> <答复文本>`。看到路由名就说明分类与派活都通了。

### parallel：并行跑，再合并

互相独立的任务没有理由串行，直接用 `asyncio.gather` 并发。唯一的硬要求是**必须在一个追踪（trace）里**，否则排障时你会看到几段互不相关的记录。

这段同时跑两个翻译 Agent，并用 `trace()` 把它们收进同一次工作流。

```python
import asyncio

from agents import Agent, ItemHelpers, Runner, trace

spanish = Agent(name="Spanish", instructions="Translate the message to Spanish.")
french = Agent(name="French", instructions="Translate the message to French.")


async def main() -> None:
    message = "Good morning!"
    with trace("Parallel translation"):
        es_result, fr_result = await asyncio.gather(
            Runner.run(spanish, message),
            Runner.run(french, message),
        )
    print(ItemHelpers.text_message_outputs(es_result.new_items))
    print(ItemHelpers.text_message_outputs(fr_result.new_items))


if __name__ == "__main__":
    asyncio.run(main())
```

预期输出两段译文，一段西语、一段法语。`ItemHelpers.text_message_outputs` 只取本次新产生的文本消息。

把它存成 `pattern_parallel.py`，放在 SDK 根目录 `openai-agents-python/` 下。运行命令：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python pattern_parallel.py
```

预期输出：两行译文。到追踪面板里能看到它们同属 `Parallel translation` 这一次工作流。

### evaluator-optimizer：生成 → 评审 → 再生成

质量要求高、且"好"可以被明确判定时，用这个循环。关键是**给循环装上硬上限**，否则两个模型会互相客套到天荒地老。

这段最多循环 3 轮：评审给 `pass` 就停，否则把反馈交回 writer 重写。

```python
import asyncio
from typing import Literal

from pydantic import BaseModel

from agents import Agent, Runner


class Review(BaseModel):
    score: Literal["pass", "needs_improvement"]
    feedback: str


writer = Agent(name="Writer", instructions="Write a one-paragraph product blurb.")
reviewer = Agent(
    name="Reviewer",
    instructions="Review the blurb. Return pass only if it states one benefit and one proof point.",
    output_type=Review,
)


async def main() -> None:
    draft = (await Runner.run(writer, "A noise-cancelling headphone for commuters.")).final_output

    for _ in range(3):
        review: Review = (await Runner.run(reviewer, draft)).final_output
        if review.score == "pass":
            break
        draft = (
            await Runner.run(writer, f"Draft:\n{draft}\n\nPlease improve: {review.feedback}")
        ).final_output

    print(draft)


if __name__ == "__main__":
    asyncio.run(main())
```

预期最终 `draft` 是已经过评审的版本。3 轮都没 `pass`，循环也会停，不会无限跑下去。

把它存成 `pattern_evaluator.py`，放在 SDK 根目录 `openai-agents-python/` 下。运行命令：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python pattern_evaluator.py
```

预期输出：一段产品文案。脚本会正常退出，这本身就证明硬上限生效了。

### orchestrator-workers：先规划，再分派，再汇总

任务本身不确定有几块时用这个。分工是三步：规划者输出结构化子任务，代码并发执行，最后由汇总者统一成文。

这段先用 `Plan` 拿到子任务列表，再并发跑 worker，最后交给 synthesizer 合并。

```python
import asyncio

from pydantic import BaseModel

from agents import Agent, Runner


class Plan(BaseModel):
    subtasks: list[str]


planner = Agent(
    name="Planner",
    instructions="Split the research question into 2-4 independent subtasks.",
    output_type=Plan,
)
worker = Agent(name="Worker", instructions="Answer one subtask with two factual sentences.")
synthesizer = Agent(name="Synthesizer", instructions="Merge worker notes into one brief.")


async def main() -> None:
    question = "How do solar and wind compare for a mid-size factory?"
    plan: Plan = (await Runner.run(planner, question)).final_output
    notes = await asyncio.gather(*(Runner.run(worker, task) for task in plan.subtasks))
    merged = "\n\n".join(str(note.final_output) for note in notes)
    result = await Runner.run(synthesizer, f"Question: {question}\n\nNotes:\n{merged}")
    print(result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

预期输出一段合并后的简报，`plan.subtasks` 一般是 2 到 4 条。

把它存成 `pattern_orchestrator.py`，放在 SDK 根目录 `openai-agents-python/` 下。运行命令：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python pattern_orchestrator.py
```

预期输出：一段简报。第七节的降级片段也嵌在这个脚本里，可以用它做失败实验。

## 四、四个维度上的真实差异

同一件事换模式，差异主要落在这四个维度上。

| 维度 | routing | parallel | evaluator-optimizer | orchestrator-workers | manager | handoff |
| --- | --- | --- | --- | --- | --- | --- |
| 状态归属 | 代码持有 | 代码持有 | 代码持有 | 代码持有 | 中心 Agent | 目标 Agent |
| 成本 | 1 次路由 + 1 次专家 | N 份并行 | 2~4 倍轮次 | 规划 + N + 汇总 | 中心 + 每次工具调用 | 交接后一份 |
| 延迟 | 两次串行 | 取决于最慢者 | 随轮次线性增长 | 规划 + 最慢 worker + 汇总 | 串行调用累加 | 一次切换 |
| 失败传播 | 显式（`if`） | `gather` 抛出即整体失败 | 评审失败可重试 | 单 worker 失败可降级 | `failure_error_function` 兜底 | 目标 Agent 的错误留在它的 run 里 |

另外有两个容易忽略的成本点。

- **并行不是免费**：`gather` 里每个 `Runner.run` 都是独立计费的模型调用。N 个 worker 就是 N 份输入 token，而且往往带着重复的指令。
- **manager 有溢价**：中心 Agent 每一轮都要重看一遍自己的对话。专家产出越多，它后面的输入越长。超过三轮工具调用后，成本曲线会明显变陡。

## 五、什么时候干脆单 Agent + 更多工具

多智能体不是默认答案。出现下面任意两条，就该考虑"别拆"：

| 别拆的信号 | 判断依据 |
| --- | --- |
| 工具总数不到十个，且模型能一次看清 | 工具少时，拆分只增加调度成本 |
| 不需要不同的模型/参数 | 例如全用同一个模型、同样的 reasoning effort |
| 没有"话术不同"的需求 | 拆分的主要收益之一就是各自写专属 instructions |
| 拆完还是要靠一段 prompt 描述协作规则 | 那你只是把 prompt 换了个地方放 |
| 排障成本已经高过收益 | 一次多智能体 run 的 trace 里有多个 agent span，定位问题的时间是单 Agent 的数倍 |

反过来，出现这些信号就该拆：单个 prompt 超过两屏还在加、工具描述互相干扰导致选错、需要不同权限等级、需要并行提速。

一个可执行的成长路径有四个阶段，每一步都有可观测的触发条件。

| 阶段 | 做什么 | 触发条件 |
| --- | --- | --- |
| 1 | 先把所有工具挂在一个 Agent 上，跑通并记录失败样本 | 起点，不拆分 |
| 2 | 工具按业务域分组，用 `routing` 拆开 | 失败样本里"选错工具"占比超过三成 |
| 3 | 升级成 `as_tool` | 某个域需要自己的话术或模型 |
| 4 | 用交接 | 用户需要与该域长期对话 |

判断依据来自实测，而不是"听说多智能体更先进"。

> 注意：先写单 Agent，跑通，再记录"它哪里不行"（选错工具？话术不对？成本？），然后**只为这个问题**拆。凭想象拆出来的多智能体系统，通常比单 Agent 更难维护。

## 七、失败传播：三种降级策略

多智能体系统里，"一个环节挂了"是常态，不是异常。三种降级写法值得背下来。

| 策略 | 写法 | 效果 |
| --- | --- | --- |
| 并行降级 | `return_exceptions=True` | 把失败变成结果项，再决定补齐还是丢弃 |
| routing 降级 | 落到未知 route 后进人工队列 | 比让模型"猜一个"安全得多 |
| manager 降级 | `as_tool(..., failure_error_function=None)` | 异常冒出来由代码处理 |

这段验证并行降级：把 `gather` 的异常转成结果项，逐个写进 `notes`。

```python
results = await asyncio.gather(
    *(Runner.run(worker, task) for task in plan.subtasks),
    return_exceptions=True,
)

notes: list[str] = []
for task, outcome in zip(plan.subtasks, results):
    if isinstance(outcome, BaseException):
        notes.append(f"[{task}] failed: {type(outcome).__name__}")
    else:
        notes.append(str(outcome.final_output))
```

这是片段，不是完整脚本：把它嵌到第三节 `pattern_orchestrator.py` 的 `main()` 里，替换那段 `asyncio.gather`。`plan` 与 `worker` 来自该脚本顶部的定义，`Runner`、`asyncio` 来自该脚本的 import。

预期失败的子任务变成一行 `[<task>] failed: <异常类名>`，其余任务照常产出正文。

routing 降级：分类失败或落到未知 route 时，不要硬塞给某个专家。直接进人工队列并记录原因，这比让模型"猜一个"安全得多。

manager 降级：`as_tool(..., failure_error_function=None)` 让异常冒出来，由代码处理。保留默认值则会把失败变成一句脱敏文案交给中心 Agent，它通常会礼貌地编一个答案。这在客服场景里是事故，不是降级。

> 注意：交接也有 `failure_error_function`，语义是"交接调用失败时给调用方一段文本，调用方继续留任"。它不覆盖 `on_handoff` 之后、输入过滤器之前的失败，这些边界在第 12 章会逐条对齐。

## 常见坑与排查

按症状查，每条都给出"症状 → 原因 → 修法"。

1. **多智能体 run 的 trace 散成好几条**
   - 症状：一次工作流在 trace 里变成几段互不相关的记录。
   - 原因：每个 `Runner.run` 各自开了 trace。
   - 修法：用 `with trace("...")` 包住整个工作流，或统一传 `trace_id`/`group_id`。

2. **并行后模型输出顺序错乱**
   - 症状：结果顺序和输入对不上。
   - 原因：`asyncio.gather` 的返回顺序与传入一致，但你把它拼进了共享列表。
   - 修法：用返回值解包，不要用副作用。

3. **evaluator-optimizer 永不收敛**
   - 症状：循环停不下来，两个模型一直在互相改。
   - 原因：评审标准模糊，或没设轮次上限。
   - 修法：给 `output_type` 加枚举结论，循环加 `for _ in range(N)`。

4. **manager 越跑越贵**
   - 症状：轮次越多，中心 Agent 的单次输入越长。
   - 原因：中心 Agent 每轮重读全部历史。
   - 修法：把专家输出压成短摘要（`custom_output_extractor`），或改成 routing 直接派活。

5. **交接后"没人管用户"**
   - 症状：用户把问题发给一个只会做子任务的专家，没人应答。
   - 原因：目标专家的 instructions 里没有"面向用户"的要求。
   - 修法：在专家 instructions 里写清话术要求，或改回 manager。

6. **并行里有一个失败，全部白跑**
   - 症状：一个子任务失败，整批结果一起丢失。
   - 原因：`gather` 默认快速失败。
   - 修法：`return_exceptions=True` 后逐个降级，或用 `asyncio.TaskGroup` 明确语义。

## 本章小结

- 选架构先回答"谁拥有最终答案"：中心 Agent 用 manager，专家直接服务用户用交接；本章默认走交接。
- routing 最确定、parallel 最快、evaluator-optimizer 最提质量、orchestrator-workers 最适合任务边界不清。
- 并行有真实成本（N 份输入 token），manager 有真实溢价（每轮重读历史）。
- 单 Agent + 更多工具常常是正确的起点；拆分的理由要来自实测，不是想象。
- `examples/agent_patterns` 是模式博物馆，先看 `trace()` 的边界再看代码。
- 所有循环都要有硬上限，所有并行都要想清楚失败语义；降级要显式：并行用 `return_exceptions`，routing 落到人工队列，manager 想暴露细节就把 `failure_error_function` 设为 None。
