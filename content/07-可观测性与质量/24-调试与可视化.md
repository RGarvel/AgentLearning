# 第24章 调试与可视化

第 23 章解决“上线前怎么证明它对”，这一章解决“它不对的时候，怎么在十分钟内定位”。调试 Agent 与调试普通程序最大的差别是：错误往往不在栈里，而在数据里。prompt 拼错了、工具描述写得含糊、模型选了另一条路，这些都只在数据里留下痕迹。所以本章给的是一套“从现象缩到一行输入”的方法，而不是一堆零散技巧。

读完你会得到四个能直接跑的脚本、一张可视化入口对照表，以及一条按成本排序的排查顺序。先跑通这四个脚本，再回头看原理。

## 24.1 run_demo_loop：最便宜的验证

核心结论：写 UI 之前，先用 REPL 确认 Agent 的行为，`run_demo_loop()` 就是官方给的最小终端壳。

写 UI 之前，先用 REPL 确认 Agent 的行为。`run_demo_loop()` 就是官方给的最小终端壳，几行代码就能把 prompt 试起来。把下面这段存成 `repl_debug.py`，放在 SDK 根目录 `openai-agents-python/` 下。前提：第 2 章的模型 key 已配好。

```python
import asyncio

from agents import Agent, run_demo_loop


async def main() -> None:
    agent = Agent(
        name="Support triage",
        instructions="先判断问题类型，再决定是否转人工。",
    )
    await run_demo_loop(agent)


if __name__ == "__main__":
    asyncio.run(main())
```

运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python repl_debug.py
```

预期结果是一个等待输入的提示符，输入一句话就能看到完整回答；输入 `exit` 退出。

它的签名是 `run_demo_loop(agent, *, stream=True, context=None, max_turns=10)`。行为上有四个细节值得知道。

| 细节 | 行为 |
| --- | --- |
| 输出方式 | 默认流式输出 |
| 对话历史 | 跨轮保留（内部用 `input_items` 累积） |
| 退出方式 | 输入 `quit` 或 `exit` 结束 |
| 工具审批 | 遇到需要审批的工具时，提示你输入 `y` 或 `yes` |

它解决的是“这段 prompt 到底行不行”的问题，成本最低。三个使用建议如下。

1. 把 `stream` 传 `False` 再跑一遍，比较非流式下行为是否一致。
2. 故意让工具死循环，观察 `MaxTurnsExceeded` 的实际表现与消息。
3. 不要在 REPL 里调真实写操作的工具，改成打印参数。

`context` 参数常被忽略。如果你的 Agent 用 `RunContextWrapper` 依赖注入（第 6 章），REPL 里必须传入同类型的 context，否则工具里第一次访问 `ctx.context.xxx` 就会 `AttributeError`。这不是 REPL 的 bug，而是它不会替你造依赖。

## 24.2 draw_graph：把拓扑画出来

核心结论：多 Agent 系统最难排查的是“谁连到了谁”，`draw_graph()` 把 Agent、工具、MCP server 与交接画成一张有向图。

把下面这段存成 `draw_graph_demo.py`，放在 SDK 根目录 `openai-agents-python/` 下。它不需要模型 key，因为画的是静态配置。

```python
from agents import Agent
from agents.decorators import tool
from agents.extensions.visualization import draw_graph


@tool
def get_order_status(order_id: str) -> str:
    """查询订单状态。"""
    return "已发货"


def main() -> None:
    refund_agent = Agent(name="Refund agent", instructions="处理退款。")
    triage_agent = Agent(
        name="Triage agent",
        instructions="按问题类型分流。",
        tools=[get_order_status],
        handoffs=[refund_agent],
    )
    draw_graph(triage_agent, filename="agent_graph")


if __name__ == "__main__":
    main()
```

先装可选依赖，在 SDK 根目录执行：

```bash
pip install "openai-agents[viz]"
```

再运行：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python draw_graph_demo.py
```

预期结果是当前目录多出一个 `agent_graph.png`，图里能看到分流 Agent 指向退款 Agent 的一条边。

图元素的约定是固定的。

| 元素 | 画法 |
| --- | --- |
| Agent | 黄色方框 |
| 工具 | 绿色椭圆 |
| MCP server | 灰色方框 |
| handoff | 实线箭头 |
| 工具调用 | 点线 |
| MCP 调用 | 虚线 |
| 端点 | `__start__` 与 `__end__` |

三个容易误解的点。

| 误解 | 实际情况 |
| --- | --- |
| 以为它只画一层 | 它会递归展开 `handoffs` 里的 Agent，以及通过 `handoff(agent)` 注册的目标；但自定义 `Handoff` 没有可用的目标 Agent 时，只画一个命名终点，不会展开它背后的资源 |
| 以为节点按名字去重 | 节点身份按对象而非名字：两个同名但不同的工具会画出两个节点，标签相同 |
| 以为它画的是实际路径 | 它画的是静态配置，不是运行时实际走过的路径；想看实际路径请回第 22 章的 trace |

`filename` 传了会落盘（如 `agent_graph.png`），不传则尝试内联显示。`draw_graph(agent).view()` 可以单独开窗口。想拿 DOT 源码自己渲染，用同模块的 `get_main_graph(agent)`。

它最适合两个时刻。设计评审前，用它证明“我确实只挂了三把工具”。排查“模型为什么不交接”时，用它确认目标 Agent 真的在 `handoffs` 里，而不是只写进了 instructions。静态图看不出时序，但能立刻排除一半的“我以为它连上了”。

## 24.3 日志：默认安静，是有意的

核心结论：SDK 定义了两个 logger 且不挂任何 handler，想看到一切要先打开日志级别，再打开载荷开关。

SDK 定义了两个 logger：`openai.agents` 与 `openai.agents.tracing`，并且不挂任何 handler，日志走你应用的 logging 配置。想在本地看到一切，最省事的是调用 `enable_verbose_stdout_logging()`。把下面这段存成 `debug_logging.py`，放在 SDK 根目录 `openai-agents-python/` 下。前提：第 2 章模型 key 已配好。

```python
import asyncio

from agents import Agent, Runner, enable_verbose_stdout_logging


async def main() -> None:
    enable_verbose_stdout_logging()  # 把 openai.agents 设为 DEBUG 并输出到 stdout
    agent = Agent(name="Ops assistant", instructions="汇总工单，简洁作答。")
    result = await Runner.run(agent, "汇总这批工单")
    print(result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

更细的控制就用标准 logging。下面这段只改一个 logger 的级别，不影响全局配置。这是片段，不是完整脚本：把它放进 `debug_logging.py` 的 `main()` 开头，替代 `enable_verbose_stdout_logging()` 那一行的位置；`logging` 为标准库，直接 import。

```python
import logging

logger = logging.getLogger("openai.agents")
logger.setLevel(logging.DEBUG)
logger.addHandler(logging.StreamHandler())
```

但你会立刻发现：即使 DEBUG，也看不到模型输入输出与工具参数。这是两个环境变量在起作用，默认都是 `1`，即不记录。

| 变量 | 默认 | 保护什么 |
| --- | --- | --- |
| `OPENAI_AGENTS_DONT_LOG_MODEL_DATA` | `1` | 模型请求/响应、错误里的模型载荷 |
| `OPENAI_AGENTS_DONT_LOG_TOOL_DATA` | `1` | 工具入参/出参、工具异常详情 |

排查需要时临时设成 `0`。工作目录是 SDK 根目录 `openai-agents-python/`，`debug_repro.py` 就是你放在该目录下的复现脚本；直接把 `debug_logging.py` 当作它即可。

```bash
# 工作目录：openai-agents-python/（SDK 根目录；debug_repro.py 是你自己写的复现脚本，放在这里）
export OPENAI_AGENTS_DONT_LOG_MODEL_DATA=0
export OPENAI_AGENTS_DONT_LOG_TOOL_DATA=0
python debug_repro.py
```

预期结果是同一个脚本跑起来，prompt 原文与工具入参都会出现在日志里。

> 注意：这两个开关不仅影响日志，还影响异常内容。关掉脱敏后，`ModelBehaviorError` 可能带上原始 JSON，工具参数校验失败也会链接底层 `ValidationError`。只在受控的开发环境里开，别带进生产。

## 24.4 Usage 与 raw_responses：钱花在哪

核心结论：`result.context_wrapper.usage` 是一次运行的用量汇总，`raw_responses` 给出每次请求的 ID。

`Usage` 的字段包括 `requests`、`input_tokens`、`output_tokens`、`total_tokens`、`request_usage_entries`。另有 `input_tokens_details`（`cached_tokens`、`cache_write_tokens`）与 `output_tokens_details.reasoning_tokens`。

下面这段把用量按请求拆开打印，同时列出每次请求的 ID。把它存成 `usage_report.py`，放在 SDK 根目录 `openai-agents-python/` 下。前提：第 2 章模型 key 已配好。

```python
import asyncio

from agents import Agent, Runner, Usage


def report(usage: Usage) -> None:
    print(f"requests={usage.requests} in={usage.input_tokens} out={usage.output_tokens}")
    for index, entry in enumerate(usage.request_usage_entries, start=1):
        print(f"  #{index}: {entry.input_tokens} in / {entry.output_tokens} out")


async def main() -> None:
    agent = Agent(name="Ops assistant", instructions="汇总工单，简洁作答。")
    result = await Runner.run(agent, "汇总这批工单")
    report(result.context_wrapper.usage)
    for response in result.raw_responses:
        print(response.response_id, response.request_id)


if __name__ == "__main__":
    asyncio.run(main())
```

运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python usage_report.py
```

预期结果是先打印一行总量，再逐行打印每次请求的输入与输出 token，最后列出响应 ID。

四个判断要点。

| 字段 | 能回答什么 |
| --- | --- |
| `request_usage_entries` | 哪一轮最贵；多轮工具调用里通常最后一轮输入最大 |
| `cached_tokens` | 前缀缓存是否生效；该值高时，实际成本会显著低于表面 token 数 |
| 流式下的 `usage` | 可能滞后到最后几个 chunk 才齐 |
| session 下的 `usage` | 每次 `run()` 只统计本次执行，但历史会被重新计入输入 token，所以第二轮比第一轮贵是正常的 |

要看供应商原始用量，例如区分“字段缺失”与“真的是 0”，设 `ModelSettings(preserve_raw_usage=True)`，然后读 `result.raw_responses[i].raw_usage`。

## 24.5 常见报错速查表

核心结论：这张表按“你看到什么”组织，而不是按异常层次，价值在于缩短第一分钟。每一条都在 0.25.0 的源码或文档里有出处。

| 症状 | 关键字 | 根因 | 修法 |
| --- | --- | --- | --- |
| 一启动就报 key 缺失 | `The api_key client option must be set` | 没有 `OPENAI_API_KEY`，也没有显式 client | 设环境变量，或 `set_default_openai_key("sk-...")`、`set_default_openai_client(...)` |
| 404 / 模型不存在 | `model_not_found`、`does not exist` | 模型名拼错、账号无权限、或走了错误的 provider | 核对模型名与 `MultiProvider` 前缀；或用 `Agent(model=<Model 实例>)` 直连 |
| 跑到一半报轮次上限 | `MaxTurnsExceeded: Max turns (10) exceeded` | 工具循环不收敛，或 `tool_choice=required` 逼模型反复调工具 | 提高 `max_turns`；修工具返回值噪音；用 `tool_use_behavior` 或 `reset_tool_choice` 收敛 |
| 构造 Agent 就报 schema 错 | `Strict JSON schema is enabled, but the output type is not valid` | `output_type` 含 `dict[str, Any]`、非 None 默认值、根级 `anyOf` | 改类型，或 `AgentOutputSchema(T, strict_json_schema=False)` |
| 校验阶段报 JSON 错 | `ModelBehaviorError: Invalid JSON`、`Expected a dict` | 非 strict 模式下模型给了坏 JSON | 先开 strict；再用 `invalid_final_output` 处理器降级 |
| 工具从不被调用，请求阶段报错 | `UserError: Unknown tool type: <class "function">` | 列表里放的是裸函数，忘了 `@tool` | 加 `@tool`（等价 `function_tool(fn)`） |
| 模型说“工具出错了”，你却看不到异常 | `An error occurred while running the tool.` | 默认 `failure_error_function` 把异常换成了固定文案 | 传 `failure_error_function=None` 让异常冒泡，或自定义错误函数并落日志 |
| 非 OpenAI 模型下追踪报 401 | traces ingest 401 | 有模型 key 但没有 OpenAI key，追踪仍要上传 | `set_tracing_disabled(True)`，或 `set_tracing_export_api_key()` 单独配 |
| 偶发超时 | `ModelTimeoutError`、`ToolTimeoutError` | 设了 `ModelSettings(timeout=...)` 或工具 `timeout` 且真的超了 | 调大阈值、加 `retry`、检查工具里的阻塞调用 |

这张表的价值在于缩短第一分钟。真正花时间的往往不是“报什么错”，而是“为什么只有生产环境报”。

还有一类“不报错但不对”的症状，值得单独记：Agent 总是提前收工。常见原因是 instructions 与工具描述互相矛盾，比如描述里写着“仅当用户明确要求时调用”，而 instructions 又从不让用户提。另一种是 `tool_use_behavior="stop_on_first_tool"`，它让第一次工具调用就结束了整轮。这两条都不会抛异常，只能靠 `new_items` 看出来。

## 24.6 最小可复现：四步剥离法

核心结论：线上问题最贵的不是修复，而是“在完整业务里定位”，按四步剥离通常十分钟内能把范围缩到一处。

1. **拿到真实输入**：从 `result.input` 或 `raw_responses[i]` 里把模型实际看到的输入原样复制出来。注意别用你“以为”发了什么，session、handoff filter、`call_model_input_filter` 都可能改过它。
2. **剥到单 Agent、单工具**：去掉 handoff、去掉护栏、去掉 session，只留触发问题的那一个工具。很多问题在这一步就消失了，说明是交互而非单点。
3. **用 `ScriptedModel` 复现编排**：如果问题在“SDK 怎么处理工具结果”，把它变成第 23 章的确定性测试；如果问题在“模型怎么选”，才需要真模型。
4. **把三样东西打出来**：一个最小复现脚本通常只需要下面这几行诊断。

把下面这段存成 `debug_dump.py`，放在 SDK 根目录 `openai-agents-python/` 下。前提：第 2 章模型 key 已配好；`dump()` 保留异步签名，调用处用 `await`。

```python
import asyncio

from agents import Agent, Runner


async def dump(result) -> None:
    print("final:", result.final_output)
    for index, item in enumerate(result.new_items):
        print(index, item.type, getattr(item, "agent", None) and item.agent.name)
    for response in result.raw_responses:
        print("response", response.response_id, "request", response.request_id)
        print("usage", response.usage)


async def main() -> None:
    agent = Agent(name="Ops assistant", instructions="汇总工单，简洁作答。")
    result = await Runner.run(agent, "汇总这批工单")
    await dump(result)


if __name__ == "__main__":
    asyncio.run(main())
```

运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python debug_dump.py
```

预期结果是打印出最终输出、带序号的 item 轨迹，以及每次请求的 ID 与用量。

三样东西各管一段。`new_items` 告诉你“做了什么、用的哪个 Agent”，`raw_responses` 告诉你“模型被调了几次、每次 ID 是什么”，`usage` 告诉你“每次花了多少”。三样凑齐，90% 的“玄学问题”会变成一句可验证的假设。

一个反直觉的建议：不要靠加 `print` 调试。临时 print 会让你在“改代码、重跑、删代码”的循环里耗掉半小时，而同样的信息在 `new_items` 与 trace 里本来就有。

真正值得新增的打印只有一种：模型实际收到的输入。它应该通过 `call_model_input_filter` 输出，而不是散落各处的 print。用 `RunConfig(call_model_input_filter=...)` 可以在调用前打印 `ModelInputData`，这比翻源码猜拼装逻辑可靠得多。

另外把 `RunConfig(tool_name_collision_policy="error")` 打开，可以在开发期把函数工具与 handoff 的同名冲突从“警告”变成“直接失败”。

## 24.7 一个可执行的排查顺序

核心结论：把上面所有工具串成一条线，遇到问题时按序自问，顺序越靠前越便宜。

1. **能复现吗？** 不能就先补日志与 trace ID（22 章），不要盲改。
2. **REPL 里能复现吗？** 能，问题在 prompt、工具描述或模型选择；不能，问题在调用方（并发、session、超时）。
3. **拓扑对吗？** `draw_graph()` 看一眼 handoff 与工具挂载位置是否符合预期。
4. **模型收到什么？** 用 `call_model_input_filter` 打印，或看 `raw_responses`。
5. **SDK 做了什么？** `new_items` 逐条读；需要确定性就搬进 `ScriptedModel` 测试。
6. **钱和时间花在哪？** 看 `usage.request_usage_entries` 与 trace 的 span 时长。

新手常直接从第 5 步开始读源码，那是最贵的一步。

## 常见坑与排查

按症状查，每条都给出“症状 → 原因 → 修法”。

1. **症状**：开了 `enable_verbose_stdout_logging()` 还是看不到 prompt 与工具参数。
   **原因**：`OPENAI_AGENTS_DONT_LOG_MODEL_DATA` 与 `OPENAI_AGENTS_DONT_LOG_TOOL_DATA` 默认是 `1`，载荷级日志被有意屏蔽。
   **修法**：本地临时设 `0`；生产保持默认，靠 trace 与 processors 做脱敏后的观测。

2. **症状**：`draw_graph()` 里少了一个子 Agent，或少了 MCP server。
   **原因**：对象没放进 `handoffs`（自定义 `Handoff` 无可展开目标时只画终点）；或 MCP server 没挂在该 Agent 的 `mcp_servers` 上。
   **修法**：检查 `agent.handoffs` 与 `agent.mcp_servers`；必要时先用 `agent.clone(...)` 构造一个“只含目标”的临时 Agent 画图。

3. **症状**：两条 `new_items` 同名工具调用，但只有一个有输出。
   **原因**：并行工具调用中有一条被审批中断或抛错，`ToolCallOutputItem` 数量不对等；也可能两个工具同名，导致 dispatch 命中同一个。
   **修法**：开发期设 `tool_name_collision_policy="error"`；排查时按 `call_id` 对齐调用与输出。

4. **症状**：生产 `usage` 比预期高很多，但没有报错。
   **原因**：session 每轮都把历史重新作为输入计费；或 `cached_tokens` 为 0，说明前缀被改动、缓存失效。
   **修法**：看 `request_usage_entries` 定位哪一轮变大；稳定前缀，少在开头插时间戳之类的内容。

5. **症状**：报错信息里只有一句“发生了错误”，没有任何上下文。
   **原因**：默认工具错误函数返回固定文案，且模型数据脱敏把细节抹掉了。
   **修法**：开发期用 `failure_error_function=None` 或自定义错误函数；配合 `RunConfig(tool_error_formatter=...)` 只把“允许给模型看”的信息回填。

## 本章小结

- `run_demo_loop(agent, *, stream=True, context=None, max_turns=10)` 是最便宜的手工验证，跨轮保留历史。
- `draw_graph()` 画静态拓扑：Agent 方框、工具椭圆、MCP 灰框；实线 handoff、点线工具、虚线 MCP。
- 两个 logger 默认不挂 handler；`enable_verbose_stdout_logging()` 只打开日志级别，不打开载荷。
- `OPENAI_AGENTS_DONT_LOG_MODEL_DATA` 与 `OPENAI_AGENTS_DONT_LOG_TOOL_DATA` 默认 `1`，设 `0` 才看得到 prompt 与工具参数；这两个开关也会改变异常内容。
- `Usage` 的 `request_usage_entries` 用来定位“哪一轮变贵”，`cached_tokens` 解释成本差异。
- 报错速查的原则：先看异常类，再看是谁抛的（构造期、请求期、运行期），最后才怀疑模型。最小可复现四步是真实输入、剥到单点、`ScriptedModel` 复现、打印 `new_items`、`raw_responses` 与 `usage`。
