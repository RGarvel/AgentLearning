# 第16章 人类在环与中断恢复

上一章结尾我们让 Agent 在危险工具前停下来等人点头。但"停下来"只是开始。

进程可能重启，Web 请求早已返回，审批的人在两小时后才点按钮。

这一章要解决的是跨越时间与进程的难题：如何把一次跑到一半的 Agent 运行**完整地冻结、搬运、解冻**。而且解冻之后，既不会漏执行，也不会重复执行。这就是人类在环（HITL，human-in-the-loop）要补齐的最后一块。

按这一章走完，你会得到一个能完整跑通的脚本：它触发一次审批中断、把状态序列化成字符串、再从字符串续跑，屏幕上能看到"暂停时是 `None`、恢复后是字符串"。你还会拿到一张"漏配就报错"的配置对照表和一套 Web 审批的服务端设计。

## 学习目标

- 能说清 `interruptions` 的本质，以及为什么暂停时 `final_output` 是 `None`
- 能熟练使用 `result.to_state()` / `to_json()` / `to_string()` / `RunState.from_json()` / `RunState.from_string()` 完成跨进程恢复
- 能区分 `RunState`（暂停的执行）与 `Session`（对话历史）各自负责什么
- 能设计一个服务端持有快照、前端只拿不透明 ID 的 Web 审批接口
- 能识别"审批通过 ≠ 恰好执行一次"，并为有副作用的工具设计幂等与对账

## 中断不是失败，是"暂停"

中断（interruption）不是失败，只是暂停。理解这一点，才不会把 `final_output` 为 `None` 当成 bug。

运行器在两种情况下会停下来：模型给出了最终输出，或者有工具调用需要人工决策。后者就是我们说的中断。

暂停时，`result.final_output` 是 `None`。这不是 bug，而是语义正确：这一轮对话还没产出面向用户的答案。

真正的产出是 `result.interruptions`，一个 `ToolApprovalItem` 列表。每一项描述"哪个 Agent、要调哪个工具、参数是什么、call_id 是什么"。

中断之所以能"暂停"，是因为 `ToolCallItem`（模型的工具调用）已经记录下来了，但 `ToolCallOutputItem`（执行结果）还没有。恢复时要做的，就是补上这条输出，然后让运行循环继续。

### 跑通本章要配齐什么（漏一项就报错）

下面的配置一个都不能少。先看对照表，再照着主线做。

| 配置项 | 在哪设 | 漏了会报什么错 |
| --- | --- | --- |
| Python 3.10+ 与 agents 0.25.0 | 第2章的 `uv venv` + `uv pip install -e .` | 3.9 下 import 就报语法错；版本不符则参数签名对不上 |
| key / base URL / 模型名 / API 形态 | 第2章的环境变量或 `AsyncOpenAI` client | 模型调用时报鉴权失败或 `model not found`，中断永远不触发 |
| `from agents.decorators import tool` 与 `@tool(needs_approval=True)` | 脚本顶部 import 与工具定义 | 不声明审批就没有中断，`final_output` 直接有值，恢复演示无从开始 |
| `result.interruptions` 判空 | `Runner.run` 之后 | 不判空就在无中断时误把 `None` 当待办处理，或漏掉真正的暂停 |
| `result.to_state()` | 拿到 `result` 且 `interruptions` 非空时调用 | 运行已异常结束时调用会报 `UserError: Cannot serialize RunState` 或 `No current agent` |
| `state.to_string()` / `to_json()` | 固化之后 | 不序列化就无法跨进程搬运，恢复链路断在落盘这一步 |
| `await RunState.from_string(agent, payload)` | 新进程里重建 | 忘了 `await` 会拿到协程对象，随后各种 `AttributeError`；`agent` 传错会找不到 Agent |
| `state.approve(item)` / `state.reject(item, ...)` | 恢复之前 | 不决策就反复暂停，永远拿不到最终输出 |
| `Runner.run(agent, state)` | 恢复调用 | 传原始字符串会从零重跑，审批决策与已生成 items 全部丢失 |
| schema 版本一致（1.22） | SDK 版本对齐快照 | 老 SDK 读新快照 fail-fast 直接拒绝，不"尽力解析" |
| Agent 图可复现（名字唯一且稳定） | Agent 定义 | 同名不同实例或改名的快照会被拒绝恢复 |
| 恢复时延续同一 session | 带会话的运行 | 传不同 `session_id` 会让 Agent 看起来"失忆" |
| 幂等键 + 权威对账 | 有副作用的工具与下游 | 崩溃后从旧快照恢复会重复执行，退款退两次 |
| Web 快照服务端独占 + 原子消费 | Web 审批接口 | 快照交给客户端会被改参数；不做 CAS 会重复审批 |

一条贯穿全章的规则：`RunState.from_json` / `from_string` 都是 `async` 静态方法，必须 `await`。忘记 `await` 是新手最常踩的坑，报错通常是各种 `AttributeError`。

## 五步恢复流程

所有 HITL 场景，无论多复杂，都是这五步的变体。

1. `state = result.to_state()`：把当前 `RunResult` 固化成可序列化的 `RunState`；
2. `payload = state.to_json()`（或 `state.to_string()`）：变成 JSON，可以进数据库、进队列、进对象存储；
3. 把 `payload` 存起来，把"待决策事项"展示给人；
4. `state = await RunState.from_json(agent, payload)`：在新进程里重建，然后 `state.approve(item)` / `state.reject(item)`；
5. `result = await Runner.run(agent, state)`：用 `state` 作为 `input` 恢复运行（`run_streamed` 同理）。

注意第 5 步：恢复时传的是 `state`，不是原始字符串输入。这是 `Runner.run` 支持 `input: str | list | RunState` 的原因。

下面这段是本章主线，把暂停、序列化成字符串、重建、决策、恢复串成一个**能直接运行的完整脚本**，验证 `to_string()` 与 `RunState.from_string()` 的跨进程往返。

```python
import asyncio

from agents import Agent, Runner, RunState
from agents.decorators import tool


@tool(needs_approval=True)
async def publish_article(article_id: str) -> str:
    """把草稿发布到官网。"""
    return f"article {article_id} published"


agent = Agent(name="内容助手", instructions="处理内容发布请求。", tools=[publish_article])


async def main():
    # 1) 触发中断：这一步会暂停，不会真正执行工具
    result = await Runner.run(agent, "把 A-1024 这篇稿子发出去")
    print("暂停时 final_output:", result.final_output)
    for item in result.interruptions:
        print("待审批:", item.agent.name, item.name, item.arguments, item.call_id)

    # 2) 固化 + 序列化成字符串，可写数据库/队列；这里只在内存里走一遍
    state = result.to_state()
    payload = state.to_string()

    # 3) 模拟"另一个进程"：从字符串重建（真实系统里 payload 来自存储）
    restored = await RunState.from_string(agent, payload)

    # 4) 逐项决策
    for pending in restored.get_interruptions():
        if pending.name == "publish_article":
            restored.approve(pending)
        else:
            restored.reject(pending, rejection_message="未通过合规审核。")

    # 5) 恢复：传 state，不是原始输入
    resumed = await Runner.run(agent, restored)
    print("恢复后 final_output:", resumed.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

把这个脚本存成 `hitl_resume_demo.py`，放在 SDK 根目录 `openai-agents-python/` 下。按第2章配好 key 与模型名后运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python hitl_resume_demo.py
```

预期输出是这样三行（call_id 每次不同）：

```text
暂停时 final_output: None
待审批: 内容助手 publish_article {"article_id":"A-1024"} call_abc123
恢复后 final_output: article A-1024 published
```

看到这三行，说明"触发中断 → 序列化 → 反序列化 → 审批 → 续跑"整条链已经通了，这就是本章的总验收点。

下面这段把暂停、落盘、恢复串成一个函数，验证 `to_json()` / `from_json()` 的落盘版本。它是片段，不是完整脚本：把这段嵌进你自己的入口脚本，`Agent`、`Runner`、`RunState`、`json`、`Path` 的 import 已在片段内，`STATE_DIR` 指向你指定的目录。

```python
import json
from pathlib import Path

from agents import Agent, Runner, RunState

STATE_DIR = Path(".cache/hitl")


async def pause_and_resume(agent: Agent, user_input: str):
    result = await Runner.run(agent, user_input)
    if not result.interruptions:
        return result.final_output

    # 1-3：固化 + 落盘（key 用你自己的业务单号，这里用 call_id 示意）
    state = result.to_state()
    STATE_DIR.mkdir(parents=True, exist_ok=True)
    run_key = result.interruptions[0].call_id or "run"
    (STATE_DIR / f"{run_key}.json").write_text(json.dumps(state.to_json()))

    # 4：可能在另一个进程里执行
    payload = json.loads((STATE_DIR / f"{run_key}.json").read_text())
    restored = await RunState.from_json(agent, payload)

    # 5：逐项决策后恢复
    for pending in restored.get_interruptions():
        if pending.name == "publish_article":
            restored.approve(pending)
        else:
            restored.reject(pending, rejection_message="未通过合规审核。")
    return await Runner.run(agent, restored)
```

预期结果是：无中断时直接返回 `final_output`，有中断时落盘、重建、决策、恢复。它和主线脚本的差别只在"字符串往返"与"写文件再读文件"，五步完全一样。

两个开发期常犯的错：

- **把同一个 `payload` 用两次**。恢复一次之后，这个快照就"用过了"。要再批一次，必须从最新的 `result` 重新 `to_state()`。
- **`from_json` 是异步的**。`RunState.from_json` / `from_string` 都是 `async` 静态方法，忘了 `await` 会拿到协程对象，随后各种 `AttributeError`。

## RunState 里到底装了什么

`RunState` 装的是继续跑下去所需的全部状态。理解它能装什么，才能判断"什么情况下恢复会失败"。

序列化快照包含：

| 内容 | 用途 |
| --- | --- |
| 当前 Agent / 起始 Agent 的身份 | 恢复时定位到同一个 Agent 节点 |
| 原始输入与已生成的 items | 重建模型上下文 |
| 待审批项与审批决策（含粘性决策） | 续上审批状态 |
| 待执行的工具调用及其参数 | 批准后真正执行 |
| `usage` 累计用量 | 成本核算跨进程延续 |
| `pending_input`（`add_input` 暂存的新输入） | 暂停期间用户补充的话 |
| 嵌套 `Agent.as_tool()` 的恢复数据 | 嵌套运行也能续上 |
| 追踪元数据、服务端会话设置 | 恢复后继续导出 trace、续上 conversation |

特别值得记住的是 `RunState.add_input()`。如果用户在你等审批的时候又补了一句"另外把摘要也发我"，可以先把这句话暂存进 state。

用法是 `state.add_input("...")`。它会被序列化，并在恢复后的下一次模型调用前作为新输入进入流程。它还能通过 `state.pending_input` 读取（返回副本），用 `state.clear_pending_input()` 丢弃。

但它有明确的适用边界。终态、没有剩余模型轮次、模型响应尚未处理完毕、或"待执行的工具结果可能直接结束本轮"的暂停态，都会拒绝 `add_input`。

另一个必须知道的约束是**版本**。`RunState` 有自己的 schema 版本（源码里 `CURRENT_SCHEMA_VERSION = "1.22"`），并且**前向兼容是 fail-fast 的**。老 SDK 读到新版本会直接拒绝，不会"尽力解析"。这意味着升级 SDK 时，积压的待审批快照要么先消化完，要么准备迁移脚本。

还有一条隐形约束：**Agent 图必须可复现**。恢复时按名字/身份定位 Agent，所以同一个运行里不要有"同名但不同实例"的 Agent。

源码会直接拒绝那些"无法仅凭 hook 状态区分同名 Agent"的快照，并提示你先用唯一名字再启动可持久化的运行。改名字也修不好已经生成的歧义快照。

## RunState 与 Session 的分工

**RunState 管"这一次运行走到哪了"，Session 管"这段对话说过什么"。** 这两个概念特别容易混，用一句话就能分开。

| 维度 | `RunState` | `Session` |
| --- | --- | --- |
| 生命周期 | 一次运行的暂停→恢复，用完即弃 | 跨多轮对话，长期存在 |
| 内容 | 待审批项、待执行调用、用量、暂停点 | 对话历史 items |
| 存储 | 你的数据库/队列，序列化成 JSON | SQLite / Redis / SQLAlchemy / OpenAI 服务端 |
| 恢复方式 | `Runner.run(agent, state)` | 每次 `Runner.run(..., session=session)` |
| 能否互替 | 不能 | 不能 |

两者要**配合**使用。带 session 的运行暂停后，恢复时要么传同一个 session 实例，要么传"同一 `session_id` + 同一后端"的另一个实例。否则恢复的这一轮会被追加到另一段历史里，用户会看到"Agent 忘了刚才说过什么"。

> 注意：同一轮里不能既用 session，又用 `conversation_id` / `previous_response_id` / `auto_previous_response_id`。前者是客户端托管历史，后者是服务端托管历史，混用会重复上下文。

## 跨进程/跨机器的持久化设计

把快照从内存搬到生产环境，要回答四个问题。

| 问题 | 做法 |
| --- | --- |
| **存哪里** | 任何能存 JSON 的地方都行，如 PostgreSQL 的 `jsonb` 列、Redis（配合 TTL）、S3、消息队列的延迟消息。关键不是介质，而是"服务端独占"。 |
| **用什么 key** | `run_id`（你自己的业务单号）+ `call_id`（SDK 的调用 ID）。不要只用 `call_id`，它不保证跨运行唯一；也不要只用 `user_id`，一个用户可能同时有多条待审批。 |
| **怎么防重放** | 消费快照必须是**原子**的。典型做法是先 `UPDATE ... SET status='consumed' WHERE id=? AND status='pending'`，影响行数为 1 才继续执行，0 就直接返回"该审批已被处理"。并发点击、网络重试、用户刷新页面，都靠这一条兜住。 |
| **怎么防版本漂移** | 在快照旁边存一个"代码版本 / Agent 定义版本 / SDK 版本"标记，反序列化时路由到匹配的代码路径。审批可能压几天，期间模型、提示词、工具定义都可能变，没有版本标记，你会在最不该出错的时候遇到奇怪的恢复失败。 |

## Web 场景：前端确认按钮怎么落地

正确架构只有一句话：**快照永远在服务端，前端只拿不透明 ID 和可展示字段**。这是本章最实用的部分。

错误做法也是事故高发区：把 `state.to_json()` 整个塞进前端隐藏字段，用户点"批准"时再提交回来。

`RunState.from_json()` **不校验快照的来源与完整性**，客户端提交什么，它就恢复什么。攻击者可以改工具名、改参数、改审批记录，等于把执行权交给了浏览器。

正确流程分四步：

1. **认证**：用你已有的会话/中间件确认"是谁在点"。审阅者身份绝不从请求体里读。
2. **授权**：确认这个人有权处理这条运行、这个工具调用。拿到 `run_id` 不等于有权。
3. **校验**：决策的 ID 与布尔值必须对照服务端持有的待办项，用 `state.get_interruptions()` 取当前待办，**不接受客户端传来的工具调用、参数或审批记录**。
4. **原子消费 + 恢复**：按上面的 CAS 方式把待办标记为已处理，再 `approve`/`reject` 并 `Runner.run(agent, state)`。

下面这段把审批拆成 `start` 与 `decide` 两个接口，验证服务端独占快照的写法。它是片段，不是完整脚本：把它嵌进你的 Web 框架处理函数，`Agent`、`store`、`run_id` 由外层提供，`json`、`dataclass`、`Agent`、`Runner`、`RunState` 的 import 已在片段内。

```python
import json
from dataclasses import dataclass

from agents import Agent, Runner, RunState


@dataclass
class PendingRun:
    run_id: str
    snapshot: str          # 服务端独占的 RunState JSON
    consumed: bool = False


class RunStore:
    """示意：真实实现换成带条件更新的数据库。"""

    def __init__(self) -> None:
        self._rows: dict[str, PendingRun] = {}

    def save(self, row: PendingRun) -> None:
        self._rows[row.run_id] = row

    def consume(self, run_id: str) -> PendingRun | None:
        row = self._rows.get(run_id)
        if row is None or row.consumed:
            return None
        row.consumed = True   # 真实系统用 UPDATE ... WHERE consumed = false
        return row


async def start(agent: Agent, store: RunStore, run_id: str, user_input: str) -> dict:
    result = await Runner.run(agent, user_input)
    if not result.interruptions:
        return {"done": True, "output": result.final_output}

    store.save(PendingRun(run_id=run_id, snapshot=json.dumps(result.to_state().to_json())))
    # 只把可展示字段 + 不透明 ID 发给前端
    return {
        "done": False,
        "pending": [
            {"id": f"{run_id}:{item.call_id}", "tool": item.name, "arguments": item.arguments}
            for item in result.interruptions
        ],
    }


async def decide(agent: Agent, store: RunStore, run_id: str, decision_id: str, approve: bool) -> dict:
    row = store.consume(run_id)
    if row is None:
        return {"error": "该审批已被处理或不存在"}

    state = await RunState.from_json(agent, json.loads(row.snapshot))
    target = next((i for i in state.get_interruptions() if f"{run_id}:{i.call_id}" == decision_id), None)
    if target is None:
        return {"error": "决策项与服务端待办不一致"}

    if approve:
        state.approve(target)
    else:
        state.reject(target, rejection_message="审阅者拒绝该操作。")
    result = await Runner.run(agent, state)
    return {"done": not result.interruptions, "output": result.final_output}
```

预期结果是：`start` 只回传不透明 ID 与可展示字段，`decide` 在服务端对照待办、消费快照、恢复运行。

前端侧要点：工具名和参数属于**不可信展示内容**，渲染进 HTML 时必须转义，参数里完全可能藏 `<script>`。也不要把 `output_info`、上下文、密钥回传前端。

官方还专门提醒：`context_override`、`strict_context`、或者"只删掉审批记录"都不足以让不可信快照变安全。其它字段依然控制着恢复后的执行。

## 失败与幂等：审批不等于恰好一次

审批不等于恰好一次执行，这是 HITL 最容易被忽略、后果最严重的一点。

审批只授权了一次工具调用，它**不保证**这次调用只发生一次。设想：审批通过、工具真的发出了退款请求、进程在把结果写回会话之前崩溃。你从旧快照恢复，工具会**再执行一次**。钱退了两次。

正确的处理有三层：

| 层级 | 做法 |
| --- | --- |
| **给每个逻辑动作分配稳定的幂等（idempotency）键** | 比如 `refund:{order_id}:{refund_request_id}`，传给真正执行副作用的下游，由下游原子去重，并遵守对方的键保留期与重试规则。 |
| **失败后先对账，再决定是否重试** | "查不到记录"不等于"没发生过"。读可能滞后，之前的请求可能还在路上。只有在权威对账确认"没执行过、也不会再执行"之后才重试。 |
| **无法确定就记为 unknown** | 人工介入，不要自动重放。 |

SDK 自身也处理了一类恢复。恢复后的运行若在"把已完成的工具调用写回 Session"这一步失败，你可以保留同一个 `RunState`（或序列化后重建）重试。SDK 会先与 Session 历史对账：历史尾部完全吻合就不再重复追加，不吻合就重试追加。

全程不会重跑已完成的工具、护栏、hook 和交接。但这条恢复路径要求"原始 Session 后端 + 同一 session_id + 独占访问"，历史被别的写入者改过就会 fail-closed 抛 `UserError`。

还有一条硬边界：如果运行**已经接受了最终输出**（跑完输出护栏、跑完终止 hook），只是随后写 Session 失败，那么该 `RunState` 会被标记为不可恢复。之后任何 `Runner.run` 都会在接触模型之前抛 `UserError`。这时唯一正确的动作是开新一轮，而不是重试旧状态，否则终止副作用会重复。

## 常见坑与排查

按症状查，每条都给出"症状 / 原因 / 修法"。

1. **症状：恢复后报 `UserError: Cannot serialize RunState` 或 `No current agent`。** 原因：`to_state()` 之前运行已经异常结束，或 Agent 未被正确绑定。修法：只在拿到 `result` 且 `interruptions` 非空时调用 `to_state()`。

2. **症状：`RunState.from_json` 报 schema 版本不兼容。** 原因：快照由更新版本的 SDK 写出，前向兼容 fail-fast。修法：对齐 SDK 版本；升级前清理积压快照或写迁移。

3. **症状：恢复后提示找不到 Agent / 找错 Agent。** 原因：Agent 图变了（改名、增删、同名不同实例）。修法：让 Agent 名字在运行图内唯一且稳定；给快照存版本标记。

4. **症状：审批完成后，Agent 好像"失忆"了。** 原因：恢复时没传 session，或传了不同 `session_id` 的 session。修法：恢复时传同一 session 实例或同 ID 同后端的实例。

5. **症状：同一个审批被点了两次，工具执行了两次。** 原因：没有原子消费快照。修法：条件更新 `consumed` 状态 + 幂等键 + 下游去重。

6. **症状：前端提交回来的快照能改参数。** 原因：把整份快照交给了客户端。修法：快照留在服务端，前端只拿不透明 ID；决策对照 `state.get_interruptions()` 校验。

## 本章小结

- 中断是暂停：`final_output` 为 `None`，产出在 `result.interruptions`（`ToolApprovalItem` 列表）；`ToolCallItem` 已记录，`ToolCallOutputItem` 还没产生。
- 恢复五步：`to_state()` → `to_json()`/`to_string()` → 存储/搬运 → `await RunState.from_json()`/`from_string()` → `approve`/`reject` 后 `Runner.run(agent, state)`；传 `state` 而非原始输入。
- `RunState` 管暂停的执行，`Session` 管对话历史；恢复时要延续同一个 session，且不能与服务端托管历史混用。
- 快照有 schema 版本（1.22），前向兼容 fail-fast；Agent 图必须可复现，同名 Agent 会被拒绝。
- Web 审批：快照服务端独占，前端只拿不透明 ID；认证、授权、对照服务端待办校验、原子消费，四步缺一不可。
- 审批不等于恰好一次执行，用稳定幂等键 + 权威对账 + unknown 兜底；已接受最终输出后写 Session 失败的 `RunState` 不可恢复，必须开新一轮。
