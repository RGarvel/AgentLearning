# 第15章 工具护栏与工具审批

上一章我们给 Agent 装上了"首尾两道闸门"：输入护栏守入口，输出护栏守出口。但只要链条中间有交接、有工具调用，这道闸门就漏了。

一个越权的删除操作，可能发生在第二跳 Agent 的第三次工具调用里。它既不是"起始输入"，也不是"最终输出"，两道闸门都看不见。

这一章我们把护栏下沉到工具粒度，同时把"要不要让机器自己动手"这个决定，交还给人。

读完你会知道：工具护栏（tool guardrail）怎么挂、审批中断怎么恢复、以及哪些工具根本挂不上护栏。

按这一章走完，你会得到一个能跑的最小审批闭环：软删除自动放行、硬删除先中断再决策、拒绝时给风控话术、输出里的邮箱被屏蔽。

路径约定和上一章一致。课程正文里的 `repo/src/agents/tool_guardrails.py` 是逻辑前缀，点击跳到 GitHub 上的 v0.25.0；本机上它对应 `openai-agents-python/src/agents/tool_guardrails.py`。

## 学习目标

- 能写出 `@tool_input_guardrail` / `@tool_output_guardrail`，并说清它们拿到的 `data` 对象里有什么
- 能区分 `allow` / `reject_content` / `raise_exception` 三种行为在模型、运行器、调用方三个层面的后果
- 能用 `needs_approval`（布尔或异步函数）让危险工具在真正执行前停下来等人
- 能走通 `interruptions → to_state() → approve/reject → Runner.run(agent, state)` 的完整恢复链路
- 能配置 `pre_approval_tool_input_guardrails`、MCP 的 `require_approval`，并说明各自边界

## 为什么 Agent 级护栏管不到工具

工具护栏只覆盖 `FunctionTool` 的执行管线，这就是它和 Agent 级护栏的根本边界。

回顾上一章的结论：输入护栏只在第一轮跑，输出护栏只在最终输出时跑。工具调用恰好发生在两者之间，而且可能发生很多次。所以"每次工具执行前后都检查"这件事，必须由工具自己声明。

源码把这条边界写得很直白。它适用于两类场景：

- 用 `@tool` / `@function_tool` 创建的函数工具；
- 本地 MCP 服务端通过 `tool_input_guardrails` / `tool_output_guardrails` 下发给它所有工具的护栏。

它**不适用**于：交接（handoff）本身、托管工具（`WebSearchTool`、`FileSearchTool`、`HostedMCPTool`、`CodeInterpreterTool`、`ImageGenerationTool`）、内置执行工具（`ComputerTool`、`ShellTool`、`ApplyPatchTool`、`LocalShellTool`）。

另外 `Agent.as_tool()` 目前不直接暴露工具护栏参数。它的 `needs_approval` 走的是另一条审批链路。

> 注意：托管工具在服务端执行，客户端护栏在物理上就拦不住。要控制它们，得用它们的 `tool_config`（比如托管 MCP 的 `require_approval`）或干脆不暴露该工具。

### 跑通本章要配齐什么（漏一项就报错）

下面的配置一个都不能少。先看对照表，再照着主线做。

| 配置项 | 在哪设 | 漏了会报什么错 |
| --- | --- | --- |
| Python 3.10+ 与 agents 0.25.0 | 第2章的 `uv venv` + `uv pip install -e .` | 3.9 下 import 就报语法错；版本不符则参数签名对不上 |
| key / base URL / 模型名 / API 形态 | 第2章的环境变量或 `AsyncOpenAI` client | 模型决定调用工具时报鉴权失败或 `model not found`，中断永远不触发 |
| `from agents.decorators import tool, tool_input_guardrail, tool_output_guardrail` | 脚本顶部 import | 写成别的模块名会 `ImportError`；护栏装饰器写错名同样 `ImportError` |
| `@tool(tool_input_guardrails=[...], tool_output_guardrails=[...])` | 工具定义处 | 不挂就等于没护栏，护栏函数里的 `print` 一点输出都没有 |
| `ToolGuardrailFunctionOutput.allow() / .reject_content() / .raise_exception()` | 护栏函数 `return` | 返回其它形状 → 行为不生效，或判定异常 |
| `json.loads(data.context.tool_arguments or "{}")` | 输入护栏内 | 把原始 JSON 字符串当 dict 用会 `TypeError`，拿不到入参 |
| `needs_approval=...` 且危险参数必填 | `@tool(...)` | 参数带默认值会触发 fail-closed，条件回调退化成"每次都审批" |
| `result.interruptions` 与 `result.to_state()` | `Runner.run` 之后 | 不处理中断就一直停在暂停态，拿不到最终输出 |
| `state.approve(item)` / `state.reject(item, ...)` | 恢复前 | 不决策就反复暂停；决策要对照服务端待办项 |
| `Runner.run(agent, state)` | 恢复调用 | 传原始字符串会从零重跑，审批决策全部丢失 |
| `RunConfig(tool_error_formatter=...)` | `RunConfig` 构造 | 拒绝文案用默认，前端拿不到定制提示 |
| `ToolExecutionConfig(pre_approval_tool_input_guardrails=True)` | `RunConfig` 构造 | 默认是"先审批后护栏"，非法参数会打扰审批人 |
| MCP `require_approval` / 托管 MCP 的 `tool_config` | MCP 服务端或工具配置 | 本地 MCP 不声明就没有审批；托管 MCP 不走本地 `RunState` |

## 两个装饰器，一个 data 参数

工具护栏函数只接收一个参数，而且是数据对象，不是散开的三个参数。这是它和 Agent 级护栏最大的不同。

下面这段在工具入参里查密钥前缀，验证工具输入护栏的写法。它是片段，不是完整脚本：把它嵌到主线脚本的工具定义区，`ToolGuardrailFunctionOutput` 和装饰器的 import 在脚本顶部已备好。

```python
from agents import ToolGuardrailFunctionOutput
from agents.decorators import tool, tool_input_guardrail, tool_output_guardrail


@tool_input_guardrail(name="block_secrets")
def block_secrets(data) -> ToolGuardrailFunctionOutput:
    # data.context 是 ToolContext：tool_name / tool_call_id / tool_arguments（原始 JSON 字符串）
    if "sk-" in (data.context.tool_arguments or ""):
        return ToolGuardrailFunctionOutput.reject_content("请先移除密钥再调用该工具。")
    return ToolGuardrailFunctionOutput.allow()
```

预期结果是：参数里出现 `sk-` 就返回拒绝文案，工具不执行；否则放行。两个 data 对象的区别只有一处：

- 输入护栏拿 `ToolInputGuardrailData(context: ToolContext, agent)`；
- 输出护栏拿 `ToolOutputGuardrailData(context, agent, output)`，多一个 `output` 字段，即工具函数的真实返回值。

`ToolContext` 继承自 `RunContextWrapper`，所以 `data.context.context` 仍是你的业务上下文。而 `data.context.tool_arguments` 是**未经解析的 JSON 字符串**，需要自己 `json.loads`。

这一点和 `needs_approval` 的回调不同，后者直接拿到解析好的参数字典。

### 执行位置：一张顺序表

审批先于护栏，这是工具执行的默认顺序，也是最容易记反的一处。

工具从"模型说要调"到"结果回给模型"，中间的顺序是固定的：

| 步骤 | 发生什么 | 相关配置 |
| --- | --- | --- |
| 1 | 查审批决策，必要时计算 `needs_approval` | `needs_approval` |
| 2 | 若已开启，先跑输入护栏再决定是否发中断 | `ToolExecutionConfig(pre_approval_tool_input_guardrails=True)` |
| 3 | 没有审批决策 → 产出 `ToolApprovalItem`，run 暂停 | `result.interruptions` |
| 4 | 被拒绝 → 用拒绝文案作为工具输出 | `tool_error_formatter` / `rejection_message` |
| 5 | 通过 → 跑输入护栏 | `tool_input_guardrails` |
| 6 | 执行工具函数本体 | — |
| 7 | 跑输出护栏，可能替换输出 | `tool_output_guardrails` |
| 8 | 生成 `ToolCallOutputItem`，回传模型 | — |

第 5 步在第 3 步之后，这个默认顺序很关键：**审批先于护栏**。含义是"人已经点了通过，护栏仍可能拦下"。

如果你希望护栏先过滤掉明显非法的参数、免得人看到一堆垃圾审批请求，就打开 `pre_approval_tool_input_guardrails`。护栏会在第 2 步先跑一遍，通过审批后在第 5 步**再跑一遍**，防止审批期间参数被改写。

## ToolGuardrailFunctionOutput：三种行为，没有第四种

`ToolGuardrailFunctionOutput` 只有三种行为，没有第四种。它有两个字段：`output_info`（任意证据）和 `behavior`（行为）。`behavior` 是一个 TypedDict，三种形态如下：

| 构造方式 | `behavior["type"]` | 工具函数是否执行 | 模型看到什么 | 运行器 |
| --- | --- | --- | --- | --- |
| `ToolGuardrailFunctionOutput.allow(output_info=None)` | `allow` | 执行（输出护栏场景已执行完） | 真实结果 | 继续 |
| `.reject_content(message, output_info=None)` | `reject_content` | 输入侧：**不执行**；输出侧：已执行但结果被丢弃 | 你给的 `message` | 继续下一轮 |
| `.raise_exception(output_info=None)` | `raise_exception` | 输入侧不执行 | — | 抛 `ToolInputGuardrailTripwireTriggered` / `ToolOutputGuardrailTripwireTriggered` |

这里必须纠正一个常见误解：**没有"replace"这种独立行为**。所谓"替换工具输出"，就是输出护栏返回 `reject_content(message)`。

工具已经跑过，真实结果被丢弃，模型收到的是你给的 `message`。源码里这条路径会把结果标记为 rejection，并跳过输出 JSON schema 校验，因为你的 `message` 未必符合工具的输出结构。

`reject_content` 和 `raise_exception` 的选择标准很清楚：

- 想让 Agent **继续把活干完**（模型看到"我不让你查这个字段"，自己换个说法），用 `reject_content`；
- 想让整条流程**立刻终止**（安全事件、必须人工介入），用 `raise_exception`。

两个 tripwire 异常的字段也不一样。它们不像 Agent 级异常那样带 `guardrail_result`，而是直接暴露 `guardrail` 和 `output`。

累计结果在 `result.tool_input_guardrail_results` / `tool_output_guardrail_results` 里，跨轮累积。异常抛出时，已完成轮次的结果在 `exception.run_data.tool_*_guardrail_results` 里。

下面这段拦下含邮箱的工具输出，验证"替换结果"其实就是拒绝内容。它是片段，不是完整脚本：嵌到主线脚本的工具护栏定义区，前置 import 在脚本顶部。

```python
from agents import Agent, ToolGuardrailFunctionOutput
from agents.decorators import tool, tool_output_guardrail


@tool_output_guardrail(name="redact_customer_pii")
def redact_customer_pii(data) -> ToolGuardrailFunctionOutput:
    text = str(data.output or "")
    if "@" in text:
        # 工具已执行，但结果不回给模型，改成这句
        return ToolGuardrailFunctionOutput.reject_content(
            "查询结果包含邮箱，已按隐私策略屏蔽。请让用户通过工单系统查看。",
            output_info={"reason": "email_in_output"},
        )
    return ToolGuardrailFunctionOutput.allow()
```

预期结果是：工具照常执行，但模型拿到的是屏蔽说明，原始结果不会进入上下文。

## needs_approval：把决定权交给人

`needs_approval` 让危险工具在真正执行前停下来等人点头，它是 `FunctionTool` 的字段，`@tool(...)` 也能传。

类型是 `bool | Callable[[RunContextWrapper, dict[str, Any], str], Awaitable[bool]]`，两种用法：

- 传 `True`：这个工具**永远**要审批；
- 传一个 `async def (ctx, params, call_id) -> bool`：按本次调用的参数决定。参数是解析后的字典，所以可以直接判断"退款金额 > 1000 就要审批"。

下面这个回调按金额决定是否审批，验证条件审批的写法。它是片段，不是完整脚本：嵌到主线脚本的工具定义区，`tool` 装饰器的 import 在脚本顶部。

```python
from agents.decorators import tool


async def refund_needs_review(_ctx, params, _call_id) -> bool:
    return float(params.get("amount", 0)) > 1000


@tool(needs_approval=refund_needs_review)
async def issue_refund(order_id: str, amount: float, reason: str) -> str:
    """对指定订单发起退款。"""
    ...
```

预期结果是：金额超过 1000 弹审批，其余直接执行。

源码注释里有一条非常重要的 fail-closed 规则：**当参数无法被安全检查时，回调不会被调用，而是直接要求人工审批**。

这些情况都算"无法安全检查"：参数缺失、为空、只有空白、JSON 非法、JSON 合法但不是对象（`null` / 数组）、含有 `NaN` / `Infinity` 这类非标准常量，以及函数签名带默认值、类型转换、自定义校验器等"无法保真"的情况。

这条规则是善意的（宁可多问一次，也不要漏审），但它会带来一个真实的工程后果：**给危险工具的参数加默认值，会让"按条件审批"退化成"每次都审批"**。

所以财务、删除类工具的参数尽量全部必填，把判断逻辑放在回调里，而不是放在 Python 默认参数里。

## 审批交互流程：ToolApprovalItem 与 RunState

运行器暂停后，`result.interruptions` 里是 `ToolApprovalItem` 列表，恢复则靠 `RunState`。常用字段和属性有四组：

| 属性 | 含义 |
| --- | --- |
| `interruption.agent` | 发起该调用的 Agent（可能是交接后的子 Agent） |
| `interruption.name` | 工具名（内部优先取 `tool_name`，回落到 raw item 的 `name`） |
| `interruption.arguments` | 原始 JSON 字符串 |
| `interruption.call_id` | 调用 ID |

标准五步是下面这样。它是片段，不是完整脚本：嵌进入口脚本，`agent`、`reviewer_confirms` 由你的业务提供，`Agent`、`Runner` 的 import 在片段内。

```python
from agents import Agent, Runner

result = await Runner.run(agent, "删除订单 A-1024 的记录")

while result.interruptions:
    state = result.to_state()
    for item in result.interruptions:
        print(item.agent.name, item.name, item.arguments)
        if await reviewer_confirms(item):
            state.approve(item)              # 也可 always_approve=True
        else:
            state.reject(item, rejection_message="该操作已被风控拒绝。")
    result = await Runner.run(agent, state)   # 传 state，不是原始输入
```

预期结果是：每一轮都把待审批项处理完，最后一轮 `interruptions` 为空，`result` 里拿到最终输出。

几个容易踩的细节：

| 细节 | 说明 |
| --- | --- |
| **恢复要用原始顶层 Agent** | 即使中断来自交接后的子 Agent 或嵌套的 `Agent.as_tool()`，也是在外层 `RunState` 上审批、用外层 Agent 恢复。 |
| **可以只处理一部分** | 未处理的项会留在 `interruptions` 里，下次恢复时再次暂停；已处理的调用继续执行。 |
| **`always_approve=True` / `always_reject=True` 是"粘性决策"** | 会记在 `RunContextWrapper` 与 `RunState` 中。函数工具的粘性决策**按 Agent 隔离**；但 `ShellTool` / `ApplyPatchTool` 只按"工具类型 + 名字"匹配，跨 Agent 共享，官方文档专门为此写了警告。权限不同的执行器之间，请坚持用逐次决策。 |
| **拒绝文案有两层** | `RunConfig.tool_error_formatter` 管全局默认（`ToolErrorFormatterArgs.kind == "approval_rejected"` 时返回你的文案），`state.reject(item, rejection_message=...)` 管单次覆盖，后者优先。 |

## MCP 工具的审批

本地 MCP 服务端用 `require_approval` 声明审批策略，支持的形态有四种。

`MCPServerStdio`、`MCPServerSse`、`MCPServerStreamableHttp` 都适用：

| 形态 | 写法 |
| --- | --- |
| 布尔或字符串 | `"always"` / `"never"` / `True` / `False` |
| 按工具名映射 | `{"delete_file": "always", "read_file": "never"}` |
| 分组对象 | `{"always": {"tool_names": ["delete_file"]}}` |
| 同步或异步可调用对象 | `(run_context, agent, tool) -> bool` |

注意最后一条与 `needs_approval` 的差异。这个回调拿到的是 **MCP SDK 的 `Tool` 对象**（可以读 `tool.annotations`），而**不是**本次调用的参数和 call id。要按参数审批，只能在可调用对象里读应用上下文，或在服务端做限制。

托管 MCP（`HostedMCPTool`）则是在 `tool_config={"require_approval": "always"}` 上开关，并可提供 `on_approval_request` 做程序化决策。它不会进入本章这套本地 `RunState` 流程。

下面把删除订单交给服务端审批，验证分组写法。它是片段，不是完整脚本：把它嵌进你自己的 MCP 客户端入口，`async with` 退出后按业务继续。

```python
from agents.mcp import MCPServerStreamableHttp

async with MCPServerStreamableHttp(
    name="订单库 MCP",
    params={"url": "http://localhost:8000/mcp"},
    require_approval={"always": {"tool_names": ["delete_order"]}},
) as server:
    ...
```

预期结果是：模型每次调用 `delete_order`，都会先产生一条审批中断。

## 完整闭环：删除数据库记录需审批

把本章所有零件装成一个可运行的最小系统，就是一条完整的审批闭环。这也是本章的主线，是一段可直接运行的完整脚本。

目标是：`delete_order` 工具只能在"有明确 order_id、非全表、金额影响可控"时执行，且必须人工批准，执行结果不得把用户手机号带出去。

下面这段验证"护栏 + 审批 + 拒绝文案 + 输出脱敏"如何串成一条链。

```python
import asyncio
import json
from dataclasses import dataclass

from agents import (
    Agent,
    RunConfig,
    Runner,
    ToolErrorFormatterArgs,
    ToolGuardrailFunctionOutput,
)
from agents.decorators import tool, tool_input_guardrail, tool_output_guardrail


@dataclass
class OpsContext:
    operator: str
    tenant_id: str


# ---- 1. 输入护栏：参数级硬约束，零成本 ----
@tool_input_guardrail(name="guard_destructive_args")
def guard_destructive_args(data) -> ToolGuardrailFunctionOutput:
    args = json.loads(data.context.tool_arguments or "{}")
    if not args.get("order_id"):
        return ToolGuardrailFunctionOutput.reject_content("必须提供 order_id，禁止全表删除。")
    if args.get("hard_delete") not in (True, False):
        return ToolGuardrailFunctionOutput.raise_exception({"reason": "unexpected_args"})
    return ToolGuardrailFunctionOutput.allow()


# ---- 2. 输出护栏：脱敏 ----
@tool_output_guardrail(name="mask_phone")
def mask_phone(data) -> ToolGuardrailFunctionOutput:
    if "@" in str(data.output or ""):
        return ToolGuardrailFunctionOutput.reject_content("结果含邮箱，已按隐私策略屏蔽。")
    return ToolGuardrailFunctionOutput.allow()


# ---- 3. 审批策略：硬删除才要人批 ----
async def delete_needs_approval(_ctx, params, _call_id) -> bool:
    return bool(params.get("hard_delete"))


@tool(
    needs_approval=delete_needs_approval,
    tool_input_guardrails=[guard_destructive_args],
    tool_output_guardrails=[mask_phone],
)
async def delete_order(order_id: str, hard_delete: bool) -> str:
    """按订单号删除记录。

    Args:
        order_id: 订单号，必填。
        hard_delete: True 表示物理删除，False 表示软删除。
    """
    # 真实实现里这里是 UPDATE orders SET deleted_at = ... 或 DELETE ...
    return f"订单 {order_id} 已{'物理' if hard_delete else '逻辑'}删除。"


def format_rejection(args: ToolErrorFormatterArgs[OpsContext]) -> str | None:
    if args.kind != "approval_rejected":
        return None
    return "删除请求已提交审批，当前被拒绝；请补充工单号后重试。"


agent = Agent(
    name="运维助手",
    instructions="根据运维人员指令管理订单数据，删除前必须确认订单号。",
    tools=[delete_order],
)

run_config = RunConfig(tool_error_formatter=format_rejection, workflow_name="ops-console")


async def run_ops(command: str, ctx: OpsContext):
    result = await Runner.run(agent, command, context=ctx, run_config=run_config)
    while result.interruptions:
        state = result.to_state()
        for item in result.interruptions:
            # 真实系统在这里渲染前端确认弹窗，而不是 input()
            if item.name == "delete_order" and "hard" in (item.arguments or ""):
                state.reject(item, rejection_message="物理删除需 DBA 双人复核，本轮拒绝。")
            else:
                state.approve(item, always_approve=False)
        result = await Runner.run(agent, state, context=ctx, run_config=run_config)
    return result.final_output


async def main():
    ctx = OpsContext(operator="alice", tenant_id="T-1001")
    print(await run_ops("请调用 delete_order，order_id 为 A-1024，hard_delete 为 true。", ctx))


if __name__ == "__main__":
    asyncio.run(main())
```

把这个脚本存成 `tool_guardrail_demo.py`，放在 SDK 根目录 `openai-agents-python/` 下。按第2章配好 key 与模型名后运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python tool_guardrail_demo.py
```

预期输出是模型收到拒绝话术后的最终回复，形如"删除请求已提交审批，当前被拒绝；请补充工单号后重试。"或模型据此改口的答案。过程中还会看到一次中断被 `state.reject` 处理。如果模型没有调用工具，把命令写得更明确（例如直接点名 `delete_order` 和参数），再跑一次即可。

这段代码有四个关键点：

| 关键点 | 说明 |
| --- | --- |
| **护栏与审批各管一段** | 护栏判断"参数结构是否安全"（确定性、零成本），审批判断"这次操作是否被授权"（人的判断）。两者不能互相替代。 |
| **`hard_delete` 没有默认值** | 这是刻意的：有默认值会让 `needs_approval` 回调 fail-closed 成"每次都审批"。必填参数反而让策略更精确。 |
| **`raise_exception` 用于"参数被篡改"** | 这属于不该继续的场景；而"缺少 order_id"用 `reject_content`，让模型有机会补参数重试。 |
| **拒绝文案可定制** | 且区分了"全局默认"与"单次覆盖"，方便前端展示不同提示。 |

还有一处默认行为值得注意。上面的 `run_config` 没有打开预审批护栏，所以流程是"先弹审批 → 批准后再跑输入护栏"。

可选微调：如果你希望"参数都不合法的请求根本不该打扰审批人"，加上下面的 `tool_execution`，让输入护栏提前到审批之前跑。下面这段是片段，不是完整脚本：用它替换主线脚本里那行 `run_config = RunConfig(...)`，`format_rejection` 来自主线脚本。

```python
from agents import RunConfig, ToolExecutionConfig

run_config = RunConfig(
    tool_error_formatter=format_rejection,
    tool_execution=ToolExecutionConfig(pre_approval_tool_input_guardrails=True),
    workflow_name="ops-console",
)
```

预期结果是：输入护栏在发出审批中断之前先跑一遍，拦截明显非法的请求。通过审批后再跑一遍，前一遍省掉无意义的打扰，后一遍防止审批期间参数被改写。

## 常见坑与排查

按症状查，每条都给出"症状 / 原因 / 修法"。

1. **症状：工具护栏完全不生效，函数里打了 print 也没输出。** 原因：被保护的是托管工具或内置执行工具，它们不走 `FunctionTool` 管线；或护栏挂在了 `Agent.as_tool()` 上（该 API 不接受工具护栏参数）。修法：换成函数工具，或在服务端/应用层做检查。

2. **症状：审批通过了，但工具还是没执行。** 原因：输入护栏在审批之后又跑了一遍并返回了 `reject_content`。修法：查看 `result.tool_input_guardrail_results` 最后一条；把"结构性非法"与"需审批"拆成两条规则，避免互相打架。

3. **症状：`needs_approval` 回调里的条件从不生效，永远弹审批。** 原因：工具参数带默认值/类型转换/自定义校验器，触发 fail-closed。修法：把危险参数改成必填，或在回调里读 `call_id` 之外的上下文自行判断。

4. **症状：审批后恢复，历史里出现两条一样的工具调用。** 原因：拿旧 `result` 反复恢复，或没有复用同一个 `session`。修法：每次都用最新的 `result.to_state()`；带会话时恢复要传同一个 session 实例（同一 session_id）。

5. **症状：`state.approve(item)` 抛 `UserError: Cannot apply approval...`。** 原因：两个待审批项共享同一工具调用身份（常见于嵌套 `Agent.as_tool()` 里重复的 call_id）。修法：保证嵌套运行内 call_id 唯一。

6. **症状：`always_approve=True` 之后，另一个 Agent 的同名 shell 工具也被自动放行。** 原因：shell / apply_patch 的粘性决策不按 Agent 隔离。修法：改用逐次审批，或不要复用同一个 `RunContextWrapper`。

## 本章小结

- 工具护栏只覆盖 `FunctionTool` 管线（`@tool`/`@function_tool` 与本地 MCP 下发的工具）；护栏函数只收一个 data 对象，输入侧有 `context`/`agent`，输出侧多一个 `output`，参数要从 `data.context.tool_arguments` 自己解析。
- 行为只有三种：`allow`、`reject_content(message)`（输入侧跳过执行，输出侧替换结果）、`raise_exception`（抛 tripwire）；没有独立的 replace。
- 默认顺序是"审批 → 输入护栏 → 执行 → 输出护栏"；`pre_approval_tool_input_guardrails` 可让输入护栏提前到审批之前。
- `needs_approval` 支持布尔或异步回调；参数无法安全检查时 fail-closed，危险参数要必填。
- 审批走 `interruptions` + `RunState`，用顶层 Agent 恢复；`always_approve` 是粘性决策，函数工具按 Agent 隔离，shell/apply_patch 不隔离。
- 本地 MCP 用 `require_approval`，回调拿到的是 MCP `Tool` 而非调用参数；托管 MCP 用 `tool_config` 的 `require_approval`，不走本地 `RunState`。
