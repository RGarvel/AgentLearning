# 第18章 跨轮状态策略与上下文工程

第 17 章把 `Session` 讲透了，但它只回答"历史存哪里"。真实项目里紧接着会遇到第二个问题：**下一轮到底该把什么送进模型？** 全量重发、只发增量、交给服务端、还是读会话？四种选择在成本、可控性、可移植性上完全不同。这一章把它们放进一张决策表，再把"上下文窗口快满了怎么办"讲成可落地的工程手段。

## 学习目标

- 能列出四种跨轮状态策略，并说清各自的状态存在哪里、下一轮该传什么
- 能判断什么情况下必须用 `to_input_list()`、什么情况下 session 更合适
- 能正确使用 `previous_response_id` / `auto_previous_response_id` / `conversation_id`，并避开互斥组合
- 能用 `session_input_callback`、`call_model_input_filter`、`SessionSettings.limit`、压缩四种手段管理上下文窗口
- 能通过 `Usage` 观测每轮的 token 与请求数，并把一个手工循环平滑迁移到 session

## 四种策略：状态到底存在哪

先给结论表，后面逐条展开：

| 策略 | 状态存放位置 | 下一轮传什么 | 适合 | 不适合 |
| --- | --- | --- | --- | --- |
| `result.to_input_list()` | 你的应用内存/数据库 | 上一轮返回的完整列表 + 新用户消息 | 手工聊天循环、需要完全掌控、任意模型厂商 | 长对话（重发全量）、多进程共享 |
| `session=` | 你的存储 + SDK 管理 | 同一个 session 实例或同 ID 后端 | 持久化聊天、可恢复运行、自建存储 | 需要与服务端会话混用 |
| `conversation_id` | OpenAI Conversations API | 同一个 `conversation_id` + 只传新输入 | 跨服务/跨语言共享的命名会话 | 想离线保存全量原始上下文 |
| `previous_response_id` | OpenAI Responses API | `result.last_response_id` + 只传新输入 | 最轻量的服务端续接 | 需要脱离 OpenAI 存储、需要审计原文 |

两条判据可以先帮你砍掉一半选项：**状态归谁管**（客户端 vs 服务端），以及**你要不要拿到原始全量历史**。要审计、要迁移、要换厂商，就一定得是客户端托管（前两种）。

## 策略一：to_input_list()，最透明也最累

`result.to_input_list()` 把本轮运行转换成一个"扁平输入列表"：历史输入 + 本轮新生成的 item。下一轮你把它和新消息拼起来再传回去。

```python
from agents import Agent, Runner, trace

agent = Agent(name="助手", instructions="回答简洁。")
history: list = []

with trace(workflow_name="Conversation", group_id="thread_123"):
    history += [{"role": "user", "content": "金门大桥在哪个城市？"}]
    result = await Runner.run(agent, history)
    history = result.to_input_list()

    history.append({"role": "user", "content": "它在哪个州？"})
    result = await Runner.run(agent, history)
    history = result.to_input_list()
```

0.25 里 `to_input_list` 多了一个 `mode` 参数：

- `mode="preserve_all"`（默认）：历史行为的完整视图，把 `new_items` 全量转成 input item，适合日志、审计、UI 展示。
- `mode="normalized"`：当交接（handoff）的输入过滤器改写过模型历史时，优先返回"规范的续接输入"，普通运行下两者一致。

判断标准很简单：**这份列表接下来要喂回 `Runner.run`，就用 `normalized`；要存档或展示，就用默认值。**

它的最大优点是可控：你能看见每一个 item，能裁剪、能替换、能存进自己的数据库。最大的缺点是**每轮重发全量**——对话到第 30 轮，输入 token 会非常可观。它也不适合多进程：历史在某个进程的变量里，别的 worker 看不见。

## 策略二：session=，让 SDK 管读写

```python
from agents import Agent, Runner, SQLiteSession

agent = Agent(name="助手", instructions="回答简洁。")
session = SQLiteSession("thread_123", "conversations.db")

result = await Runner.run(agent, "金门大桥在哪个城市？", session=session)
result = await Runner.run(agent, "它在哪个州？", session=session)
```

运行器自动做三件事：读历史、拼新输入、写回新 item。你的代码里不再出现"历史列表"这个变量。

它和 `to_input_list` 的本质差别不是"少写几行"，而是**状态的归属从函数局部变量变成了可共享的存储**。多进程、多实例、重启后继续，都靠它。代价是你得为存储负责：选型、清理、并发、备份（第 17 章整章都在讲这个）。

> 提示：`Runner.run` 的 `session` 是关键字参数，且不能与 `conversation_id` / `previous_response_id` / `auto_previous_response_id` 同轮出现。这是最常见的组合报错来源。

## 策略三：previous_response_id，最轻的服务端续接

OpenAI Responses API 会保存响应。下一轮只要告诉它"接着哪个响应"，就不用重发历史：

```python
from agents import Agent, Runner

agent = Agent(name="助手", instructions="回答简洁。")
previous_response_id = None

while True:
    user_input = input("你：")
    result = await Runner.run(
        agent,
        user_input,
        previous_response_id=previous_response_id,
        auto_previous_response_id=True,   # 首轮没有上一个响应也能链起来
    )
    previous_response_id = result.last_response_id
    print("助手：", result.final_output)
```

三个要点：

1. `result.last_response_id` 就是最近一次模型响应的 ID；多步运行（含工具调用）会有多个响应，它是最后一个。
2. `auto_previous_response_id=True` 让**首轮**也走链式路径（此时还没有 ID），后续轮的行为保持一致，避免"第一轮走 A 路径、第二轮走 B 路径"的诡异差异。
3. 它和 `conversation_id` **互斥**，一次只能用一个。

它的优势是省流量、省延迟。代价是历史留在服务端：你拿不到原始全量文本，换厂商/换模型时迁移成本高，也无法做本地全文审计。另外，如果运行会暂停审批再恢复，SDK 会把 `previous_response_id` / `auto_previous_response_id` 一起存进 `RunState`，恢复后仍在同一条链上。

## 策略四：conversation_id，命名的服务端会话

`previous_response_id` 是"链式"，`conversation_id` 是"命名容器"。你可以在任意进程里用同一个 ID 接上同一段对话：

```python
from agents import Agent, Runner
from openai import AsyncOpenAI

client = AsyncOpenAI()
agent = Agent(name="助手", instructions="回答简洁。")

conversation = await client.conversations.create()
conv_id = conversation.id

result = await Runner.run(agent, "帮我查下订单 A-1024", conversation_id=conv_id)
result = await Runner.run(agent, "那退款进度呢？", conversation_id=conv_id)
```

什么时候选它而不是 `previous_response_id`？当"这段对话本身是一个可被多方引用的资源"时——比如客服系统里，Web 前端、工单系统、质检后台都要挂到同一段会话上。反之，如果只是"接着上一句说"，`previous_response_id` 更轻。

> 注意：服务端托管（`conversation_id` / `previous_response_id` / `auto_previous_response_id`）会让 `RunConfig.handoff_input_filter` 与 `nest_handoff_history` 失效（后者会带警告自动关闭）。因为历史不在本地，SDK 无法改写交接时传给下一个 Agent 的内容。做多 Agent 交接又要精细控制历史，就必须用客户端托管。

## 组合禁区与选型流程

把限制集中列一下，能省掉大量调试时间：

| 组合 | 是否允许 | 说明 |
| --- | --- | --- |
| `session` + `to_input_list()` | 概念冲突 | 二者都在做历史拼接，容易重复；选一个 |
| `session` + `conversation_id` | ❌ | 客户端托管 vs 服务端托管 |
| `session` + `previous_response_id` | ❌ | 同上 |
| `session` + `auto_previous_response_id` | ❌ | 同上 |
| `conversation_id` + `previous_response_id` | ❌ | 两个服务端容器互斥 |
| 服务端托管 + `handoff_input_filter` | ❌（失效） | 历史不在本地，无法改写 |

选型可以按这个顺序问自己：

1. **必须用非 OpenAI 模型或要换厂商吗？** 是 → 客户端托管（`to_input_list` 或 session）。
2. **要跨进程/多 worker 共享吗？** 是 → session（配 Redis/Postgres）。
3. **要审计每一轮的原始 item 吗？** 是 → session 或 `to_input_list`。
4. **有精细的交接历史控制需求吗？** 是 → 客户端托管。
5. 以上都不是，只想要"接着上一句" → `previous_response_id`；要"命名会话资源" → `conversation_id`。

## 上下文窗口管理：四把刀

即便选了 session，历史也会无限增长。四把刀从轻到重：

**第一把：限制读取条数。** `SessionSettings(limit=N)` 或 `RunConfig.session_settings`。最省事，但它是"硬截断"，可能把关键的系统性约定（比如"用户是 VIP，不要说退款时限"）也截掉。

**第二把：合并时裁剪/重排。** `RunConfig.session_input_callback(history, new_input) -> list`。适合"保留前 2 条 + 最近 20 条"这种结构化策略：

```python
from agents import Agent, RunConfig, Runner, SessionSettings, SQLiteSession


def keep_pinned_and_recent(history, new_input):
    if len(history) <= 22:
        return history + new_input
    return history[:2] + history[-20:] + new_input


session = SQLiteSession("thread_123", "conversations.db")
agent = Agent(name="客服", instructions="回答简洁。")

result = await Runner.run(
    agent,
    "继续刚才的退款问题。",
    session=session,
    run_config=RunConfig(
        session_input_callback=keep_pinned_and_recent,
        session_settings=SessionSettings(limit=200),
    ),
)
```

注意分工：`limit=200` 控制"从存储读多少"，callback 控制"送模型多少"。两个数字不必相等。

**第三把：模型调用前的最后一道加工。** `RunConfig.call_model_input_filter` 收到 `CallModelData`（含 `model_data.input`、`model_data.instructions`、`agent`、`context`），必须返回一个 `ModelInputData`。它比 `session_input_callback` 更晚、更底层：**每次**模型调用前都会跑（多步运行里一轮可能有多次），而 `session_input_callback` 只在准备本轮输入时参与合并。

```python
from agents.run import CallModelData, ModelInputData


def trim_before_model_call(data: CallModelData[None]) -> ModelInputData:
    items = data.model_data.input
    if len(items) > 40:
        items = items[:1] + items[-39:]
    return ModelInputData(input=items, instructions=data.model_data.instructions)
```

返回其它形状会抛 `UserError`，这是 0.25 的显式校验。

**第四把：压缩。** `OpenAIResponsesCompactionSession`（第 17 章）把前缀折叠成压缩项，比截断更"记得住"。它解决的是"历史长度"，不是"优先级"——重要约定仍然应该写进 `instructions`，而不是指望它活过压缩。

## 观测 token 与成本

没有度量就没有优化。每次运行结束后，`result.context_wrapper.usage` 是一个 `Usage` 对象：

| 字段 | 含义 |
| --- | --- |
| `requests` | 模型请求次数（含多步、含交接后的调用） |
| `input_tokens` / `output_tokens` / `total_tokens` | token 统计 |
| `input_tokens_details.cached_tokens` | 命中缓存的输入 token |
| `output_tokens_details.reasoning_tokens` | 推理模型消耗的推理 token |

```python
result = await Runner.run(agent, user_input, session=session)
usage = result.context_wrapper.usage
log.info(
    "turn done",
    extra={
        "requests": usage.requests,
        "input_tokens": usage.input_tokens,
        "cached": usage.input_tokens_details.cached_tokens,
        "output_tokens": usage.output_tokens,
    },
)
```

三条实践建议：

1. **盯 `input_tokens` 的增长曲线**，而不是单轮值。它的斜率就是你上下文策略的效果。
2. **看 `cached_tokens`**。客户端托管历史时，稳定的前缀更容易命中提示缓存；把易变内容（时间戳、用户昵称）放到后面能提升命中率。
3. **把 usage 存在会话维度上**，才能回答"哪类用户把成本推高了"。

## 多轮 + 交接 + 流式：三个叠加的坑

这三个特性单独用都不难，叠在一起就开始出问题。

**坑一：流式时 `final_output` 是 `None`。** 必须在 `stream_events()` 迭代结束后再读 `final_output`、`interruptions`、`raw_responses`。中途读到的都是半成品。

**坑二：交接改写了历史，下一轮却用了旧的列表。** 如果用了 `handoff_input_filter`，交接后模型看到的历史与"你手里的列表"可能不同。此时下一轮的输入应该来自 `result.to_input_list(mode="normalized")`，而不是你自己拼的列表。

**坑三：暂停恢复时同时换了两样东西。** 恢复 `RunState` 时，如果你既换了 session 又换了 Agent，很可能得到"历史对不上"的结果。规则是：恢复用**原始顶层 Agent**，session 用**同一个实例或同 ID 后端**。

## 演进式示例：长对话客服的三次迭代

**v1：手工列表。** 最快能跑，也最容易出 bug。

```python
from agents import Agent, Runner

agent = Agent(name="客服", instructions="你是电商客服，回答简洁，必要时查订单。")
history: list = []


async def chat_v1(user_message: str) -> str:
    history.append({"role": "user", "content": user_message})
    result = await Runner.run(agent, history)
    history[:] = result.to_input_list()
    return result.final_output
```

问题：进程重启就失忆；第 30 轮时输入 token 暴涨；多实例无法共享。

**v2：换成 session。** 调用方代码从"维护列表"变成"传一个对象"。

```python
from agents import Agent, Runner, SQLiteSession

agent = Agent(name="客服", instructions="你是电商客服，回答简洁，必要时查订单。")
session = SQLiteSession("ticket_456", "support.db")


async def chat_v2(user_message: str) -> str:
    result = await Runner.run(agent, user_message, session=session)
    return result.final_output
```

行为等价，但历史落到了 SQLite，重启和多进程都能续上。注意 `chat_v2` 的入参不再需要 `history`——这是"状态外置"带来的接口简化。

**v3：加窗口、加观测、加压缩。** 真实长对话客服最终大概是这个形态：

```python
from agents import Agent, RunConfig, Runner, SQLiteSession, SessionSettings
from agents.memory import OpenAIResponsesCompactionSession

base = SQLiteSession("ticket_456", "support.db")
session = OpenAIResponsesCompactionSession(
    session_id="ticket_456",
    underlying_session=base,
    should_trigger_compaction=lambda ctx: len(ctx["compaction_candidate_items"]) >= 20,
)

agent = Agent(name="客服", instructions="你是电商客服，回答简洁，必要时查订单。")


def keep_pinned(history, new_input):
    return history if len(history) <= 30 else history[:2] + history[-28:] + new_input


run_config = RunConfig(
    session_input_callback=keep_pinned,
    session_settings=SessionSettings(limit=120),
    workflow_name="support-chat",
)


async def chat_v3(user_message: str) -> str:
    result = await Runner.run(agent, user_message, session=session, run_config=run_config)
    print("tokens:", result.context_wrapper.usage.input_tokens)
    return result.final_output
```

在这个形态里，四层各司其职：`limit=120` 控制 IO，`keep_pinned` 控制送模型的内容，压缩控制存储膨胀，`usage` 负责告警。**它们不是互相替代的关系，而是同一条流水线上的不同闸门。**

## 常见坑与排查

**症状：第二轮回答"忘了上一轮"，但日志里历史明明写了。**
原因：`to_input_list()` 的结果被覆盖而不是追加，或每轮重新 `Runner.run(agent, 单条消息)` 而没传历史/session。修法：统一成一个策略，别一半手工一半自动。

**症状：报错提示不能同时使用 session 和 conversation_id。**
原因：混用了客户端与服务端托管。修法：一轮只选一种；迁移期把开关收敛到一个配置项。

**症状：交接之后的回答风格突变，像丢了上下文。**
原因：用了服务端托管，导致 `handoff_input_filter` / `nest_handoff_history` 失效。修法：改客户端托管，或显式在交接后补一段摘要。

**症状：`call_model_input_filter` 报 `UserError`。**
原因：返回了 list 或 `None`，而不是 `ModelInputData`。修法：严格构造 `ModelInputData(input=..., instructions=...)`。

**症状：流式输出结束事件之后还报错。**
原因：没等 `stream_events()` 迭代完就读结果，或提前 `cancel()` 后没继续消费。修法：始终迭代到底，再读 `final_output` / `interruptions`。

**症状：token 账单突然翻倍，代码没改。**
原因：从 `previous_response_id` 换成了手工全量重发，或压缩阈值调高。修法：对比 `usage.input_tokens` 斜率，回看历史策略变更。

## 本章小结

- 四种策略：`to_input_list()`（客户端全量）、`session`（客户端存储）、`previous_response_id`（服务端链式）、`conversation_id`（服务端命名容器）。
- `to_input_list(mode="normalized")` 用于交接后继续喂给 `Runner.run`；默认 `preserve_all` 用于展示与审计。
- session 与三种服务端托管参数互斥；`conversation_id` 与 `previous_response_id` 互斥。
- 服务端托管会让 `handoff_input_filter`、`nest_handoff_history` 失效。
- 四把刀：`SessionSettings.limit` → `session_input_callback` → `call_model_input_filter` → 压缩，各管一段。
- `call_model_input_filter` 每次模型调用前都跑，且必须返回 `ModelInputData`。
- 用 `result.context_wrapper.usage` 观测 `requests` / `input_tokens` / `cached_tokens`，看斜率不看单点。
- 演进路径：手工列表 → session → 窗口 + 压缩 + 观测，每步都保持对外接口不变。
