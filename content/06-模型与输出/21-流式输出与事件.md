# 第21章 流式输出与事件

第 20 章让输出变成可入库的对象，但对象是「最终态」。用户在产品里看到的不是最终态，而是**一个词一个词冒出来的过程**。

流式不只是体验优化。在长任务里，它决定用户会不会在 30 秒后直接关掉页面。

这一章讲清三件事：事件有哪几类、流式运行的生命周期特殊在哪、以及出错和取消时你怎么不丢数据。读完你会知道：怎么把 SDK 的事件翻译成前端的打字机与工具卡片。

## 学习目标

- 能说出 `Runner.run_streamed()` 与 `Runner.run()` 在返回时机和生命周期上的三点差异。
- 能区分 `RawResponsesStreamEvent`、`RunItemStreamEvent`、`AgentUpdatedStreamEvent` 各自的用途与字段。
- 能写出「打字机文本 + 工具调用卡片」的前端事件协议。
- 能在流式 + session 的场景下判断数据何时落盘，避免读到半成品。
- 能正确使用 `cancel("immediate")` 与 `cancel("after_turn")`，并知道必须继续消费事件。
- 能用 `to_state()` 把一次被中断的流式运行恢复起来。

## 21.1 两个 API，两种时间观

两个入口的差别不在参数，而在「什么时候把控制权交还给你」。并排看一眼调用形态就清楚了。

```python
result = await Runner.run(agent, "按季度汇总这份财报")      # 等全部结束才返回
result = Runner.run_streamed(agent, "按季度汇总这份财报")     # 立刻返回一个句柄
async for event in result.stream_events():                    # 事件随生成而到达
    ...
```

预期结果是：`run()` 要等全部结束才返回，`run_streamed()` 立刻拿到句柄，事件随后逐条到达。

`run_streamed()` 是普通方法，不是 `async def`。它启动后台运行任务并立刻返回 `RunResultStreaming`，真正的执行在 `stream_events()` 被迭代时推进。由此产生三条铁律。

1. **不消费就不算完成。** 流式运行必须把异步迭代器读到底；`final_output`、`interruptions`、`raw_responses` 都可能在你看到最后一个 token 之后仍在收尾。
2. **`final_output` 在流结束前一直是 `None`。** 不要在处理事件时读它，读到的必然是 `None`。
3. **提前 `break` 不会停止后台运行。** 它可能继续调模型、继续调工具。想停就显式取消（见 21.6）。

`RunResultStreaming` 上可实时观察的字段与 `RunResult` 不同，值得单独记一张表。

| 字段 | 含义 | 何时可信 |
| --- | --- | --- |
| `current_agent` | 当前执行的 Agent（handoff 后会变） | 流进行中 |
| `current_turn` | 当前轮次 | 流进行中 |
| `is_complete` | 是否到达终止态 | 流结束后 |
| `interruptions` | 待审批的工具调用 | 流结束后 |
| `final_output` | 最终输出 | 流结束后 |
| `run_loop_exception` | 后台任务的异常（可能没经事件抛出） | 流结束后 |

最后一行是排障的关键。某些失败发生在「还没产出任何事件」之前，例如初始化阶段，此时 `stream_events()` 可能安静结束。收流后补一句 `if result.run_loop_exception: raise result.run_loop_exception`，是低成本的自保。

顺便解释一个常见困惑：为什么 `run_streamed()` 不是 `async def`？因为它只做两件事，构造结果对象、把运行循环丢进后台任务，本身没有需要 `await` 的 I/O。真正的等待发生在你迭代事件时。

这也意味着**忘了迭代就等于忘了运行**。对象建好了，后台任务却不会被推进，最终什么也不会发生。

## 21.2 三类事件：从底层到语义层

`StreamEvent` 是三个 dataclass 的联合类型，用 `event.type` 区分。

| 事件 | `type` | 关键字段 | 用途 |
| --- | --- | --- | --- |
| `RawResponsesStreamEvent` | `raw_response_event` | `data`（Responses API 原始事件） | 逐 token 渲染、观察参数拼接 |
| `RunItemStreamEvent` | `run_item_stream_event` | `name`、`item`（`RunItem`） | 消息完成、工具调用、工具结果、handoff |
| `AgentUpdatedStreamEvent` | `agent_updated_stream_event` | `new_agent` | 当前 Agent 切换（handoff） |

`RunItemStreamEvent.name` 是一个**固定枚举**，0.25.0 共 11 个值：`message_output_created`、`handoff_requested`、`handoff_occured`、`tool_called`、`tool_search_called`、`tool_search_output_created`、`tool_output`、`reasoning_item_created`、`mcp_approval_requested`、`mcp_approval_response`、`mcp_list_tools`。

> 注意：`handoff_occured` 少一个 r，是历史拼写错误。源码注释明确写了「不能改，改了就是 breaking change」。用字符串比较时别自作聪明改成 `occurred`。

`event.item.type` 又是另一套名字（`message_output_item`、`tool_call_item`、`tool_call_output_item`、`reasoning_item`、`handoff_call_item`…）。两套命名并存是常态。

`name` 描述「发生了什么动作」，`item.type` 描述「产物是什么类型」。写 UI 时建议按 `name` 分支，再按需读 `item`。

## 21.3 打字机：只认一个 delta 事件

最小可用的打字机实现，只需要一种原始事件 `ResponseTextDeltaEvent`。下面这段跑起来就是一个逐字输出的终端。

```python
import asyncio

from openai.types.responses import ResponseTextDeltaEvent

from agents import Agent, Runner


async def main() -> None:
    agent = Agent(name="Summarizer", instructions="用中文简洁作答。")
    result = Runner.run_streamed(agent, input="用三句话解释什么是幂等。")
    async for event in result.stream_events():
        if event.type == "raw_response_event" and isinstance(event.data, ResponseTextDeltaEvent):
            print(event.data.delta, end="", flush=True)
    print()


if __name__ == "__main__":
    asyncio.run(main())
```

预期结果是：三句话逐词打印在同一行，最后换行结束。

`event.data.delta` 是增量片段，不是完整文本。不要每帧覆盖，要累加。`flush=True` 不能省，否则终端缓冲会把「流式」变成「最后一次性输出」。

如果你要做「逐字动画」，在 UI 侧再缓冲一层。网络分片大小不可控，一个 delta 可能是三个字，也可能是半句话。

## 21.4 工具调用卡片：两个阶段，两种事件

工具调用的可视化分两个阶段，对应两类事件。

| 阶段 | 事件 | 你能拿到什么 |
| --- | --- | --- |
| 模型开始生成参数 | `raw_response_event` 加 `ResponseFunctionCallArgumentsDeltaEvent` | 参数 JSON 的增量片段 |
| 工具真的被执行 | `run_item_stream_event`（`tool_called` / `tool_output`） | 完整 `ToolCallItem` 与 `ToolCallOutputItem` |

前者适合做「正在调用 get_weather，参数 {city: 东」这种实时反馈，后者适合做「调用完成、结果是晴」的结果卡片。只想要卡片的话，可以完全忽略原始事件。

```python
from agents import Agent, ItemHelpers, Runner
from agents.decorators import tool


@tool
def get_weather(city: str) -> str:
    """查询城市天气。"""
    return f"{city}：晴，24 度"


async def render(agent: Agent, user_input: str) -> None:
    result = Runner.run_streamed(agent, input=user_input)
    async for event in result.stream_events():
        if event.type == "agent_updated_stream_event":
            print(f"[切换到 {event.new_agent.name}]")
        elif event.type == "run_item_stream_event":
            if event.name == "tool_called":
                print(f"[调用工具 {getattr(event.item.raw_item, 'name', 'unknown')}]")
            elif event.name == "tool_output":
                print(f"[工具返回 {event.item.output}]")
            elif event.name == "message_output_created":
                print(f"[消息] {ItemHelpers.text_message_output(event.item)}")
```

预期结果是：一次问答里依次打印切换提示、工具调用、工具返回和最终消息，全程不解析原始协议。

这段代码验证一件事：**语义事件足够支撑一个完整的对话 UI**。你不需要解析原始协议。原始事件只在两种场景值得用：逐 token 渲染，以及观察工具参数生成过程。

另外注意 `tool_called` 与 `handoff_requested` 的分工。交接不会被同时报成 `tool_called`，它是独立事件。做 UI 时如果只处理 `tool_called`，交接会被静默吞掉，用户会看到 Agent 突然换了个说话风格却没有任何提示。

## 21.5 流式 + session：落盘发生在流结束之后

带 `session=` 的流式运行，落盘时机比你想的晚：「会话写入、审批簿记、历史压缩等收尾动作，可能发生在最后一个可见 token 之后」。文档的原话是「流式运行要等你把 `stream_events()` 消费完才算完成」。

由此推出两条实践规则。

1. 判断「这一轮结束了」要用**迭代器结束**，不要用「收到最后一条 message」。
2. 流式跑完立刻用同一份 session 发起下一轮，是安全的。但如果中途 `break`，session 里可能只写了一半，此时下一轮会看到残缺历史。

`cancel(mode="after_turn")` 正是为这个场景设计的。它允许当前轮把 LLM 响应读完、把待执行工具跑完、把 session 状态存好，然后在下一轮开始前停下。

## 21.6 取消：两种模式与一个必做动作

取消有两种模式，选错会让 session 停在半截。先看调用位置。

```python
result = Runner.run_streamed(agent, "生成长报告", session=session)
async for event in result.stream_events():
    if user_pressed_stop():
        result.cancel(mode="after_turn")   # 优雅：本轮做完再停
        # result.cancel()                  # 立即：清空队列、取消任务
```

预期结果是：用户点停止时，本轮仍会跑完再退出，而不是立刻断开。

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `"immediate"`（默认） | 取消所有任务、清空队列、立刻标记完成 | 用户明确放弃、要立刻释放资源 |
| `"after_turn"` | 读完本轮 LLM 响应、执行待跑工具、保存 session，再停 | 用户想「先看完这段」、需要状态一致 |

**取消后必须继续消费 `stream_events()`**，让清理路径跑完。这句话在源码注释和文档里各出现一次，不是客套。不消费会让清理悬挂。

还有一类更隐蔽的情况：消费者自己提前退出（`break`、处理事件时抛异常、任务被取消）。此时后台运行不一定停。文档给的范式值得背下来。

```python
result = Runner.run_streamed(agent, input="请生成 5 个笑话")
events = result.stream_events()
exhausted = False
try:
    async for event in events:
        await forward_to_client(event)
    else:
        exhausted = True
finally:
    if not exhausted:
        result.cancel()
        await events.aclose()
        async for _ in result.stream_events():   # 用新迭代器跑完清理
            pass
```

预期结果是：无论消费者是正常读完还是中途退出，后台任务都会被取消，清理逻辑都会跑完。

三个细节。`else` 挂在 `for` 上，只有正常耗尽才执行。`cancel()` 只是「请求取消」，不等于已经停下。收尾要用**新的**迭代器，因为原迭代器可能已被取消关闭。

## 21.7 错误、最终结果与流里的异常从哪抛

`stream_events()` 抛出的异常与同步运行一致，区别只在**抛出的位置**。异常会在迭代过程中抛出，而不是在 `run_streamed()` 调用时抛出。

会出现的异常包括 `MaxTurnsExceeded`、`InputGuardrailTripwireTriggered`、`OutputGuardrailTripwireTriggered`、`ModelBehaviorError`、`ModelRefusalError`、工具超时等。

所以流式代码必须把整个 `async for` 包在 `try/except` 里，而不是只包 `run_streamed()`。同时保留一个「流已中断」的标记，供前端把最后一条消息标成失败。

```python
from agents import MaxTurnsExceeded, OutputGuardrailTripwireTriggered

try:
    async for event in result.stream_events():
        await forward_to_client(event)
    if result.run_loop_exception is not None:
        raise result.run_loop_exception
except MaxTurnsExceeded:
    await notify_client("达到轮次上限，请缩小任务范围")
except OutputGuardrailTripwireTriggered as exc:
    await notify_client(f"输出被拦截：{exc.guardrail_result.guardrail.get_name()}")
```

预期结果是：轮次超限与输出被拦截各走各的提示，前端不会只看到一条断掉的流。

注意 `MaxTurnsExceeded` 在流式下会**先把队列里已有的事件吐完再抛**。源码里对这种情况专门做了 drain，所以你不必担心「异常来了但用户什么都没看到」。

异常抛出后，`result` 上的累计状态仍然可读。`new_items`、`raw_responses`、`context_wrapper.usage` 都保留了中断前已产生的部分。做成本核算或问题归因时，这些部分数据比异常消息有用得多。尤其 `usage` 已经计过费，别因为「这一轮失败了」就把它从账单里抹掉。

## 21.8 to_state：流式的可恢复快照

`RunResultStreaming.to_state()` 与同步版行为一致，返回一个可序列化的 `RunState`。它的典型用途是工具审批中断。

```python
result = Runner.run_streamed(agent, "删除临时文件")
async for _event in result.stream_events():
    pass

if result.interruptions:
    state = result.to_state()
    for item in result.interruptions:
        if item.tool_name == "delete_files":
            state.approve(item)
        else:
            state.reject(item, rejection_message="该操作需要人工确认")
    result = Runner.run_streamed(agent, state)
    async for _event in result.stream_events():
        pass
```

预期结果是：审批通过的工具继续执行，被拒的带上拒绝理由返回，运行从断点接着走。

三个边界要记住。第一，**必须先把流读完**再看 `interruptions`，中途读是空的。

第二，`to_state()` 做的是快照，恢复出的新运行与原 `RunResult` 的 usage 相互独立。

第三，若失败发生在「已接受最终输出、但在写 session 时失败」之后，状态会被标记为不可恢复。再次恢复会直接抛 `UserError`，这时应该开新一轮，而不是重试旧状态。

## 21.9 与 FastAPI / WebSocket 结合的骨架

下面是一个最小骨架：浏览器发一句话，服务端把 SDK 事件翻译成自己的 JSON 协议推回去。注意这里**没有引入任何 SDK 之外的抽象**，只做了协议映射。

```python
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

from agents import Agent, Runner

app = FastAPI()
agent = Agent(name="Assistant", instructions="用中文简洁作答。")


@app.websocket("/chat")
async def chat(websocket: WebSocket) -> None:
    await websocket.accept()
    try:
        while True:
            user_text = await websocket.receive_text()
            result = Runner.run_streamed(agent, input=user_text)
            try:
                async for event in result.stream_events():
                    if event.type == "raw_response_event":
                        delta = getattr(event.data, "delta", None)
                        if isinstance(delta, str):
                            await websocket.send_json({"type": "delta", "text": delta})
                    elif event.type == "run_item_stream_event":
                        if event.name == "tool_called":
                            await websocket.send_json({"type": "tool_call"})
                        elif event.name == "tool_output":
                            await websocket.send_json(
                                {"type": "tool_result", "content": str(event.item.output)}
                            )
            except WebSocketDisconnect:
                result.cancel()
                raise
            await websocket.send_json({"type": "done"})
    except WebSocketDisconnect:
        return
```

预期结果是：前端收到一串 `delta`、若干 `tool_call` / `tool_result`，最后收到一条 `done`。

四个设计决定值得解释。只转发 `delta` 与少数语义事件，避免把原始协议泄露给前端。`WebSocketDisconnect` 时显式 `cancel()`，否则模型会在没人听的情况下继续烧 token。

结尾统一发 `done`，让前端知道「流结束」而不是「网络卡住」。整段没有 `await result.final_output` 这类调用，因为流式下它只在结束后才有值。

> 提示：生产环境还要加三样东西：鉴权、心跳，以及「同一连接同时只跑一个 run」的互斥。这些与 SDK 无关，但漏了就会在生产上以「偶发重复扣费」的形式出现。

## 常见坑与排查

1. **症状**：`final_output` 一直是 `None`，但事件看起来都收完了。
   **原因**：在读事件期间访问了 `final_output`，或迭代器没读完就 `break`。
   **修法**：把读取移到 `async for` 之后；用 `result.is_complete` 判断是否真的结束。

2. **症状**：用户点了「停止」，后台仍在跑、仍在计费。
   **原因**：只 `break` 了循环，没调 `cancel()`；或调了 `cancel()` 但没继续消费事件。
   **修法**：按 21.6 的范式，`cancel()` 加继续用新迭代器收尾。要保 session 一致就用 `mode="after_turn"`。

3. **症状**：流式跑完后立刻发下一轮，session 里少了最后几条消息。
   **原因**：不知道 session 写入发生在流结束之后，提前换了轮次或换了 session 对象。
   **修法**：等迭代器结束；需要中途停就用 `after_turn`。

4. **症状**：UI 只在最后一次性显示全文，看起来不像「流式」。
   **原因**：漏了 `flush=True`、前端按帧覆盖而不是累加、或在中间层做了缓冲。
   **修法**：累加 delta，逐帧推送，别在服务端做整段 join。

5. **症状**：交接之后 UI 状态错乱，工具卡片消失。
   **原因**：只处理了 `tool_called`，没处理 `handoff_requested` 与 `agent_updated_stream_event`。
   **修法**：把 `agent_updated_stream_event` 当作「会话上下文切换」的信号，重置卡片区。

```bash
# 工作目录：repo/openai-agents-python/（SDK 根目录）
cd repo/openai-agents-python
```

## 本章小结

- `run_streamed()` 立即返回句柄，执行由 `stream_events()` 推进；不消费完就不算完成。
- 三类事件：`RawResponsesStreamEvent`（原始）、`RunItemStreamEvent`（语义产物）、`AgentUpdatedStreamEvent`（Agent 切换）。
- `RunItemStreamEvent.name` 是固定枚举，`handoff_occured` 拼写是历史遗留，不能改；打字机只需 `ResponseTextDeltaEvent`，工具卡片用 `tool_called` 与 `tool_output`。
- 流式加 session 的落盘发生在流结束后；`cancel("after_turn")` 用来保住本轮状态。
- 取消后必须继续消费事件；提前 `break` 要显式 `cancel()` 并收尾。
- 异常从 `stream_events()` 抛出，收流后再查一次 `run_loop_exception` 防静默失败；`to_state()` 用于审批中断恢复，前提是先把流读完。
