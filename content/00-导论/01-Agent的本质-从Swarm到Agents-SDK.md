# 第1章 Agent的本质：从Swarm到Agents SDK

上一章给了你一张地图和一套学习方法，从这一章起开始装零件。但在写下第一行 `Agent(...)` 之前，你得先回答一个更基本的问题：当一个团队说"我们要做个 Agent"时，他们说的到底是哪台机器？

本章只用一页纸的代码，把这个词拆成四个可检查的部件，同时说清 Agents SDK 在 OpenAI 技术栈里占的是哪一层。学完你能做三件事：用四部件拆解任意 Agent 产品，判断一个需求该用 SDK 还是直接调 Responses API，并画出一次单轮执行的时序图。

---

## 学习目标

- 能说清 LLM 应用三代演进（提示词 → 函数调用 → 智能体循环），并指出每一代多解决了什么问题、又多出了什么责任。
- 能用"模型 + 指令 + 工具 + 循环"四个部件拆解任意一个 Agent 产品。
- 能说出 Agents SDK 的三个原语，以及它们各自的边界。
- 能判断一个需求该用 Agents SDK，还是直接调 Responses API。
- 能画出一次单轮执行的时序：模型调用 → 工具调用 → 结果回填 → 再调用。

---

## 一、三代演进：从"把话说好"到"把事做完"

Agent 不是突然出现的概念，而是 LLM 应用形态演进的第三站；把三代并排看，更容易理解 SDK 为什么长成现在这样。

| 代际 | 典型形态 | 核心动作 | 新增能力 | 新增责任 | 失败长相 |
| --- | --- | --- | --- | --- | --- |
| 第一代 | 提示词工程 | 一次请求，一次响应 | 会按要求组织语言 | 无 | 答得不对、格式不稳 |
| 第二代 | 函数调用（tool calling / function calling） | 模型输出结构化的调用请求，你的代码负责执行 | 能触发副作用、能取外部数据 | 参数校验、结果回填 | 该调不调、参数错、结果塞不回去 |
| 第三代 | Agent 循环（agent loop） | 模型调用、工具执行、结果回填组成一个循环，直到模型给出最终答案 | 能自己把多步任务做完 | 停止条件、预算、错误恢复、可观测 | 循环不收敛、超轮次、成本失控 |

关键差别只有一句：**前两代是无状态的一次调用，第三代是有状态的循环。**

一旦你写下那个 `while`，就同时接手了四件麻烦事：什么时候停、出错怎么办、花了多少钱、出了事怎么复盘。Agents SDK 存在的理由，就是把这四件事从你的业务代码里拿走。

> 提示：判断一个需求是不是"真 Agent"，不要看它用了多少次模型，而要看**是否允许模型自己决定下一步做什么**。如果流程是你写死的三步调用，那它是一个工作流，用不用 SDK 都可以。

## 二、Agent 的最小定义：四个部件

抛开所有框架，一个 Agent 就是模型、指令、工具、循环四样东西的组合，四个部件各管一件事，缺一件就少一层能力。

| 部件 | 决定什么 |
| --- | --- |
| 模型 | 决定"能不能想明白" |
| 指令 | 决定"以什么身份、什么格式、什么边界说话" |
| 工具 | 决定"能不能碰到真实世界" |
| 循环 | 决定"能不能自己把一件事做完" |

验证什么：下面这段代码把上面的定义压到最小，它是本章唯一需要跑的东西——没有一行循环代码，却已经发生了循环。跑之前先把第 2 章的环境装好，那章有逐步命令和四项配置的完整对照表。

```python
import asyncio

from agents import Agent, Runner


agent = Agent(
    name="历史老师",
    instructions="你回答历史问题时，先给结论，再给两条依据。",
)


async def main() -> None:
    result = await Runner.run(agent, "罗马帝国是什么时候灭亡的？")
    print(result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

把它存成 `agent_basics.py`，放在 SDK 根目录 `openai-agents-python/` 下。运行命令如下：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python agent_basics.py
```

预期结果：一段先给结论、再给两条依据的历史回答，打印完程序就结束。

- `Agent` 只是声明，构造它不发任何网络请求。四个部件里它只填了两个（指令、模型默认值）。
- `Runner.run` 才是发动机：它持有循环、调用模型、判定"这算不算最终答案"。
- 因为没有 `tools`，模型第一轮就只能给文本，循环跑一轮就结束。
- `final_output` 的类型跟着 Agent 走：没有 `output_type` 时是 `str`（第 20 章讲结构化输出）。

把四个部件映射到 SDK 字段，缺哪个会怎样，一张表就够：

| 部件 | SDK 里的位置 | 缺了它的后果 |
| --- | --- | --- |
| 模型 | `Agent.model`（默认取 `get_default_model()`，当前为 `gpt-5.6-luna`，可用 `OPENAI_DEFAULT_MODEL` 覆盖） | 用默认模型，通常能跑，但成本与能力不可控 |
| 指令 | `Agent.instructions`（可以是字符串，也可以是函数） | 能跑，但行为完全靠模型自由发挥 |
| 工具 | `Agent.tools`、`Agent.mcp_servers` | 只能"说"，不能"做"，永远一轮结束 |
| 循环 | `Runner`（无需你声明） | 它一直在跑，由 `max_turns` 兜底 |

> 注意：循环不是可选件。你不显式配置它，它也一直在跑；区别只是你**知不知道**它跑了几轮、为什么停。

### 跑通本章示例要配什么

第 2 章已把运行环境装好；这里只列本章示例和坑里会碰到的配置，逐项说清漏了或设错会怎样。

| 配置项 | 怎么设 | 漏了 / 设错会报什么错 |
| --- | --- | --- |
| API Key | `OPENAI_API_KEY`，或把网关签发的 key 传进 `AsyncOpenAI(api_key=...)` | 找不到凭据，鉴权失败（401）；只设环境变量却传了不带 key 的 client，同样失败 |
| base URL | `OPENAI_BASE_URL`，或 `AsyncOpenAI(base_url=...)`；网关场景必设 | 请求发到官方 `api.openai.com`，网关 key 被拒或连接失败；只设环境变量、不改 client 也不生效 |
| 模型名 | `Agent.model` 或 `OPENAI_DEFAULT_MODEL`，默认是 `gpt-5.6-luna` | 网关没这个模型时返回 `model not found`；官方场景可以不设 |
| API 形态 | `set_default_openai_api("chat_completions")`，默认是 Responses API | 兼容网关多只实现 Chat Completions，漏设会返回 404 或"接口不支持" |
| `max_turns` | 传给 `Runner.run`，默认 10 | 不设不会立刻报错，但工具反复失败会驱动模型反复重试，轮次和账单同时失控 |
| `model_settings` | `Agent(model_settings=ModelSettings(temperature=0.2))` | 把 `temperature` 直接写进 `Agent(...)` 会报 `TypeError`；模型侧参数必须走 `model_settings` |

一条贯穿全章的规则：这些配置都必须在**第一次模型调用之前**生效，因为 SDK 惰性解析配置（`repo/docs/config.md`）。要按官方或网关场景逐步配齐，回到第 2 章照那张表走一遍即可。

## 三、三个原语：Agents、Handoffs、Guardrails

SDK 只提供三个原语，各管一段职责，代价也各不相同（`repo/docs/index.md`）。

| 原语 | 解决什么 | SDK 入口 | 边界与代价 |
| --- | --- | --- | --- |
| Agents | 一个执行单元：模型 + 指令 + 工具 | `Agent` | 单 Agent 的能力上限就是它的工具集与指令质量 |
| Agents as tools / Handoffs | 多个执行单元之间"谁接手、谁保留控制权" | `agent.as_tool(...)`、`handoffs=[...]` | 交接（handoff）会改变后续轮次的执行者；两种模式的控制权归属完全不同（第 11、12 章展开） |
| Guardrails | 对输入输出做"不合格就熔断"，即护栏（guardrail） | `input_guardrails`、`output_guardrails` | 输入护栏只在链条的第一个 Agent 上跑（源码注释原文：Only the first agent's input guardrails are run） |

三者之外，还有一件"不是原语但默认开着"的东西：追踪（tracing）。它不参与业务逻辑，却决定了你出问题时有没有现场可看（第 22 章）。

这里要建立一个重要直觉：**这三个原语是"声明"，不是"执行"。** 你写 `handoffs=[退款专员]`，只是在告诉模型"你有这个选项"。模型会不会用、什么时候用，是运行时的事。这也解释了后面很多"我明明配了它却没用"的困惑。

## 四、SDK 与 Responses API 的分工

SDK 和 Responses API 不是二选一，而是分工关系；`repo/docs/index.md` 给了一张很干脆的分工表。很多人第一次接触会问：既然 Responses API 已经能带工具、能维护会话，为什么还要 SDK？

**直接使用 Responses API，当你：**

- 想自己拥有循环、工具分发和状态处理；
- 流程很短，主要目标就是"把模型这一次的回复拿回来"。

**使用 Agents SDK，当你：**

- 希望运行时替你管理轮次、工具执行、护栏、交接或会话；
- Agent 需要产出工件，或跨多个协同步骤工作；
- 需要真实工作区，或需要可恢复执行（沙盒 Agent）。

官方还特别补了一句，值得抄进你的技术选型文档：**你不需要全局二选一**。很多应用用 SDK 跑受管流程，同时在底层路径上直接调 Responses API。

一个实用的判断顺序：

| 问题 | 若答"是" | 若答"否" |
| --- | --- | --- |
| 模型需要自己决定调几次工具吗？ | 用 SDK | 继续问 |
| 需要护栏/交接/会话/追踪中的任意一个吗？ | 用 SDK | 继续问 |
| 只是一次补全、一次分类、一次摘要？ | 直接调 API | 用 SDK |

## 五、从 Swarm 到 Agents SDK

SDK 是 Swarm 的生产就绪升级版，官方定位只有一句话：它是"我们此前智能体实验项目 Swarm 的生产就绪升级版"（`repo/docs/index.md`）。这句话包含两层信息。

**继承的部分**：极少的原语、把"Agent"和"交接"当作一等公民、让模型自己决定何时把控制权交出去。这套思路在 Swarm 时代就被验证过：它足够表达复杂的协作关系，而不需要引入新的抽象层。

**补齐的部分**：Swarm 是个实验原型，生产环境需要的东西它没有。受管的运行循环、护栏、会话持久化、追踪、流式事件、重试与超时，以及沙盒/实时/语音这些子栈，都是后来补上的。你在 0.25.0 仓库里看到的 `run_internal/`、`memory/`、`tracing/`、`sandbox/`，基本都是"从原型到生产"这段路补出来的。

> 注意：Swarm 的代码不在本仓库内，本章只按官方定位讲它的历史角色，不复述它的实现细节。凡涉及行为的结论，一律以本仓库 0.25.0 源码为准。

## 六、什么时候不该用 SDK

框架的成本不是性能，而是**认知负担与耦合**；以下几种情况，直说"别用"更诚实。

| 场景 | 为什么别用 |
| --- | --- |
| 你只需要一次调用 | 分类、摘要、抽取、改写都是一次请求一次响应。SDK 的循环、结果对象、事件流全是负担。 |
| 你已经有一套编排层 | 团队已有工作流引擎、任务队列、状态机，再套一层 Agent 运行时，会得到两套"谁负责重试"的答案。 |
| 你要的确定性高于灵活性 | 模型自主决定下一步，意味着行为不可完全预测。合规审计要求"每一步都可预先枚举"的场景，工作流比 Agent 合适。 |
| 你的瓶颈不在编排 | 检索质量差、工具本身不稳、指令写得含糊，这些换框架都救不了。 |
| 你只是想要一个更好用的 HTTP 客户端 | 那就用官方 `openai` SDK。 |

反过来说，当你的痛点变成"我需要模型自己决定调几次工具、中间还要有人审、出问题要能回放"时，SDK 的抽象成本立刻值回票价。

## 七、一次单轮执行的时序（文字版）

一次"用户提问 → 得到答案"的单 Agent 单轮执行只有六个动作，这是本章最该记住的图。

```text
用户输入 "帮我查订单 A123 的状态"
   │
   ▼
[1] Runner 组装模型输入
      instructions（系统提示）
    + 历史对话
    + 本轮用户消息
    + 工具 schema 列表
   │
   ▼
[2] 调用模型（第 1 次）
   │
   ├── 模型返回：一个工具调用请求 get_order_status(order_id="A123")
   │        │
   │        ▼
   │   [3] Runner 执行工具（本地 Python 函数）
   │        │  产出：工具输出 "已发货，预计 3 天到达"
   │        ▼
   │   [4] 结果回填：把工具输出作为新的一条消息，追加进模型输入
   │        │
   │        ▼
   │   [5] 再次调用模型（第 2 次）
   │        │
   │        ▼
   └── 模型返回：纯文本 "订单 A123 已发货，预计 3 天到达。"
            │
            ▼
        [6] 判定：是文本、且没有工具调用 → 这是最终答案
            │
            ▼
        RunResult.final_output = "订单 A123 已发货……"
```

六个动作里有三个是你以后排查问题的抓手：

| 动作 | 为什么是抓手 |
| --- | --- |
| [1] 组装输入 | `call_model_input_filter` 可以在这里改写（第 18 章）。 |
| [3] 执行工具 | 这一步是**你的代码**在跑，异常、超时、审批都发生在这里（第 7、15 章）。 |
| [6] 判定停止 | 判定规则不是你写的，是 Runner 写的："产出期望类型的文本，且没有工具调用"。理解这条规则，能解释 80% 的"它为什么又调了一次"。 |

还有一条容易被忽略的时序细节：**输入护栏（input guardrails）默认与模型调用并行跑**。一旦触发 tripwire，整个 run 立刻中断。这是"fail fast"设计，也意味着护栏不是"先检查再执行"，而是"边执行边检查"（第 14 章）。

## 常见坑与排查

五条都按症状查，每条给出症状、原因和修法。

1. **症状**：写了一个很详细的 `instructions`，指望模型自己分多步完成，结果每次都只回一段话。
   **原因**：没有工具，模型没有任何"再来一轮"的理由；循环在第一轮就满足了停止条件。
   **修法**：要么给它工具，要么把任务拆成多次 `Runner.run`。

2. **症状**：在 `instructions` 里写"用户的余额在数据库 users 表里"，模型却开始编造数字。
   **原因**：context 与本地数据库对模型完全不可见，只有进入对话历史的内容它才看得到。
   **修法**：用工具按需取数，或把数据拼进动态 instructions（第 6 章）。

3. **症状**：一次 run 跑了几十秒、账单突然变高。
   **原因**：`max_turns` 默认是 10，工具反复失败会驱动模型反复重试，每一轮都是一次完整计费调用。
   **修法**：显式设小 `max_turns`，给工具加护栏，并在 trace 里看轮次数（第 4、22 章）。

4. **症状**：把 Responses API 的原始请求参数直接塞进 `Agent(...)`，报 `TypeError`。
   **原因**：`Agent` 是声明式对象，构造函数只接受固定字段，模型侧参数要走 `model_settings`。
   **修法**：`Agent(model_settings=ModelSettings(temperature=0.2))`，而不是 `Agent(temperature=0.2)`。

5. **症状**：以为 SDK 会自动选 Chat Completions 或 Responses。
   **原因**：默认走 Responses API，但可以用 `set_default_openai_api("chat_completions")` 改。
   **修法**：在项目初始化处显式声明，并记进 README。否则换个人接手就会踩到行为差异。

## 动手练习

三题按"先拆解、再跑通改坏、最后改仓库示例"的顺序做，第 2 题是本章的动手主线。

1. **拆解一个你熟悉的产品**：挑一个号称"AI 助手"的产品，用"模型 + 指令 + 工具 + 循环"四栏写下来。哪一栏是空的？它还能被称为 Agent 吗？

2. **跑通并改坏**：把上面的历史老师例子存成 `agent_basics.py`，放进 SDK 根目录再运行。若你把仓库 clone 到了别处（比如目录就直接叫 `repo`），按自己的目录替换下面这行路径即可。预期结果是一段两句式的历史回答；改坏之后，输出会明显变短。

   验证什么：确认脚本能在你自己的环境里跑起来。

   ```bash
   # 工作目录：openai-agents-python/（SDK 根目录）
   cd openai-agents-python
   python agent_basics.py
   ```

   预期结果：打印出那段历史回答。跑通后做两件事：把 `instructions` 换成"只用一句话回答"，观察输出长度；再把 `instructions` 整个删掉，观察行为退化。

3. **改仓库示例**：打开 `repo/examples/basic/tools.py`，给 `get_weather` 加一个"城市名为空就抛 `ValueError`"的分支，然后故意问一个会触发它的输入。观察 `final_output` 长什么样，再想想：模型看到的是你的异常堆栈，还是别的什么？（提示：默认 `failure_error_function` 只返回一句固定文案，不泄露异常。）

## 本章小结

- LLM 应用三代：prompt（一次调用）→ tool calling（能动手）→ agent loop（能自己收尾）。
- Agent 的最小定义是四个部件：模型、指令、工具、循环；其中循环是唯一"你不用声明它也存在"的部件。
- SDK 的三个原语是 Agents、Agents as tools / Handoffs、Guardrails；它们是**声明**，执行发生在运行时。
- SDK 与 Responses API 不是二选一：受管流程用 SDK，底层单次调用直接打 API。
- SDK 是 Swarm 的生产就绪升级：继承"少原语 + 模型自主交接"，补齐循环、护栏、会话、追踪、流式等生产件。
- 一次单轮执行的关键判定是"文本 + 无工具调用 = 最终答案"。
- 不该用 SDK 的典型场景：一次调用、已有编排层、需要预先枚举每一步。
