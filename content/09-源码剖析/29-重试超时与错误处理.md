# 第29章 重试超时与错误处理

第 28 章末尾那张异常表，只回答了"会抛什么"。这一章回答三个更实际的问题：**抛之前 SDK 试过几次、这个次数怎么改、兜不住时怎么优雅收场。**

本章解决的真实问题也很具体。凌晨三点上游 429 限流，你的 Agent 是安静地失败，还是把一次请求放大成五次、账单翻倍？以及"模型超时"和"工具超时"为什么是两套参数？

本章只走一条主线：拿一个"第三方库存 API 返回 429 加偶发连接重置"的场景，从"谁在重试"开始，写出策略、配上退避、划清安全边界、配好两个超时，最后用一个完整脚本验收。第七节的兜底处理器、第八节的异常表是主线末端两个工具，第九节的生产建议是收尾清单。按这章走完，你会得到一份可复制的重试配置、一条错误兜底路径、一组定位重试源码的命令。

## 学习目标

- 能说清 0.25 的两层重试：provider 内建重试与 runner 管理的重试，各自在什么时候生效。

## 一、两层重试：先搞清谁在重试

重试（retry）分两层，先搞清是谁在重试。

| 层 | 归谁 | 默认行为 | 你能改吗 |
| --- | --- | --- | --- |
| provider 内建 | 模型适配层 / 传输栈 | 对瞬时网络错误、部分 5xx 有隐式重试 | 间接：配了 `retry` 后 SDK 会按规则**关掉**它，避免双层叠加 |
| runner 管理 | `run_internal/model_retry.py` | **完全不重试**，必须 opt-in | 是：`ModelSettings(retry=ModelRetrySettings(...))` |

0.25 的核心立场是一句话：**通用模型请求默认不重试**。你不配 `retry`，SDK 就只做它一直以来那点传输层兜底，不会偷偷帮你重放。

这跟你用过的很多 HTTP 客户端直觉相反，但它是正确的。LLM 请求往往带副作用（工具调用、服务端会话状态），无脑重放比失败更贵。

还有一条隐含规则。一旦 `retry` 生效，runner 会**主动抑制 provider 的隐藏重试**（`_should_disable_provider_managed_retries`），否则一次失败可能变成 3×4=12 次请求。同时 `max_retries=0` 也是"彻底关掉一切重试"的开关。

下面这条命令验证这两个开关确实存在于源码中，为主线后面的配置提供依据。

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
grep -n "_should_disable_provider_managed_retries\|max_retries" src/agents/run_internal/model_retry.py | head -20
```

预期看到什么：抑制 provider 隐藏重试的判断函数与 `max_retries` 的取值分支同时出现，说明"配了 `retry` 就不再叠两层"是源码里的真实逻辑。

## 二、三个类型：Policy / Context / Decision

`retry.py` 里只有三个核心类型，读懂它们就能读懂全部重试行为。

先看 `repo/src/agents/retry.py` 里的类型别名原文，验证重试策略的签名到底是什么。

```python
# agents/retry.py 里的类型别名（原样）
RetryPolicy: TypeAlias = Callable[[RetryPolicyContext], MaybeAwaitable[bool | RetryDecision]]
```

预期结果：`RetryPolicy` 就是一个回调，输入 `RetryPolicyContext`，返回 `bool` 或 `RetryDecision`。

在源码里确认这一行，用这条命令：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
grep -n "RetryPolicy: TypeAlias" src/agents/retry.py
```

预期看到什么：回显的类型别名与上面摘录一致，证明这不是课程自造的写法。

下面是一个能跑的最小策略。注意它拿到的是**事实**，不是异常对象。这是片段，不是完整脚本：它是一个 `policy` 回调，最终通过 `ModelRetrySettings(policy=...)` 嵌进第十节的完整脚本。

```python
from agents import RetryDecision, RetryPolicyContext


def retry_on_overload(context: RetryPolicyContext) -> bool | RetryDecision:
    if context.normalized.status_code in (429, 503) and not context.stateful_request:
        return RetryDecision(retry=True, reason="upstream overload")
    return False
```

预期结果：429 或 503 且非 stateful 的请求返回 `RetryDecision(retry=True, ...)`，其余一律返回 `False`。

`RetryPolicyContext` 给你的字段，都是**策略运行前就固定**的事实，不是让你去猜。

| 字段 | 用途 |
| --- | --- |
| `error` | 原始异常，需要时自己 `isinstance` |
| `attempt` / `max_retries` | 当前第几次、上限多少，用它做"只重试前两次"这类策略 |
| `stream` | 流式还是非流式，直接影响能不能重放 |
| `normalized` | 归一化事实：`status_code`、`error_code`、`retry_after`、`is_timeout`、`is_network_error`、`is_abort` |
| `provider_advice` | provider 的原始建议（是否建议重试、建议延迟、原因） |
| `response_started` | 失败时响应是否已经开始喷数据 |
| `replay_safety` | `"safe" / "unsafe" / "unknown"` |
| `stateful_request` | 请求是否带 `previous_response_id` 或 `conversation_id` |

返回值有两种形态：`bool`（够用了）或 `RetryDecision`（要指定延迟、写原因、或显式批准一次不安全重放）。

`RetryDecision` 的字段定义摘自 `repo/src/agents/retry.py`，先用 grep 把它调出来核对字段。

```python
@dataclass
class RetryDecision:
    retry: bool
    delay: float | None = None
    reason: str | None = None
    approve_unsafe_replay: bool = False   # 显式批准"provider 说不安全"的重放
```

预期结果：除了 `retry`，其余字段都有默认值，写决策时可以只传你关心的那几项。

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
grep -n -A 12 "class RetryDecision" src/agents/retry.py
```

预期看到什么：四个字段 `retry`、`delay`、`reason`、`approve_unsafe_replay` 与上面摘录一致，且后三个都带默认值。

> 注意：`approve_unsafe_replay` 与 `retry=True` 是两件事。普通的 `RetryDecision(retry=True)` **永远**不会绕过重放保护；只有这个字段为真、且场景是"非流式 + 无本地副作用"时才可能放行。

## 三、ModelRetrySettings 与 backoff

先看一个完整配置示例，把重试次数、退避（backoff）、策略一次写全。这是片段，不是完整脚本：它只负责造出 `agent`，最终嵌进第十节的完整脚本里运行。

```python
from agents import Agent, ModelRetrySettings, ModelSettings, retry_policies

agent = Agent(
    name="客服助手",
    model_settings=ModelSettings(
        retry=ModelRetrySettings(
            max_retries=4,
            backoff={"initial_delay": 0.5, "max_delay": 5.0, "multiplier": 2.0, "jitter": True},
            policy=retry_policies.any(
                retry_policies.provider_suggested(),
                retry_policies.retry_after(),
                retry_policies.network_error(),
                retry_policies.http_status([408, 409, 429, 500, 502, 503, 504]),
            ),
        )
    ),
)
```

预期结果：`max_retries=4` 表示最多 5 次总尝试，`policy` 用 `any()` 合并四个判定器。

三个字段的语义：

- `max_retries`：**初始请求之后**还能重试几次。`4` 表示最多 5 次总尝试。
- `backoff`：只在策略"重试但没给延迟"时用作默认退避。`max_delay` 只封顶这个计算值，**不封顶**策略显式返回的延迟，也不封顶 `retry_after` 提示。
- `policy`：运行时回调，**不参与序列化**（`to_json_dict()` 只输出前两个字段）。

**配置写在哪很重要。** `retry` 在 runner 级（`RunConfig.model_settings`）与 agent 级（`agent.model_settings`）之间是**深合并**。Agent 只覆盖 `retry.max_retries` 时，仍会继承 runner 的 `policy`；只覆盖 `backoff.max_delay` 时，其余退避字段从上向下继承。这让"全局策略 + 单 Agent 调参"成为可能。

## 四、retry_policies：现成的判定器

`retry_policies` 提供了一批现成判定器，可以直接组合。

| 助手 | 什么时候返回真 | 注意 |
| --- | --- | --- |
| `never()` | 永不 | 显式 opt-out |
| `provider_suggested()` | provider 建议重试时 | **最安全的起点**，因为它保留 provider 的否决与重放安全标记 |
| `network_error()` | `is_network_error` 或 `is_timeout` | 模型超时也走这里 |
| `retry_after()` | 有 `retry_after` 提示时 | 用提示值作为延迟，退避不封顶 |
| `http_status([...])` | 状态码命中列表 | 429/5xx 的常用组合 |
| `any(...)` | 任一为真 | 合并延迟与原因；硬否决优先 |
| `all(...)` | 全部为真 | 用于"必须同时满足"的严格场景 |

组合时要懂得取舍。`any()` 里如果某个子策略给出**硬否决**（比如 provider 明确说不该重试），它会压过其他子策略的"重试"。这就是为什么"无脑 `any(network_error(), http_status([500]))`"在 stateful 请求上仍然可能不重试：第二道闸（第五节）还没到它。

## 五、安全边界：这几种情况绝不重试

有些情况绝不重试，策略写得再激进也绕不过。`_evaluate_retry` 会在调用你的策略**之前**，先做下面几道判断。

| 绝不重试的情况 | 判定依据 | 说明 |
| --- | --- | --- |
| abort 类错误 | `normalized.is_abort` | 用户主动中止，重试没有意义。 |
| 流式已喷出用户可见内容 | `emitted_retry_unsafe_event` | 重放会让用户看到重复的开头。 |
| 本地副作用否决 | `replay_unsafe_request`（例如 Programmatic Tool Calling） | 本地可能已经执行过，这是策略批准 `approve_unsafe_replay` **也不能**解除的。 |
| stateful 请求默认 fail-closed | 带 `previous_response_id` / `conversation_id` | 请求依赖服务端状态，重放安全性未知时一律不重试。想放行必须有 provider 的 `replay_safety="safe"`（通常来自 `provider_suggested()`），或对"provider 标记 unsafe 的非流式失败"显式 `approve_unsafe_replay=True`。 |
| provider 标记 unsafe | provider 的 safety 标记 | 默认拦截，只有上面那条显式批准能放行。 |

> 提示：判断"我这个请求能不能安全重试"，看 `context.stateful_request` 与 `context.replay_safety` 两个字段就够了。别去猜异常类型。

## 六、超时：模型与工具是两套

模型超时和工具超时是两套参数，别混。先看模型超时，它用 `ModelSettings.timeout`，正数、单位秒。这是片段：只改 `ModelSettings`，其余配置沿用主线脚本。

```python
agent = Agent(name="助理", model_settings=ModelSettings(timeout=30.0))
```

预期结果：任何一次模型尝试超过 30 秒，都会抛 `ModelTimeoutError`。

它约束的是**单次模型尝试**，覆盖传输等待，但不约束整个 run、不约束工具、也不约束退避等待。超时后 SDK 会先取消并等清理完成，再抛 `ModelTimeoutError`（带 `timeout_seconds`）。启用重试时，这个错误会以 `normalized.is_timeout = True` 交给策略，因此 `retry_policies.network_error()` 能匹配到；**每次重试都重新计时**。

工具超时用装饰器参数配置。字段名有两套，要小心：

| 位置 | 参数名 | 说明 |
| --- | --- | --- |
| `@tool(...)` / `function_tool(...)` | `timeout` | 装饰器参数 |
| `FunctionTool` 数据类 | `timeout_seconds` | 字段名，别混 |

用法是这样，装饰器的参数名与数据类字段名并不一样。这也是片段：`fetch_from_erp` 是你自己的 ERP 客户端函数，需在你项目里定义；完整可运行版本见第十节。

```python
from agents.decorators import tool

@tool(timeout=8.0, timeout_behavior="error_as_result")
def query_inventory(sku: str) -> str:
    """查询库存。超时会被转成一句模型可见的错误文本。"""
    return fetch_from_erp(sku)
```

预期结果：`query_inventory` 超过 8 秒时，超时会被转成一句模型可见的错误文本。

`timeout_behavior` 只有两个值：`"error_as_result"`（默认，返回模型可见的超时说明，模型可以换个说法继续）和 `"raise_exception"`（抛 `ToolTimeoutError`，整轮失败）。想在默认模式下改文案，传 `timeout_error_function`。

这个默认值的选择很讲究：**工具超时通常不该炸掉整轮对话**，让模型知道"查不到"往往比中断更好。

## 七、RunErrorHandlers：兜底而不吞错

错误处理器（error handler）`error_handlers` 是兜底手段，它兜住错误，但不会吞掉错误。它是 `Runner` 所有入口都接受的字典，只有三个键。

| 键 | 捕获 | 典型用法 |
| --- | --- | --- |
| `max_turns` | `MaxTurnsExceeded` | 返回"本次没查完，请缩小范围" |
| `model_refusal` | `ModelRefusalError` | 返回业务化的拒答话术 |
| `invalid_final_output` | `ModelBehaviorError`（结构化输出校验失败） | 返回兜底对象 |

下面是一个完整脚本，验证 `max_turns` 兜底输出能替代异常抛出。它需要先按第 2 章配好 key 与模型；存成 `error_handler_demo.py`，放在 SDK 根目录 `openai-agents-python/` 下。

```python
from agents import Agent, RunErrorHandlerInput, RunErrorHandlerResult, Runner


def on_max_turns(data: RunErrorHandlerInput[None]) -> RunErrorHandlerResult:
    return RunErrorHandlerResult(
        final_output="这次没能查完，请把问题缩小一点再问。",
        include_in_history=False,
    )


def main():
    agent = Agent(name="助理", instructions="逐条分析合同。")
    result = Runner.run_sync(
        agent,
        "分析这份长合同",
        max_turns=3,
        error_handlers={"max_turns": on_max_turns},
    )
    print(result.final_output)


if __name__ == "__main__":
    main()
```

运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python error_handler_demo.py
```

预期结果：回合数耗尽时不再抛 `MaxTurnsExceeded`，而是打印 handler 给出的兜底文案"这次没能查完，请把问题缩小一点再问。"

三个细节：

- `include_in_history` 默认 `True`，即兜底输出会写进历史与 session；不想污染上下文就设 `False`。
- `invalid_final_output` 的返回值会**再被同一套 `output_type` 校验一次**，所以类型必须对。
- 它**不会重试模型、也不会重放工具副作用**。它是"体面收场"，不是"再来一次"。

## 八、异常体系表

`exceptions.py` 里的全部异常，都继承 `AgentsException`。这个基类带一个 `run_data: RunErrorDetails | None` 槽位。

| 异常 | 触发点 | 关键属性 |
| --- | --- | --- |
| `AgentsException` | 基类 | `run_data` |
| `MaxTurnsExceeded` | 回合数超限 | `message` |
| `ModelBehaviorError` | 模型行为异常（调不存在的工具、JSON 坏了、结构化输出校验失败） | `message` |
| `ModelRefusalError` | 模型拒答 | `refusal` |
| `ModelTimeoutError` | 单次模型尝试超时 | `timeout_seconds` |
| `ToolTimeoutError` | 工具调用超时且 `timeout_behavior="raise_exception"` | `tool_name`、`timeout_seconds` |
| `UserError` | 用法错误（参数不合法、配置冲突） | `message` |
| `MCPToolCancellationError` | MCP 工具被内部取消 | `message` |
| `InputGuardrailTripwireTriggered` | 输入护栏命中 | `guardrail_result` |
| `OutputGuardrailTripwireTriggered` | 输出护栏命中 | `guardrail_result` |
| `ToolInputGuardrailTripwireTriggered` | 工具输入护栏命中 | `guardrail`、`output` |
| `ToolOutputGuardrailTripwireTriggered` | 工具输出护栏命中 | `guardrail`、`output` |
| `RunErrorDetails`（非异常，dataclass） | 挂在异常上 | `input`、`new_items`、`raw_responses`、`last_agent`、各护栏结果 |

语音侧还有一个 `STTWebsocketConnectionError`（`voice/exceptions.py`，同样继承 `AgentsException`）。

排查时最有用的一条：**捕获 `AgentsException` 之后先看 `e.run_data`**。它不是所有异常都填，只有经过 run 循环包装的才有。但一旦有，里面就是"失败那一刻的完整现场"，比 traceback 更能说明问题。

## 九、生产建议

1. **重试必须幂等（idempotent）。** 重试一个"扣款""发邮件""提交工单"的工具，等于重复副作用。把自己的工具分成"只读"和"有副作用"两类，只对只读的允许重试，有副作用的一律走审批或幂等键。
2. **降级优于重试。** 主模型 429 连续三次，继续等不如切备用模型（换 `RunConfig.model_provider` 或换 Agent 的 `model`），或者直接返回兜底话术。
3. **熔断要放在 Agent 外面。** SDK 没有熔断器；在工具层或模型 provider 外包一层"连续 N 次失败就短路"的开关，比在策略里数 `attempt` 更可靠。
4. **可观测性三件套**：给 trace 加 `workflow_name` / `group_id` 以便按会话聚合；用 `on_llm_start` 记录每次尝试；把 `RetryDecision.reason` 打进日志，它就是为了这个字段存在的。
5. **超时要分层。** 模型 30s、工具 8s、整个 HTTP 请求 45s、上游网关 60s，层层递减才不会出现"外层已经超时、内层还在烧 token"。
6. **别用 `except Exception` 包 `Runner.run`。** 你在 3.8+ 抓不到 `CancelledError`，会漏掉取消；用 `except AgentsException` 抓业务失败，其余让它上抛。

## 十、配置示例：外部 API 限流重试

场景：你的工具要调一个第三方库存 API，它会返回 429 并带 `Retry-After`，偶发连接重置。要求：最多重试 3 次、指数退避带抖动、记录每次决策。

下面是一个完整脚本，把主线到这里的所有配置装在一起。它验证的是"429 按提示延迟、5xx 走退避、业务侧只放行前两次"三件事。存成 `retry_inventory.py`，放在 SDK 根目录 `openai-agents-python/` 下；需先按第 2 章配好 key 与模型。脚本里用 `_ThirdPartyClient` 作演示替身，真实项目换成你的 HTTP 客户端即可。

```python
import asyncio

from agents import Agent, ModelRetrySettings, ModelSettings, RetryDecision, Runner, retry_policies
from agents.decorators import tool


class _ThirdPartyClient:
    """演示替身：真实项目里换成你的 HTTP 客户端。"""

    def get(self, path: str) -> str:
        return f"stub stock for {path}"


third_party_client = _ThirdPartyClient()


def log_decision(context) -> None:
    print(
        f"[retry] attempt={context.attempt}/{context.max_retries} "
        f"timeout={context.normalized.is_timeout} "
        f"status={context.normalized.status_code} "
        f"replay_safety={context.replay_safety} "
        f"stateful={context.stateful_request}"
    )


base_policy = retry_policies.any(
    retry_policies.provider_suggested(),
    retry_policies.retry_after(),
    retry_policies.network_error(),
    retry_policies.http_status([408, 429, 500, 502, 503, 504]),
)


async def policy(context) -> bool | RetryDecision:
    decision = base_policy(context)
    if asyncio.iscoroutine(decision):
        decision = await decision
    log_decision(context)
    if not decision:
        return False
    if isinstance(decision, RetryDecision) and decision.retry:
        # 业务侧额外约束：只在前两次尝试上放行，避免把一次抖动放大成雪崩
        if context.attempt > 2:
            return RetryDecision(retry=False, reason="attempt budget exhausted")
    return decision


@tool(timeout=8.0, timeout_behavior="error_as_result")
def query_inventory(sku: str) -> str:
    """查询第三方库存。幂等只读，允许重试。"""
    return third_party_client.get(f"/stock/{sku}")


agent = Agent(
    name="库存助手",
    instructions="回答库存问题；查不到就说查不到，不要编。",
    tools=[query_inventory],
    model_settings=ModelSettings(
        timeout=20.0,
        retry=ModelRetrySettings(
            max_retries=3,
            backoff={
                "initial_delay": 0.5,
                "max_delay": 6.0,
                "multiplier": 2.0,
                "jitter": True,
            },
            policy=policy,
        ),
    ),
)


async def main():
    result = await Runner.run(agent, "查一下 SKU-100 的库存")
    print(result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

运行它：

```bash
# 工作目录：openai-agents-python/（SDK 根目录）
python retry_inventory.py
```

预期结果：正常情况打印库存答复；把 `base_url` 指向会返回 429/503 的网关（见第 2 章）后，会看到 `[retry] attempt=...` 逐次递增，429 按 `Retry-After` 延迟、5xx 走指数退避，业务侧在第 3 次尝试给出 `attempt budget exhausted`。

四个要点：

- `provider_suggested()` 放第一位。它既能在 provider 说"该重试"时给绿灯，也能在 provider 说"不安全"时投否决票。
- `retry_after()` 让 429 的提示真正生效，而不是死等你的退避曲线。
- 业务侧的 `attempt > 2` 是**第二道保险**：SDK 的 `max_retries` 管总量，你的策略管"业务能忍受几次失败"。
- 工具超时用 `error_as_result`，模型超时用 `ModelSettings.timeout`，两者互不覆盖。

本章总验收点：跑通脚本之后，再用 grep 确认"安全边界先于策略"这件事在源码里成立。

```bash

grep -n "def _evaluate_retry" src/agents/run_internal/model_retry.py
grep -n "stateful_request\|approve_unsafe_replay" src/agents/retry.py | head -20
```

预期看到什么：`_evaluate_retry` 的定义，以及 `stateful_request`、`approve_unsafe_replay` 两个闸门字段。能看到它们，就说明你已把主线从配置一路追到了源码。

## 常见坑与排查

按症状查，每条都给出"症状 → 原因 → 修法"。

1. **配了 `policy` 却完全不重试**
   原因：请求是 stateful 的（带了 `conversation_id`），而策略里没有能给出 `replay_safety="safe"` 的 `provider_suggested()`。修法：加上它，或对非流式失败显式 `approve_unsafe_replay=True`。

2. **重试次数是预期的好几倍**
   原因：provider 隐藏重试没被抑制（例如手写 provider 没走规范路径），或你在策略外层又包了一层自己的 `for` 循环。修法：只留一层；用 `max_retries=0` 验证是不是 provider 在偷偷重试。

3. **`ModelTimeoutError` 与 `ToolTimeoutError` 抓混了**
   原因：一个来自 `ModelSettings.timeout`，一个来自 `@tool(timeout=...)`。修法：分别 `except`；排查时先打 `type(exc).__name__`。

4. **工具超时后整轮崩了**
   原因：`timeout_behavior` 被设成 `"raise_exception"`。修法：一般场景保持默认 `"error_as_result"`，让模型自己消化。

5. **`error_handlers` 没生效**
   原因：`invalid_final_output` 的返回值不符合 `output_type`，二次校验又失败了。修法：返回与 `output_type` 完全一致的对象；或先 `assert isinstance(...)` 确认异常类型。

6. **`asyncio.CancelledError` 被当成普通错误**
   原因：在工具或 hook 里写了 `except Exception` 抓不到它就以为没问题，或写了 `except BaseException` 把它吞了。修法：让取消上抛；收尾放 `finally`，别在 `finally` 里长时间 `await`。

## 本章小结

- 0.25 的通用模型重试是 **opt-in**：不配 `ModelSettings(retry=...)` 就不重试，配了会抑制 provider 隐藏重试。
- 三个类型：`RetryPolicy`（回调）、`RetryPolicyContext`（事实）、`RetryDecision`（带延迟/原因/不安全感批准）。
- 退避只在策略没给延迟时生效；`retry_after` 与显式延迟不受 `max_delay` 约束。
- 安全边界优先于策略：abort、已喷流、本地副作用、stateful 未知、provider 标记 unsafe 都会先被拦。
- 模型超时用 `ModelSettings.timeout` 抛 `ModelTimeoutError`；工具超时用 `@tool(timeout=...)`，默认降级为模型可见文本。
- `error_handlers` 只有三个键，负责"体面收场"，不负责重试。
- 生产上把重试限制在幂等操作，降级与熔断放在 SDK 之外，并把 `RetryDecision.reason` 打进日志。
