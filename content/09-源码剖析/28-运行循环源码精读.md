# 第28章 运行循环源码精读

第 27 章给了地图，这一章走主干道：**一次 `Runner.run` 到底按什么顺序发生了什么**。

本章盯住三个真实问题。为什么我的 handoff 没生效？为什么 `max_turns` 比我预期更早用完？为什么工具抛异常后，有些输出还是进了历史？

这三个问题的答案，都在同一段代码里。

---

## 学习目标

- 能说出 `Runner.run` → `AgentRunner.run` → `run_single_turn` 这条调用链上每一层各加了多少"料"。
- 能按顺序复述一回合的七个阶段（准备 / 调模型 / 规划 / 执行 / 审批 / 结算 / 推流），并指出每个阶段对应哪个模块。
- 能读懂 `set(items)` 三个列表（`generated_items`、`session_items`、`model_responses`）为什么就是全部状态。
- 能判断"这一回合算不算新 turn"，并解释 handoff 为什么也吃 `max_turns`。
- 能画出一张异常传播图：工具失败、模型超时、护栏命中、外部取消分别在哪里被接住。

---

## 一、入口到循环：三层套娃

`Runner` 本身几乎不干活。`Runner.run` 只做两件事。第一，把参数转交给 `DEFAULT_AGENT_RUNNER`；第二，当 `BaseException` 是"已脱敏错误"时，做一次轨迹清理再重抛。真正的实现是 `AgentRunner.run`（`run.py` 第 574 行起）。

先看调用层次。下面这张图把从入口到循环的嵌套关系画了出来。

```text
Runner.run(...)                      # run.py:281  门面 + 脱敏兜底
  └─ DEFAULT_AGENT_RUNNER.run(...)   # run.py:574  本体：准备状态、trace、session
       └─ while True:                # run.py:1032 主循环，每圈 = 一个 turn
            ├─ run_single_turn(...)  # run_loop.py:2821  非流式
            └─ run_single_turn_streamed(...)  # run_loop.py:2422  流式
```

预期结果：三条缩进对应三层，`while True` 每转一圈就是一个 turn。

`DEFAULT_AGENT_RUNNER` 可以被 `set_default_agent_runner()` 替换，但那个函数自己标着"实验性、不属于公开 API"。把它当成"读源码时的锚点"就好，别在产品代码里替换它。

流式版本 `run_single_turn_streamed` 与非流式共用同一套阶段，差别只在两处。模型侧用 `stream_response_with_retry` 逐事件消费；每产出一批 `RunItem` 就立刻 `stream_step_result_to_queue` 推进事件队列。

所以你看到的事件顺序，就是回合内部的真实发生顺序，而不是"跑完再统一发"。

主循环 `while True` 里的顺序值得背下来。先校验输出护栏配置，首轮再跑输入护栏（顺序护栏先跑，并行护栏与模型调用同时跑），然后交给沙箱准备。接着起 `agent_span`，`current_turn += 1` 并检查 `max_turns`，再调 `run_single_turn`，最后按 `next_step` 分支。

**注意 `current_turn` 是在调模型之前自增的**。所以第 1 个回合的 `current_turn == 1`，而 `max_turns` 的比较也是"大于"而不是"大于等于"。

## 二、一回合的七个阶段

一回合可以切成七个阶段，每个阶段都对应一个明确的模块。

| 阶段 | 模块 | 关键函数 | 产出 |
| --- | --- | --- | --- |
| ① 回合准备 | `run_internal/turn_preparation.py` | `get_all_tools`、`get_handoffs`、`get_output_schema`、`maybe_filter_model_input` | 工具表、handoff 表、系统提示、最终输入项 |
| ② 调模型 | `run_internal/model_retry.py` | `get_response_with_retry` / `stream_response_with_retry` | `ModelResponse` |
| ③ 工具规划 | `run_internal/turn_resolution.py` | `process_model_response` | `ProcessedResponse`（分类后的待执行清单） |
| ④ 执行 | `run_internal/tool_execution.py` + `tool_planning.py` | `execute_function_tool_calls`、`execute_approved_tools` | `ToolCallOutputItem` 等 |
| ⑤ 审批 | `run_internal/approvals.py` | `approvals_from_step`、`index_approval_items_by_call_id` | `ToolApprovalItem`（中断） |
| ⑥ 结算 | `run_internal/turn_resolution.py` | `execute_tools_and_side_effects` → `execute_handoffs` / `execute_final_output` | `SingleStepResult.next_step` |
| ⑦ 推流 | `run_internal/streaming.py` | `stream_step_result_to_queue` | `RunItemStreamEvent` |

"工具规划"这一步最容易被忽略，但它才是关键。`process_model_response` 把模型吐出的每一条原始输出**分类**，包括 `ToolRunFunction`、`ToolRunHandoff`、`ToolRunComputerAction`、`ToolRunMCPApprovalRequest` 等，全部塞进 `ProcessedResponse`。

之后的执行阶段完全靠这份清单干活，不再看原始响应。这就是为什么"模型调了一个不存在的工具"能被精确报成 `ModelBehaviorError`：分类阶段就对不上表了。

## 三、精读 A：`run_single_turn` 的准备段

这段代码摘自 `repo/src/agents/run_internal/run_loop.py` 第 2847-2896 行。为了聚焦主线，删掉了不影响主线的错误分支。

它验证的是：一个回合的准备段，按什么顺序把输入、工具、提示和 handoff 组装起来。

```python
    try:
        turn_input = ItemHelpers.input_to_new_input_list(original_input)   # ①
    except Exception:
        turn_input = []
    context_wrapper.turn_input = list(turn_input)                          # ②

    with guard_agent_tool_configuration(public_agent):                     # ③
        if should_run_agent_start_hooks:
            agent_hook_context = AgentHookContext(...)
            await gather_with_cancel(hooks.on_agent_start(...), ...)       # ④
        all_tools = await get_all_tools(execution_agent, context_wrapper)  # ⑤

    system_prompt, prompt_config = await gather_with_cancel(               # ⑥
        execution_agent.get_system_prompt(context_wrapper),
        execution_agent.get_prompt(context_wrapper),
    )
    handoffs = await get_handoffs(execution_agent, context_wrapper)        # ⑦
    output_schema = get_output_schema(execution_agent)                     # ⑧

    if server_conversation_tracker is not None:
        input = server_conversation_tracker.prepare_input(...)             # ⑨
    else:
        input = _prepare_turn_input_items(original_input, generated_items, ...)

    new_response = await get_new_response(                                 # ⑩
        bindings, system_prompt, input, output_schema, all_tools, handoffs, ...
    )
```

预期结果：标记 ① 到 ⑩ 正好对应下面逐行注解的十个动作，最后一行才真正发出模型请求。

逐行注解：

- ① `original_input` 是本回合的"基础输入"。首轮是你传的，handoff 之后是被 filter 改过的版本。这里把它规范化成 `list[dict]`。失败时退化成空列表而不抛错，因为这只是给 hooks 用的展示数据。
- ② 写进 `context_wrapper.turn_input`。这是 `AgentHookContext.turn_input` 的来源，也是 hooks 里能拿到"本回合输入"的原因。
- ③ `guard_agent_tool_configuration` 在本回合进、出各取一次 `agent.tools` 快照做比对（`register_agent_tool_configuration` + `snapshot_agent_tools`）。如果同一个 Agent 被多个 run 并发使用、工具表又被中途改过，它会在边界上抛 `UserError`。抛错时会提示"改用 `agent.clone(tools=[...])` 或基于上下文做工具开关"。它保护的是"本回合内工具表一致"这个前提，而不是禁止你改。
- ④ `should_run_agent_start_hooks` 只在"进入新 Agent"时为真，也就是首轮、或刚 handoff 完。所以 `on_agent_start` 不会每个 turn 都跑。
- ⑤ 注意参数是 `execution_agent`，不是 `public_agent`。沙箱场景下，工具要从克隆体上取。
- ⑥ 系统提示和 prompt 模板并发取，任何一方抛错就取消另一方（`gather_with_cancel`）。
- ⑦ handoff 列表在这一步求值，会跑 `is_enabled` 回调。所以"动态开关 handoff"是在**回合开始**生效，不是调用时。
- ⑧ 结构化输出 schema 决定后面怎么解析最终输出。
- ⑨ 服务端托管会话（`conversation_id` / `previous_response_id`）走另一条输入组装路径。服务端已经持有历史，只需要发增量。
- ⑩ 真正调模型，内部就是 `model_retry.get_response_with_retry`。

## 四、精读 B：结算优先级

拿到 `ProcessedResponse` 后，`execute_tools_and_side_effects` 按固定优先级决定 `next_step`。下面这段摘自 `turn_resolution.py` 第 1150-1201 行。

它验证的是：几种 `next_step` 谁先被判定、谁会被后置。

```python
    if interruptions:                                                  # ①
        return SingleStepResult(..., next_step=NextStepInterruption(interruptions=interruptions), ...)

    if run_handoffs := processed_response.handoffs:                     # ②
        return await execute_handoffs_call(...)

    tool_final_output = await _maybe_finalize_from_tool_results(...)    # ③
    if tool_final_output is not None:
        return tool_final_output

    if not processed_response.has_tools_or_approvals_to_run():          # ④
        ...  # 继续往下才轮到「模型文本即最终输出」与 NextStepFinalOutput
```

预期结果：①②③④ 从上到下依次短路，命中靠前的分支就不会再往下走。

优先级是**审批 > handoff > 工具决定最终输出 > 模型文本即最终输出 > 再来一轮**。下面四条要点。

- ① 有任何一个工具调用在等审批，整回合立刻中断：其他工具调用**不会**被偷偷执行。
- ② 多个 handoff 同时出现时只取第一个，其余的会被写成一条 `ToolCallOutputItem`，内容是 "Multiple handoffs detected, ignoring this one."。这就是"为什么我的 handoff 没生效"最常见的原因：模型一次调了俩。
- ③ `tool_use_behavior` 的三种形态（`run_llm_again` / `stop_on_first_tool` / `StopAtTools`）都在这一层生效：命中就以工具输出作为最终输出，不再问模型。
- ④ 判定"没有工具要跑"之后才可能是最终输出；但还要排除"只有工具活动、没有任何消息"的情况，否则会被误判成空回复。

## 五、items 就是全部状态

运行循环没有状态机对象。它的状态是三个列表 + 一个整数。

| 变量 | 含义 | 谁在写 |
| --- | --- | --- |
| `generated_items` | 本次 run 生成的所有 `RunItem`（发给模型的那份） | 每回合结算时 extend |
| `session_items` | 落进 session 的完整版本（可能比上面多，例如被 filter 掉的） | 同上，另加过滤逻辑 |
| `model_responses` | 每次模型调用的 `ModelResponse` | `append_model_response_if_new` |
| `current_turn` | 已完成的回合数 | 循环末尾自增 |

`SingleStepResult` 只是这三个列表的"本回合切片"。`pre_step_items`（之前）+ `new_step_items`（本回合）→ 循环把它们 extend 回大列表。

`RunState` 存的也是同样三个列表。所以断点恢复的本质，就是把三个列表和计数器读回来。

另一个容易忽略的细节是"写入时机"。items 是先算清楚，再在回合结算后统一写 session 的（`save_turn_items_if_needed`），而不是边跑边写。

这样做是为了让"一回合"成为一个可回滚的整体。如果这一回合的输出护栏命中了，SDK 可以把这一回合的写入整体丢弃（`discard_held_current_response`），历史里不会留下半截答案。

你在排查"为什么 trace 里有、session 里没有"时，就是撞上了这个设计。

> 提示：`generated_items` 与 `session_items` 分家是有意的。handoff 的 `input_filter` 会改写喂给模型的历史，但审计/UI 需要看到未过滤的版本。搞不清"为什么 `result.new_items` 比模型看到的少"，就来看这两个变量。

## 六、什么时候产生新 turn

只有 `NextStepRunAgain` 和 `NextStepHandoff` 会让循环转下一圈。

| next_step | 循环行为 | turn 是否 +1 |
| --- | --- | --- |
| `NextStepRunAgain` | `continue` | 是（下一圈开头自增） |
| `NextStepHandoff` | 换 `current_agent`、重置 `agent_span`、`continue` | 是 |
| `NextStepFinalOutput` | 跑输出护栏、存盘、返回 `RunResult` | 否 |
| `NextStepInterruption` | 打包中断结果返回（含 `interruptions`） | 否 |

所以"`max_turns` 是什么"的准确答案是：**模型调用轮数上限，handoff 也算一轮**。一个 `max_turns=3` 的分诊 Agent，如果第 2 轮 handoff 到专家，专家只剩 1 轮。

## 七、取消与异常：谁接、谁不接

先看一张异常归位表。每行是一种失败，标出它在哪产生、被谁接住、最后给你什么。

| 情况 | 在哪里产生 | 在哪里被接住 | 最终给到你的 |
| --- | --- | --- | --- |
| 模型调用超时 | `model_retry._await_model_attempt` | 重试策略（若启用）；否则上抛 | `ModelTimeoutError` |
| 工具超时 | `tool.py` 的 `asyncio.wait_for` | 按 `timeout_behavior` | 默认转成模型可见的错误文本；`raise_exception` 则抛 `ToolTimeoutError` |
| 模型行为异常 | 工具规划阶段 | 无人接 | `ModelBehaviorError` |
| 输入/输出护栏命中 | `guardrails.py` | 只记结果，不吞异常 | `InputGuardrailTripwireTriggered` 等 |
| 回合数超限 | 主循环 | `error_handlers["max_turns"]` 可接管 | 无 handler 时抛 `MaxTurnsExceeded` |
| 外部取消 | 你的 `task.cancel()` | **没人接** | `asyncio.CancelledError` 逐层上抛 |

还有一条容易被误解：**取消不是错误**。`asyncio.CancelledError` 在 3.8 之后继承自 `BaseException`，所以 `except Exception` 抓不到它。这是好事，意味着你不会"顺手"把取消吞掉。

但它也意味着：你在工具里写 `try/finally` 做清理时，清理代码里的 `await` 如果再次被取消，可能让整个收尾挂起。SDK 的处理方式是 `_await_cleanup` 这类"重复取消也要等完"的辅助函数，值得抄。

三条实现细节值得记住。

1. **并发用 `gather_with_cancel` 而不是 `gather`**：任何子任务失败会立即取消其余任务，避免"主任务已失败、后台还在烧 token"。
2. **工具的取消被特殊标记**（`preserve_tool_task_cancellation` / `_is_tool_local_cancellation`）：工具内部的取消不会污染整个 run 的取消语义，两者在类型上都是 `CancelledError`，只能靠标记区分。
3. **`finally` 里一定收尾**：`current_turn_span.finish(reset_current=True)`、`agent_span.finish()`、session 写入回滚。所以你看 trace 时失败的那一回合也有 span，只是带 `error`。

## 常见坑与排查

1. **`MaxTurnsExceeded` 比预期早**
   原因：handoff 也算 turn。修法：把 `max_turns` 按"handoff 深度 + 工具循环次数"估，不要只按对话轮数。

2. **两个 handoff 同时触发，只有一个生效**
   原因：`execute_handoffs` 只取 `run_handoffs[0]`，其余写成 "Multiple handoffs detected"。修法：从提示里约束"一次只转接一个"，或改用 agent-as-tool 由主 Agent 决定。

3. **`result.new_items` 里有模型没见过的东西**
   原因：`session_items` 与 `generated_items` 分家。修法：要"模型视角"看 `to_input_list()` / `RunResult._model_input_items`，要"审计视角"看 `new_items`。

4. **工具失败了但 run 正常结束**
   原因：默认 `failure_error_function` 把异常转成模型可见文本，模型自己圆回来了。修法：需要严格失败就配置 `failure_error_function=None` 或 `timeout_behavior="raise_exception"`。

5. **`asyncio.CancelledError` 被吞，task 永远不结束**
   原因：自己在工具或 hook 里写了 `except Exception` 却忘了 `CancelledError` 在 3.8+ 继承自 `BaseException`；或者反过来，用 `except BaseException` 吞掉后又 `await` 一个会挂起的东西。修法：让取消自然上抛，收尾逻辑放 `finally`。

6. **在 `on_tool_end` 里改 items 想"修正"历史**
   原因：此时本回合的 `new_step_items` 已经定型，改不动。修法：改输入用 `call_model_input_filter`，改输出用输出护栏或 error handler。

三题都在 SDK 根目录 `repo/openai-agents-python/` 下完成。若你的仓库 clone 在别处，按自己的目录替换，后文不再重复。

1. **数 turn**：写一个 `max_turns=2` 的分诊 Agent + 一个必然 handoff 的专家 Agent，跑一次，从异常信息里的 `run_data` 确认它是在第几轮被掐断的。

## 本章小结

- 三层套娃：`Runner.run`（门面 + 脱敏）→ `AgentRunner.run`（状态、trace、session）→ `run_single_turn`（一回合）。
- 一回合七阶段：准备 → 调模型 → 规划 → 执行 → 审批 → 结算 → 推流。
- 结算优先级固定：审批 > handoff > 工具定终局 > 最终输出 > 再来一轮；多 handoff 只认第一个。
- 状态只有三个列表 + 一个计数器；`RunState` 存的就是它们。
- `Turn` 在调模型前自增，handoff 也算一轮，所以 `max_turns` 是"模型调用轮数"。
- 并发一律 `gather_with_cancel`；取消靠标记区分工具内部取消与整体取消；`finally` 负责收尾。
- 抽象极少：读懂 `run_steps.py` 的数据结构，就读懂了半个循环。
