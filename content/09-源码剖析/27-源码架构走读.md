# 第27章 源码架构走读

前 26 章我们一直在"用"。从这一章起换视角：当行为不符合预期、文档没写、或者你要在 SDK 上做二次封装时，唯一可信的东西是源码。

本章解决的真实问题：`src/agents` 有 317 个文件、约 11.8 万行 Python（`tests` 还有 25 万行），**你怎么在十分钟内知道某个行为是在哪实现的**。

---

## 学习目标

- 能画出一次 run 的五段数据流：`str` → `TResponseInputItem` → `ModelResponse` → `RunItem` → `RunResult`，并说清每段转换发生在哪个函数里。
- 能背出 `src/agents` 主要目录的职责，知道一个具体问题该去哪个文件找。
- 能区分三层边界：公开 API 层、`run_internal` 编排层、provider/transport 层，并说明为什么 `run_internal` 不该被依赖。
- 能用"`__init__` 找类 → 找调用点 → 归到 `run_internal` 模块 → 读 tests"这套方法定位任意一个行为。
- 能解释"抽象很少"这个设计取向，以及它带来的阅读策略差异。

## 一、一次 run 的五段数据流

这是全章最该记住的一张图。所有"数据丢了""类型不对""历史重复"的困惑，都能挂到这条链的某一段上。

```text
input                  ModelResponse                RunItem                 RunResult
str | list[dict]  ──►  output: list[...]      ──►  语义包装          ──►  input / new_items
| RunState             usage / response_id          + agent 归属           raw_responses
                                                     + 类型标签             final_output
```

| 阶段 | 类型 | 谁产生 | 特点 |
| --- | --- | --- | --- |
| ① 你传的输入 | `str` / `list[TResponseInputItem]` / `RunState` | 你 | 字符串只是便捷写法 |
| ② 规范化输入 | `list[TResponseInputItem]` | `ItemHelpers.input_to_new_input_list()` | 变成 `{"role": "user", "content": ...}` 这类 dict |
| ③ 模型响应 | `ModelResponse` | `Model.get_response()` | 原生 Responses API 输出 + `usage` + `response_id`，**没有任何 Agent 概念** |
| ④ 运行项 | `RunItem` | `process_model_response()` | 给每个原始输出套上"属于哪个 Agent、是哪一类"的语义 |
| ⑤ 运行结果 | `RunResult` | `Runner.run()` | 把整条链 + 护栏结果 + 用量打包给你 |

还有第四种输入形态要记住：`RunState`。它不是"用户消息"，而是"一次跑到一半的现场"。把 `RunState` 传给 `Runner.run` 相当于"从断点继续"：运行循环跳过了新建状态那一段，直接进 `resolve_interrupted_turn`。这也是为什么 `Runner.run` 的 `input` 类型签名是 `str | list[TResponseInputItem] | RunState[TContext]` 三选一，而不是两种。

关键认知：**`ModelResponse` 是"模型说了什么"，`RunItem` 是"这次 run 里发生了什么"**。前者可以原样 replay 给模型，后者才带得上 Agent 归属、工具输出、审批占位、handoff 记录。你在 `result.new_items` 里看到的是后者，所以它能喂给 UI，却不能直接喂给模型——要喂模型得先 `to_input_list()`。

```python
from agents import Agent, Runner
from agents.items import ItemHelpers

agent = Agent(name="示例", instructions="只回答一个字。")

result = await Runner.run(agent, "今天星期几")   # ② 内部先做 input_to_new_input_list

result.new_items          # ④ list[RunItem]，带 agent 归属
result.raw_responses      # ③ list[ModelResponse]，原始模型输出
result.to_input_list()    # ⑤ 转回 ② 的形态，可以直接作为下一轮 input
result.last_response_id   # ③ 里的 response_id，可传给下一次 run
print(ItemHelpers.text_message_outputs(result.new_items))   # 把 RunItem 拼成纯文本
```

## 二、`src/agents` 目录职责表

按"你什么时候会去读它"排序，而不是按字母序：

| 路径 | 职责 | 什么时候去读 |
| --- | --- | --- |
| `agent.py` | `Agent` / `AgentBase` 定义、`as_tool()`、`clone()`、`tool_use_behavior` 类型 | 不确定某个字段存不存在、默认值是多少 |
| `run.py` | `Runner` 门面 + `AgentRunner`（真正的运行循环，2922 行） | 查 `Runner.run` 的参数、看 turn 计数与终态分支 |
| `result.py` | `RunResult` / `RunResultStreaming`、`to_state()` | 结果字段含义、断点恢复 |
| `items.py` | `RunItem` 全家族、`ModelResponse`、`ItemHelpers` | "这个 item 是什么类型""怎么取文本" |
| `tool.py` | `FunctionTool`、内置/托管工具、工具超时与失败策略 | 工具签名、`needs_approval`、`timeout` |
| `run_context.py` | `RunContextWrapper` / `AgentHookContext` | 上下文与 usage 怎么传 |
| `run_config.py` | `RunConfig` / `RunOptions` / `DEFAULT_MAX_TURNS` | 全局开关（追踪、会话、工具策略） |
| `run_state.py` | `RunState`：可序列化的运行快照 | 审批中断、跨进程恢复 |
| `memory/` | `Session` 接口与 SQLite 实现 | 会话记忆 |
| `mcp/` | MCP server 客户端与工具适配 | MCP 连不上、工具 schema 变形 |
| `models/` | `Model` 接口、OpenAI Responses / Chat Completions / 多 provider | 换模型、改请求参数、看 provider 能力 |
| `tracing/` | trace/span 体系与 processor | trace 不出现、字段缺失 |
| `realtime/` | 实时语音（第 26 章） | 事件语义、transport |
| `voice/` | 三段式语音（第 25 章） | 转写/合成细节 |
| `sandbox/` | 沙箱 Agent、工作区、manifest | 沙箱能力与安全边界 |
| `testing/` | `ScriptedModel` 等测试替身 | 写确定性测试 |
| `extensions/` | 可选集成：`memory`（Redis/Dapr/Mongo…）、`models`（Litellm/AnyLLM）、`sandbox`、`visualization` | 接第三方基础设施 |
| `run_internal/` | **编排实现细节**（24 个模块，1.9 万行） | 想看"到底怎么跑的" |

`run_internal` 再往下分一层，按职责归类就不迷路了：

| 分组 | 模块 | 干什么 |
| --- | --- | --- |
| 回合准备 | `turn_preparation.py`、`agent_bindings.py`、`agent_tool_configuration.py` | 取工具/handoff/模型、过滤模型输入 |
| 模型调用 | `model_retry.py`、`prompt_cache_key.py`、`oai_conversation.py` | 带重试的模型请求、缓存键、服务端会话追踪 |
| 工具规划 | `tool_planning.py`、`tool_use_tracker.py`、`tool_caller.py` | 把模型输出分类成"要执行什么" |
| 工具执行 | `tool_execution.py`（2875 行）、`tool_actions.py` | 真正调用工具、审批、MCP 结果回填 |
| 回合结算 | `turn_resolution.py`（4102 行）、`run_steps.py` | 决定下一步：handoff / 最终输出 / 再来一轮 / 中断 |
| 状态与持久化 | `session_persistence.py`（2079 行）、`run_internal/items.py` | 写 session、恢复被中断的写入 |
| 编排与流式 | `run_loop.py`（3113 行）、`streaming.py`、`approvals.py` | 单回合执行、事件推流、审批占位 |

按行数看，真正的复杂度集中在三个文件：`tool_execution.py`（2875 行）、`turn_resolution.py`（4102 行）、`run_loop.py`（3113 行）。这三个正好对应"工具怎么执行""这一回合怎么结算""一回合怎么跑起来"。而 `run_steps.py` 只有 248 行、`streaming.py` 只有 73 行、`approvals.py` 只有 102 行——它们小，但是理解大文件的地图，先读小的收益最高。

## 三、三层边界：为什么 `run_internal` 不能依赖

`run_internal/__init__.py` 的模块 docstring 把规矩写死了：

> Internal helpers shared by the agent run pipeline. Public-facing APIs (e.g., RunConfig, RunOptions) belong at the top-level; only execution-time utilities that are not part of the surface area should live under run_internal.

翻译成人话，三层是这样切的：

| 层 | 内容 | 稳定性承诺 | 你可以怎么用 |
| --- | --- | --- | --- |
| 公开 API 层 | `agents/__init__.py` 里约 266 个导出名（`Agent`、`Runner`、`RunResult`、`RunConfig`、`function_tool`、`ModelSettings`…） | 有兼容性承诺，改签名要加兼容层 | 随便用 |
| 编排层 | `run_internal/*` | 明确标注"实验性、非公开" | 只读，用来理解行为；不要 import |
| provider / transport 层 | `models/`、`realtime/openai_realtime.py`、`voice/models/`、`mcp/`、`sandbox/` | 接口（`Model`、`RealtimeModel`、`STTModel`…）稳定，OpenAI 实现可换 | 实现接口来替换，而不是改实现 |

一个能说明"为什么分层"的具体例子：一次回合里其实有**两个 Agent 身份**。`bind_public_agent()` 返回的 `AgentBindings` 同时持有 `public_agent`（你创建的那个，出现在 hooks、trace、RunResult 里）和 `execution_agent`（沙箱预处理后的克隆，真正去调模型的那个）。第 28 章会看到，运行循环里到处是 `current_agent` 与 `execution_agent` 的区分——这就是"公开语义"和"执行现实"被拆开的痕迹。

这三层之间有一条硬规矩：**依赖只能向下**。公开层可以调用 `run_internal`，`run_internal` 可以调用 provider 接口，反过来都不行。所以你永远不会在 `models/openai_responses.py` 里看到它 import `Runner`——一旦看到，那就是设计事故而不是风格问题。这条规矩的实际好处是：换 provider 不需要动编排，改编排不需要动公开签名。

`extensions/` 是第四种东西：**它站在公开 API 之上**。里面的 Redis session、Litellm provider 都是"用公开接口拼出来的可选实现"，读它可以学到"如何在不碰内核的前提下扩展 SDK"。

## 四、定位一个行为的五步法

假设问题是：**"`output_type` 校验失败时，SDK 到底抛什么、能不能兜住？"**

**第一步：从 `__init__` 找类。** 打开 `src/agents/__init__.py`，搜 `output_type` 附近的导出，找到 `AgentOutputSchema`（`agent_output.py`）。这一步的目的是确认"这个能力有没有公开名字"。

**第二步：找调用点。** `grep "get_output_schema" src/agents` → 命中 `run_internal/turn_preparation.py`。顺藤摸瓜，`run_single_turn` 里把它传给 `get_single_step_result_from_response`。

**第三步：归到 `run_internal` 模块。** `turn_resolution.py` 里对 `output_schema.validate_json(...)` 的调用负责把模型文本校验成目标类型，失败时抛 `ModelBehaviorError`，紧接着由 `_resolve_invalid_final_output()` 以 `error_kind="invalid_final_output"` 去问你的 handler。

**第四步：读 tests，它们才是规格。** `grep "invalid_final_output" tests` → 你能看到"非空校验失败 → 抛 `ModelBehaviorError`"、"空响应 → 走下一轮"、"handler 返回 `None` → 放弃恢复"这些**只在测试里写清楚**的边界。

**第五步：读 `docs/ref/run_internal/*.md`。** 这些页面是 mkdocstrings 生成的模块索引，一行 `::: agents.run_internal.turn_resolution` 就能列出该模块所有公开符号——比在 4000 行里翻快得多。

具体到命令，五步是这样落地的（在仓库根目录执行）：

```bash
# 1. 这个能力有没有公开名字？
grep -n "AgentOutputSchema" src/agents/__init__.py

# 2. 它在哪里被调用？（搜调用点，不搜定义）
grep -rn "get_output_schema" src/agents --include=*.py

# 3. 归到哪个 run_internal 模块？
ls src/agents/run_internal/ | head -30

# 4. 测试里怎么规定的？
grep -rn "invalid_final_output" tests --include=*.py | head -20

# 5. 模块有哪些公开符号？
sed -n '1,20p' docs/ref/run_internal/turn_resolution.md
```

> 提示：这套方法的关键是**第二步要搜"调用点"而不是"定义"**。搜定义只告诉你"它存在"，搜调用点才告诉你"它什么时候生效"。

## 五、读源码的三个反直觉

**反直觉一：抽象非常少。** 这里没有事件总线、没有插件注册表、没有依赖注入容器。一次 run 就是若干 `async` 函数 + dataclass + 显式参数传递。你想知道某件事会不会发生，去看调用链就行，不用猜"有没有钩子偷偷干了什么"。

**反直觉二：绝大部分代码在处理"恢复"和"边界"，不在主流程。** `run_single_turn` 本体只有约 140 行：跑 hooks、取工具、取 prompt、取 handoff、调模型、交给回合结算。而 `run.py` 有 2922 行，其中大半是"从 RunState 恢复""session 写失败要回滚""错误数据脱敏"。**先读主流程，再按需读恢复路径**，否则会被淹没。

顺便说一句 trace 的位置：trace 不在主流程里"顺便记录"，而是作为上下文管理器包住整次 run（`TraceCtxManager`），再在关键节点开子 span（`agent_span`、`turn_span`、`function_span`、`handoff_span`）。所以你在 trace 里看到的层级，就是运行循环的嵌套结构——**读不通代码时，先去看一次真实 trace 的形状**，往往比读代码更快。

**反直觉三：类型就是文档。** `run_steps.py` 里 `SingleStepResult` 的字段注释，比任何教程都准：`original_input` 可能被 handoff 的 `input_filter` 改过、`pre_step_items` 是"本回合之前生成的项"、`session_step_items` 是"给 session 用的未过滤版本"。读懂这些字段，等于读懂了半个运行循环。

## 常见坑与排查

1. **一上来读 `run.py`，三天没读完**
   原因：门面 + 循环 + 恢复 + 脱敏全在一文件里。修法：先读 `run_internal/run_steps.py`（248 行，纯数据结构），再读 `run_loop.py` 的 `run_single_turn`，最后才回 `run.py` 看分支。

2. **`from agents.run_internal.xxx import ...` 之后升级就炸**
   原因：`run_internal` 明确不承诺兼容，模块会被拆分/改名。修法：只用公开导出；确实需要内部能力，把它当"参考实现"抄思路，而不是 import。

3. **grep 一个类名命中 200 处，看不出重点**
   原因：没有加限定。修法：搜"类名 + 方法名"或"参数名"（例如 `ToolApprovalItem` + `interruptions`），或者直接限定目录 `src/agents/run_internal`。

4. **文档和源码说的不一样**
   原因：文档滞后于实现。修法：以源码为准（本课程所有结论都标注了源码路径），并把差异记进笔记。

5. **分不清 `current_agent` / `execution_agent` / `public_agent`**
   原因：沙箱与工具配置会用克隆体执行，但 hooks/trace 报的是原对象。修法：记住 `AgentBindings` 这一对字段，判断"这个回调里拿到的是谁"。

6. **以为 `RunItem` 可以直接喂给模型**
   原因：`RunItem` 带 SDK 侧语义（审批占位、handoff 记录）。修法：用 `result.to_input_list()` 或 `run_item_to_input_item()` 转成 `TResponseInputItem`。

## 本章小结

- 五段流：`str/list` → `TResponseInputItem` → `ModelResponse`（模型说了什么）→ `RunItem`（run 里发生了什么）→ `RunResult`。
- `ModelResponse` 可 replay，`RunItem` 只可展示；二者靠 `to_input_list()` 打通。
- `src/agents` 分四层：公开 API、`run_internal` 编排、provider/transport、`extensions` 增量。
- `run_internal` 不承诺兼容，只能读不能依赖；它的 `__init__` docstring 就是边界声明。
- 定位行为五步法：`__init__` 找类 → 搜调用点 → 归模块 → 读 tests → 查 `docs/ref`。
- 这个 SDK 抽象很少，主流程很短，长的是恢复与脱敏路径。
- 拿不准时以源码为准，文档会滞后。
