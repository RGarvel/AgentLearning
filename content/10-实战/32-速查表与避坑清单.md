# 第32章 速查表与避坑清单

这是全书的最后一章，它不教你新东西，而是把前 31 章压成四件可以随时翻的东西：一张 import 表、三张参数表、三条决策路径、三十条踩坑记录。用法很直接——写代码时查表，出问题时查清单，不知道该用哪个能力时查决策路径。

如果你只从这本书带走一页纸，就带走这一章。

## 学习目标

- 能在 20 行 import 内找准 90% 场景要用的符号，不再靠猜模块路径。
- 能背出 `Agent` / `Runner` / `RunConfig` 三张表的"参数放哪一层"，避免把运行期配置塞进 Agent。
- 能在 handoff / as_tool、session / to_input_list / previous_response_id、护栏 / 工具内校验之间快速选型。
- 能用 30 条踩坑清单把"症状"反查成"原因 + 修法"，缩短排障时间。
- 能用四阶段 checklist 判断自己的项目现在处于哪一层、下一步该补什么。

## 二、三张参数表：东西该放哪一层

### Agent 字段表（定义"它是谁"）

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `name` | 必填 | 出现在 trace、日志、handoff 工具名里 |
| `instructions` | 无 | 字符串或 `(ctx, agent) -> str` 回调；动态指令用它 |
| `prompt` | 无 | OpenAI 平台 prompt 模板（id/version/variables） |
| `tools` | `[]` | 函数工具、托管工具、`as_tool` 产出的工具 |
| `handoffs` | `[]` | 可直接放 Agent，也可放 `handoff(...)` 定制 |
| `handoff_description` | 无 | 作为交接目标时的描述，直接影响路由准确率 |
| `mcp_servers` / `mcp_config` | `[]` / 默认 | MCP 服务与工具准备策略 |
| `model` | 无 | 字符串或 `Model` 实例；不填走全局默认 provider |
| `model_settings` | 默认值 | `temperature`、`tool_choice`、`reasoning` 等 |
| `output_type` | 无 | 结构化输出类型，触发 strict schema |
| `input_guardrails` / `output_guardrails` | `[]` | 只对链路的第一个 / 最后一个 Agent 生效 |
| `hooks` | 无 | `AgentHooks`，作用域是单个 Agent |
| `tool_use_behavior` | `"run_llm_again"` | 也可 `"stop_on_first_tool"` / `StopAtTools` / 自定义函数 |
| `reset_tool_choice` | `True` | 工具调用后是否把 `tool_choice` 重置为 auto |

### Runner 参数表（定义"这一次怎么跑"）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `starting_agent` | 必填 | 顶层 Agent；断点续跑时仍传顶层 |
| `input` | 必填 | `str` / items 列表 / `RunState` |
| `context` | `None` | 依赖注入对象，工具与护栏都能拿到 |
| `max_turns` | `10` | 超出抛 `MaxTurnsExceeded` |
| `hooks` | `None` | `RunHooks`，覆盖整个 run（含交接） |
| `run_config` | `None` | 模型、追踪、护栏、沙箱等运行期配置 |
| `error_handlers` | `None` | 细分异常处理 |
| `previous_response_id` | `None` | Responses 链式续接 |
| `auto_previous_response_id` | `False` | 自动串上一轮 response |
| `conversation_id` | `None` | Conversations API 会话 |
| `session` | `None` | 本地/自建会话存储 |

> 注意：`session` 与 `conversation_id` / `previous_response_id` / `auto_previous_response_id` **不能同一次 run 混用**，SDK 会直接拒绝。

### RunConfig 常用字段（定义"整个运行环境的策略"）

| 字段 | 用途 |
| --- | --- |
| `model` / `model_provider` / `model_settings` | 统一覆盖本次 run 的模型层 |
| `workflow_name` / `group_id` / `trace_id` / `trace_metadata` | 追踪命名与归组 |
| `tracing_disabled` / `trace_include_sensitive_data` | 关追踪 / 关敏感数据上报（合规） |
| `input_guardrails` / `output_guardrails` | 全运行护栏，兜住"最后说话的 Agent 不确定"的场景 |
| `output_guardrail_blocked_message` | 护栏拦截后给用户看的数据无关兜底文案 |
| `handoff_input_filter` | 全局交接过滤 |
| `session_input_callback` | 控制历史与本轮输入如何合并 |
| `call_model_input_filter` | 发模型前最后一刻改输入（裁剪、脱敏） |
| `tool_error_formatter` | 统一工具失败/审批拒绝的模型可见文案 |
| `tool_name_collision_policy` | 同名工具策略，默认 `"warn"` |
| `sandbox` | `SandboxRunConfig`，决定沙箱客户端与会话来源 |

## 三、三条决策路径

### handoff 还是 as_tool

```text
专家需要"直接对用户说话"、接管后续轮次？
├─ 是 ──► handoff（换 active agent，同一个 run 的下一轮）
└─ 否 ──► 需要汇总多方结论、由主控统一口径？
          ├─ 是 ──► as_tool（嵌套 run，独立 max_turns 与审批）
          └─ 否 ──► 单 Agent + 多个工具
```

判据只有一句：**谁拥有对话**。交接把对话交出去；工具只是借个脑子。补充两条硬差别：handoff 的新 Agent 收到对话历史，as_tool 的新 Agent 收到生成出来的输入；as_tool 的审批会冒泡到外层 run，用外层 `RunState` 处理。

### 跨轮状态：session / to_input_list / previous_response_id

```text
状态存在哪里？
├─ 你自己的存储（SQLite/Redis/PG） ──► session（省事）或 to_input_list（完全手动）
├─ OpenAI Conversations 资源        ──► conversation_id
└─ OpenAI Responses 链式续接        ──► previous_response_id（+ auto_previous_response_id）
```

| 策略 | 适合 | 代价 |
| --- | --- | --- |
| `session` | 生产默认；要可恢复、可审计 | 要选存储后端；默认 `:memory:` 必须改 |
| `to_input_list()` | 小循环、多 provider、要完全控制历史 | 历史越长请求越大，得自己裁剪 |
| `conversation_id` | 跨服务共享的命名会话 | 绑定 OpenAI，迁移成本高 |
| `previous_response_id` | 最轻的服务端续接 | 同样绑定 Responses API；不可与 session 混用 |

### 护栏还是工具内校验

```text
这个检查管"整条链路"还是"单个动作"？
├─ 整条：范围、注入、PII、越界承诺 ──► 护栏
│    ├─ 输入 ──► 挂首个 Agent；要省钱就 run_in_parallel=False
│    └─ 输出 ──► 挂 RunConfig；tripwire 只能拦截，不能改写
└─ 单个动作：金额、参数、权限、幂等 ──► 工具内校验
     └─ 不可逆且有金额影响 ──► 再加 needs_approval
```

一句话记住分工：**护栏决定"能不能开始/能不能交付"，工具校验决定"这一次参数对不对"，审批决定"人同不同意"**。三者不可互相替代。

## 四、从入门到生产的四个阶段

| 阶段 | 你必须已经做到 | 验收信号 |
| --- | --- | --- |
| ① 入门 | 单 Agent + 2-3 个函数工具；`output_type` 出结构化结果；能跑通 `Runner.run_sync` | 能回答"这个 Agent 有哪几个工具、每个工具什么时候被调用" |
| ② 可用 | 输入/输出护栏；`session` 按用户隔离；`trace` + `group_id`；工具失败有兜底 | 线上出问题能在 30 分钟内定位到是哪个 Agent、哪次工具调用 |
| ③ 可靠 | 关键动作 `needs_approval`；`max_turns` / 工具 `timeout`；`ScriptedModel` 形状测试；固定问题集评估 | 改一次 prompt 能说清"哪些指标动了、动了多少" |
| ④ 生产 | 幂等键落库；并发限流；成本看板（token/次）；告警（`MaxTurnsExceeded`、超时、护栏触发率）；灰度与回滚 | 能在不惊动用户的前提下换模型、换 prompt、换后端 |

> 提示：大多数人卡在 ② 到 ③ 之间。差别不是 API 熟练度，而是**有没有可重复的评估**——没有评估，你无法判断改动是优化还是退步。

## 常见坑与排查：30 条

| # | 现象 | 原因 | 修法 |
| --- | --- | --- | --- |
| 1 | 首跑就报 `MaxTurnsExceeded` | `max_turns` 默认 10，链路里有多次工具 + 交接 | 按 trace 的实际轮次调大 |
| 2 | `final_output` 是 `None` | 最后一轮只有工具调用或交接，没有最终消息 | 查 `new_items` 定位，补兜底文案 |
| 3 | 结构化输出反复不合法直到失败 | schema 嵌套太深、字段没描述 | 减少层级、给 `Field` 描述、拆成两步 |
| 4 | 模型反复调同一个工具 | 手动设了 `tool_choice="required"` 又关掉 `reset_tool_choice` | 保持 `reset_tool_choice=True` |
| 5 | 最终答案就是工具原始返回值 | `tool_use_behavior="stop_on_first_tool"` | 改回 `"run_llm_again"` 或用 `StopAtTools` |
| 6 | 交接后新 Agent 像失忆 | `input_filter` 返回的数据把历史项裁空了 | 只删 reasoning 类项，保留消息与工具结果 |
| 7 | `as_tool` 内层的审批外层拿不到 | 只处理了内层 result 的 interruptions | 在外层 `RunResult.interruptions` 处理并续跑顶层 Agent |
| 8 | 传 `session` 又传 `conversation_id` 直接报错 | 二者互斥 | 每次 run 只选一种持久化策略 |
| 9 | 历史条目翻倍、token 暴涨 | 用了 `session` 还手动拼 `to_input_list()` | 用 session 就只传本轮新输入 |
| 10 | 重启后历史全丢 | `SQLiteSession` 默认 `db_path=":memory:"` | 显式给文件路径或换持久后端 |
| 11 | 输入护栏触发了但 token 已花 | `run_in_parallel` 默认 `True`，与 Agent 并发 | `@input_guardrail(run_in_parallel=False)` |
| 12 | 输出护栏挂在分诊 Agent 上不生效 | 护栏只在产出最终输出的 Agent 上跑 | 用 `RunConfig(output_guardrails=[...])` |
| 13 | 护栏没把敏感内容替换掉 | tripwire 只拦截、不改写 | 脱敏放工具返回或 `output_guardrail_blocked_message` |
| 14 | 工具描述为空、参数没说明 | 函数没 docstring 或关了 `use_docstring_info` | 补 docstring，参数写进 Args |
| 15 | 工具拿 `ctx` 报类型不匹配 | `RunContextWrapper` 泛型与 Agent 的 `TContext` 不一致 | 统一 context 类型并显式写 `Agent[SupportContext]` |
| 16 | 工具抛异常导致整个 run 失败 | `failure_error_function=None` | 保留默认或自定义失败文案 |
| 17 | 一条命令卡住拖垮整轮 | 工具没设超时 | `@tool(timeout=15)`，并选 `timeout_behavior` |
| 18 | 审批用的可调用函数根本没跑 | 参数不是合法 JSON object 时 fail closed | 保证工具参数是 object 且可解析 |
| 19 | `always_approve=True` 后同名工具全放行 | sticky 决策按工具名生效 | 用逐次 `state.approve(item)` |
| 20 | 审批被拒后模型反复重试退款 | 没给 `rejection_message` | `state.reject(item, rejection_message="已建工单跟进")` |
| 21 | 改了 `manifest` 沙箱里却不变 | 复用了 `session` 或从 `snapshot` 恢复 | 新建会话，或改快照基线 |
| 22 | `apply_patch` 找不到文件 | 路径以工作区根为准（或 `cwd`），不跟 shell `workdir` | instructions 写清基准，或设 `SandboxRunConfig(cwd=...)` |
| 23 | 自建 `capabilities` 后不能改文件 | `capabilities=[...]` 整体替换了默认列表 | `Capabilities.default() + [...]` |
| 24 | Windows 上 Unix-local 直接报错 | 该后端只支持 macOS/Linux | 换 Docker 或托管后端 |
| 25 | 本地"沙箱"读到了宿主密钥 | Linux 上 Unix-local 无 OS 级隔离 | 换后端；收窄 manifest 与文件权限 |
| 26 | 恢复会话在沙箱启动前失败 | 序列化剥离了 `host_path` 与挂载凭据 | 恢复时提供拓扑一致的可信 manifest |
| 27 | `GitRepo` 物化失败 | 沙箱里没有 `git` | 镜像/宿主预装 git |
| 28 | `clone()` 改 tools 影响了原 Agent | `dataclasses.replace` 浅拷贝，list 共享 | `clone(tools=[*old.tools, extra])` |
| 29 | 两个同名工具被静默覆盖 | `tool_name_collision_policy` 默认 `"warn"`，只告警不拦截 | 改名，或在 RunConfig 里设为 `"error"` |
| 30 | `run_streamed` 拿不到 `final_output` | 事件没消费完 | 先 `async for` 消费完 `stream_events()` 再读 |

## 本章小结

- 参数分三层：Agent 定义"是谁"，Runner 定义"这一次怎么跑"，RunConfig 定义"整个环境的策略"。
- `session` 与 `conversation_id` / `previous_response_id` 互斥，一次 run 只能选一种状态策略。
- 交接与工具的分界线是"谁拥有对话"；护栏与工具校验的分界线是"管整条链路还是管单个动作"。
- 30 条坑里最高频的三类：参数放错层、状态策略混用、把护栏当改写器。
- 从 ② 到 ③ 的分水岭是可重复的评估，不是 API 熟练度。
- 生产化清单的六件事：幂等、限流、成本、告警、灰度、可回滚。
